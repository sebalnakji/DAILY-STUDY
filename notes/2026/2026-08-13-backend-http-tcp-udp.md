## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

### HTTP (HyperText Transfer Protocol)

**클라이언트와 서버 사이에서 데이터를 인코딩하고 전송하는 방법**이다.

- **요청/응답 프로토콜**: 클라이언트가 요청을 보내면, 서버가 관련 콘텐츠와 요청의 완료 상태 정보를 담아 응답한다.
- **자체 완결적(self-contained)** 이라, 요청과 응답이 **로드밸런싱·캐싱·암호화·압축을 수행하는 여러 중간 라우터와 서버를 거쳐 흐를 수 있다.** → [[2026-07-30-backend-load-balancer]], [[2026-08-11-backend-cache]]
- 기본 HTTP 요청은 **동사(메서드)** 와 **리소스(엔드포인트)** 로 구성된다.
- HTTP는 **애플리케이션 계층 프로토콜**로, **TCP나 UDP 같은 하위 프로토콜에 의존**한다.

### HTTP 메서드

| 동사 | 설명 | 멱등성* | 안전 | 캐시 가능 |
|---|---|---|---|---|
| **GET** | 리소스를 읽는다 | ✅ | ✅ | ✅ |
| **POST** | 리소스를 생성하거나 데이터를 처리하는 프로세스를 트리거 | ❌ | ❌ | 응답에 신선도 정보가 있으면 가능 |
| **PUT** | 리소스를 생성하거나 **교체** | ✅ | ❌ | ❌ |
| **PATCH** | 리소스를 **부분 갱신** | ❌ | ❌ | 응답에 신선도 정보가 있으면 가능 |
| **DELETE** | 리소스를 삭제 | ✅ | ❌ | ❌ |

\* **멱등성(Idempotent)**: 여러 번 호출해도 **결과가 달라지지 않는다.**

### TCP (Transmission Control Protocol)

**IP 네트워크 위의 연결 지향(connection-oriented) 프로토콜.** 핸드셰이크로 연결을 수립하고 종료한다.

**전송되는 모든 패킷이 원래 순서대로, 손상 없이 목적지에 도착하도록 보장한다.**

- 패킷마다 **시퀀스 번호**와 **체크섬 필드**
- **확인 응답(ACK) 패킷**과 **자동 재전송**

송신자가 올바른 응답을 받지 못하면 **패킷을 재전송**한다. 타임아웃이 여러 번 발생하면 **연결이 끊긴다.**

TCP는 **흐름 제어(flow control)** 와 **혼잡 제어(congestion control)** 도 구현한다.

> ⚠️ **이 보장들이 지연을 유발해, 일반적으로 UDP보다 전송 효율이 떨어진다.**

**연결 관리 비용**

- 높은 처리량을 위해 웹 서버는 **많은 수의 TCP 연결을 열어둘 수 있는데, 이는 높은 메모리 사용**으로 이어진다.
- 웹 서버 스레드와 memcached 서버 사이에 **연결이 많으면 비쌀 수 있다.**
- **커넥션 풀링(connection pooling)** 이 도움이 되며, 가능한 곳에서는 UDP로 전환하는 것도 방법이다.

**용도**: **높은 신뢰성이 필요하지만 시간에 덜 민감한** 애플리케이션 — 웹 서버, 데이터베이스 정보, SMTP, FTP, SSH

**TCP를 UDP보다 선호할 때**
- **모든 데이터가 온전히 도착해야 할 때**
- **네트워크 처리량을 자동으로 최적 추정**하고 싶을 때

### UDP (User Datagram Protocol)

**비연결(connectionless) 프로토콜.**

- 데이터그램(패킷에 해당)은 **데이터그램 수준에서만 보장**된다. 목적지에 **순서가 뒤바뀌어 도착하거나 아예 도착하지 않을 수 있다.**
- **혼잡 제어를 지원하지 않는다.**
- TCP가 제공하는 보장이 없으므로 **일반적으로 더 효율적이다.**

**브로드캐스트가 가능하다** — 서브넷의 모든 장치에 데이터그램을 보낼 수 있다.
- **DHCP에 유용하다.** 클라이언트가 아직 IP 주소를 받지 못한 상태라 TCP로는 스트리밍할 방법이 없기 때문. → [[2026-07-28-backend-domain-name-system]]

**용도**: 신뢰성은 낮지만 **실시간** 사례에 잘 맞는다 — VoIP, 영상 통화, 스트리밍, 실시간 멀티플레이 게임

**UDP를 TCP보다 선호할 때**
- **가장 낮은 지연시간**이 필요할 때
- **늦게 오는 데이터가 유실보다 나쁠 때**
- **자체 오류 정정**을 직접 구현하고 싶을 때

### TCP vs UDP 정리

| | **TCP** | **UDP** |
|---|---|---|
| 연결 | **연결 지향**(핸드셰이크) | **비연결** |
| 순서 보장 | ✅ | ❌ 뒤바뀔 수 있음 |
| 도착 보장 | ✅ 재전송 | ❌ 유실 가능 |
| 혼잡 제어 | ✅ | ❌ |
| 효율 | 낮음(보장 비용) | **높음** |
| 브로드캐스트 | ❌ | ✅ |
| 적합 | 웹, DB, SMTP, FTP, SSH | **VoIP, 스트리밍, 게임** |

> **핵심 대비: "모든 데이터가 온전히 도착" vs "가장 낮은 지연시간".**
> **늦게 오는 데이터가 유실보다 나쁘다면 UDP다.**

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

**HTTP는 클라이언트와 서버 사이에서 데이터를 인코딩하고 전송하는 방법**이다. 요청/응답 프로토콜로, 클라이언트가 요청을 보내면 서버가 관련 콘텐츠와 완료 상태 정보를 담아 응답한다. HTTP는 **자체 완결적**이어서 요청과 응답이 로드밸런싱, 캐싱, 암호화, 압축을 수행하는 여러 중간 라우터와 서버를 거쳐 흐를 수 있다. 기본 요청은 **동사(메서드)와 리소스(엔드포인트)** 로 구성된다. HTTP는 **애플리케이션 계층 프로토콜**이며 TCP, UDP 같은 하위 프로토콜에 의존한다.

**TCP는 IP 네트워크 위의 연결 지향 프로토콜**이다. 핸드셰이크로 연결을 수립·종료하며, 패킷마다의 **시퀀스 번호와 체크섬**, **확인 응답 패킷과 자동 재전송**을 통해 **모든 패킷이 원래 순서대로 손상 없이 도착하도록 보장**한다. 올바른 응답을 받지 못하면 재전송하고, 타임아웃이 여러 번이면 연결을 끊는다. 흐름 제어와 혼잡 제어도 구현한다. **이런 보장들이 지연을 유발해 UDP보다 전송 효율이 떨어진다.**

높은 처리량을 위해 많은 TCP 연결을 열어두면 메모리 사용이 높아지므로 **커넥션 풀링**이 도움이 된다. TCP는 **높은 신뢰성이 필요하지만 시간에 덜 민감한** 애플리케이션(웹 서버, DB, SMTP, FTP, SSH)에 유용하다.

**UDP는 비연결 프로토콜**이다. 데이터그램은 데이터그램 수준에서만 보장되어 **순서가 뒤바뀌거나 아예 도착하지 않을 수 있다.** 혼잡 제어를 지원하지 않으며, 보장이 없는 만큼 **일반적으로 더 효율적**이다. **브로드캐스트가 가능**해 서브넷의 모든 장치에 보낼 수 있으며, 클라이언트가 아직 IP를 받지 못한 **DHCP**에 유용하다. UDP는 **VoIP, 영상 통화, 스트리밍, 실시간 멀티플레이 게임** 같은 실시간 사례에 잘 맞는다.

**TCP를 쓸 때**는 모든 데이터가 온전히 도착해야 하거나 네트워크 처리량을 자동으로 최적 추정하고 싶을 때다. **UDP를 쓸 때**는 가장 낮은 지연시간이 필요하거나, **늦게 오는 데이터가 유실보다 나쁘거나**, 자체 오류 정정을 구현하고 싶을 때다.

## 내가 정리한 내용

**1. HTTP란? 멱등성은 왜 중요한가**

HTTP는 **클라이언트와 서버 사이에서 데이터를 인코딩하고 전송하는 방법**이다. 요청/응답 프로토콜이며, **애플리케이션 계층**으로 TCP·UDP 같은 하위 프로토콜에 의존한다.

HTTP는 **자체 완결적(self-contained)** 이라, 요청과 응답이 **로드밸런싱·캐싱·암호화·압축을 수행하는 여러 중간 라우터와 서버를 거쳐 흐를 수 있다.**

**멱등성이 중요한 이유는 재시도가 가능해지기 때문**이다. 멱등성을 보장하지 못하면 네트워크가 끊겨 응답을 못 받았을 때 **중복 처리 위험**을 감수해야 한다. GET·PUT·DELETE는 멱등이고 POST·PATCH는 아니다. POST를 안전하게 재시도하려면 **멱등성 키(Idempotency Key)** 를 사용한다.

**2. TCP의 특징과 대가**

**모든 패킷이 원래 순서대로 손상 없이 도착하도록 보장**한다. 시퀀스 번호와 체크섬, 확인 응답(ACK)과 자동 재전송, 흐름 제어와 혼잡 제어로 이를 구현한다.

**대가**는 이 보장들이 **지연을 유발해 전송 효율이 떨어진다**는 것이다. 또한 처리량을 위해 **TCP 연결을 많이 열어두면 메모리 사용이 높아지므로**, 커넥션 풀링이 필요하다.

**3. UDP를 TCP보다 선호하는 경우**

- **가장 낮은 지연시간**이 필요할 때
- **늦게 오는 데이터가 유실보다 나쁠 때** — 전화나 화상통화에서 3초 전 프레임은 지금 도착해도 쓸모없다. 차라리 버리고 다음을 받는 편이 낫다.
- **자체 오류 정정**을 직접 구현하고 싶을 때

또한 UDP는 **브로드캐스트가 가능**해, 클라이언트가 아직 IP를 받지 못한 **DHCP** 같은 상황에 쓸 수 있다.

## 검토 결과

### 확인된 부분

- **멱등성의 가치를 "재시도 가능성"으로 정확히 연결함.** 단순 정의가 아니라 왜 중요한지를 짚었다.
- TCP의 보장 내용과 **두 가지 대가**(지연, 연결당 메모리)를 모두 서술.
- 실습 Q2에서 **앞 프레임 하나가 뒤를 전부 막는 현상**을 정확히 설명. (= 헤드 오브 라인 블로킹)

### 보강 포인트

- **HTTP의 "자체 완결적(self-contained)" 성질이 초기 답변에서 누락 → 추가.** 이 한 성질이 지금까지 배운 것을 전부 가능하게 한다 — **CDN이 중간에서 응답하고, 리버스 프록시가 대신 받고, 로드밸런서가 아무 서버로나 보내도 되는 이유**가 각 요청이 독립적이기 때문이다. → [[2026-07-29-backend-content-delivery-network]], [[2026-07-31-backend-reverse-proxy]], [[2026-07-30-backend-load-balancer]]
- **UDP 선택 기준은 세 가지.** 초기 답변은 "속도가 중요할 때" 하나만 제시했다. 원문의 **"늦게 오는 데이터가 유실보다 나쁠 때"** 가 훨씬 정확한 표현이며 UDP의 존재 이유다.
- **브로드캐스트**는 UDP만의 능력. DHCP 사례가 인상적이다 — **IP를 받으려고 통신하는데 IP가 없어** TCP를 쓸 수 없다. 닭과 달걀 문제를 UDP 브로드캐스트로 푼다.

### 심화: POST 재시도 — 멱등성 키 (Q1)

**"DB를 확인하고 재시도"는 경쟁 조건(race condition)에 취약하다.**

```text
① DB 조회 → "주문 없네"
② 재시도 요청 발송
     ↑ 이 사이에 원래 요청이 서버에 도착하면? → 주문 2개 💥
```

확인하는 순간과 재시도하는 순간 사이에 **틈**이 있다. 원래 요청이 느리게 처리 중이었다면 중복이 난다.

**실무 표준: 멱등성 키(Idempotency Key)**

클라이언트가 요청마다 고유 키를 만들어 헤더에 담는다.

```http
POST /orders
Idempotency-Key: 7f3a9b2c-...

{item: "노트북"}
```

서버는 이 키를 저장해두고 판단한다.

```text
처음 보는 키    → 처리하고 결과를 키와 함께 저장
이미 처리한 키  → 처리하지 않고 저장된 결과를 그대로 반환
```

> **재시도해도 안전해진다. POST를 멱등하게 만드는 것이다.**

Stripe, 토스 같은 결제 API가 전부 이 방식이다. **분산 시스템에서는 중복이 불가피하므로, 중복이 와도 안전하게 만드는 것이 정석이다.** → [[2026-08-12-backend-asynchronism]]의 "SQS 중복 전달 → 워커가 멱등해야 함"

**다른 방법**: `PUT`으로 설계해 **클라이언트가 ID를 생성**하게 한다(`PUT /orders/{client-generated-id}`).

### 심화: 헤드 오브 라인 블로킹 (Q2)

```text
전송: [1][2][3][4][5]
       ✗ 유실
수신: [1][ ][3][4][5]   ← 3,4,5는 이미 도착했는데
        ↑ TCP: "2가 올 때까지 순서 보장을 위해 전부 대기"
```

**3, 4, 5는 이미 손에 있는데도 못 쓴다.** TCP가 순서를 보장하려고 붙잡고 있기 때문. 화상회의에서는 3초 전 프레임을 기어이 받아봐야 쓸모없는데, **그것 때문에 지금 프레임까지 못 본다.**

**이 문제가 HTTP/3를 만들었다** ⭐

| | 기반 | HOL 블로킹 |
|---|---|---|
| HTTP/1.1 | TCP | 있음 |
| HTTP/2 | TCP | **여전히 있음** (스트림은 나눴지만 TCP 계층에서 발생) |
| **HTTP/3** | **QUIC (UDP 기반)** | **해결** |

HTTP/2가 여러 요청을 한 연결에 다중화했는데, TCP가 패킷 하나를 잃으면 **관련 없는 다른 요청들까지 전부 멈췄다.** 그래서 HTTP/3는 아예 **UDP 위에 QUIC이라는 새 프로토콜**을 올려 필요한 신뢰성만 직접 구현했다.

→ 원문의 *"자체 오류 정정을 직접 구현하고 싶을 때 UDP를 쓴다"* 가 실현된 사례.

### HTTP 메서드 정리

| 동사 | 설명 | **멱등** | 안전 | 캐시 |
|---|---|---|---|---|
| **GET** | 읽기 | ✅ | ✅ | ✅ |
| **POST** | 생성 / 처리 트리거 | ❌ | ❌ | 조건부 |
| **PUT** | 생성 또는 **교체** | ✅ | ❌ | ❌ |
| **PATCH** | **부분** 갱신 | ❌ | ❌ | 조건부 |
| **DELETE** | 삭제 | ✅ | ❌ | ❌ |

⚠️ **DELETE가 멱등인 이유**: 첫 번째는 삭제하고 두 번째는 "이미 없음"이지만 **최종 상태는 동일**하다(없음). **멱등성은 응답이 아니라 상태를 기준으로 판단한다.**

**PUT vs PATCH**: PUT은 **통째로 교체**라 멱등이고, PATCH는 **부분 갱신**이라 `{count: count+1}` 같은 연산이 가능해 멱등이 아닐 수 있다.

### TCP vs UDP 한 장

| | **TCP** | **UDP** |
|---|---|---|
| 연결 | **연결 지향**(핸드셰이크) | **비연결** |
| 순서 보장 | ✅ | ❌ 뒤바뀔 수 있음 |
| 도착 보장 | ✅ 재전송 | ❌ 유실 가능 |
| 혼잡 제어 | ✅ | ❌ |
| 효율 | 낮음(보장 비용) | **높음** |
| 브로드캐스트 | ❌ | ✅ |
| 적합 | 웹, DB, SMTP, FTP, SSH | **VoIP, 스트리밍, 게임** |

> **"모든 데이터가 온전히 도착" vs "가장 낮은 지연시간".**

- **Layer 4(TCP/UDP)와 Layer 7(HTTP)** 의 실체. 로드밸런서가 무엇을 보는지가 명확해진다. → [[2026-07-30-backend-load-balancer]]

- **약한 일관성**의 실례가 UDP다 — *"전화 중 몇 초 끊기면 그동안의 말을 듣지 않는다"*. → [[2026-07-22-backend-availability-vs-consistency]]
- **멱등성**은 비동기 큐에서 이미 등장했다. 분산 시스템 전반의 필수 개념. → [[2026-08-12-backend-asynchronism]]
