## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

### SQL을 선택하는 이유

- **구조화된 데이터**(structured data)
- **엄격한 스키마**(strict schema)
- **관계형 데이터**(relational data)
- **복잡한 조인**이 필요할 때
- **트랜잭션**이 필요할 때 → [[2026-08-04-backend-database-rdbms]]의 ACID
- **확장 패턴이 명확**하다 (복제, 페더레이션, 샤딩 등 검증된 경로) → [[2026-08-05-backend-federation-sharding]]
- **더 성숙한 생태계** — 개발자, 커뮤니티, 코드, 도구 등
- **인덱스를 통한 조회가 매우 빠르다** → [[2026-08-06-backend-sql-tuning-nosql]]의 B-트리

### NoSQL을 선택하는 이유

- **반정형 데이터**(semi-structured data)
- **동적이거나 유연한 스키마**
- **비관계형 데이터**
- **복잡한 조인이 필요 없을 때**
- **수 TB(또는 PB) 규모**의 데이터를 저장할 때
- **매우 데이터 집약적인 워크로드**
- **IOPS에 대한 매우 높은 처리량**이 필요할 때

### NoSQL에 잘 맞는 데이터 (원문 예시)

| 예시 | 왜 맞는가 |
|---|---|
| **클릭스트림·로그 데이터의 빠른 수집** | 쓰기가 폭발적으로 많고 구조가 단순 |
| **리더보드·점수 데이터** | 빠른 갱신과 순위 조회 |
| **장바구니 같은 임시 데이터** | 영속성 요구가 낮고 빠르게 변함 |
| **자주 접근되는 '핫' 테이블** | 캐시 성격, 고성능 필요 |
| **메타데이터·룩업 테이블** | 단순 키 조회 |

### 대비 정리

| | **SQL** | **NoSQL** |
|---|---|---|
| 데이터 구조 | 구조화 | **반정형** |
| 스키마 | 엄격 | **동적·유연** |
| 관계 | 관계형 | **비관계형** |
| 조인 | **복잡한 조인 가능** | 조인 불필요할 때 |
| 트랜잭션 | **ACID 지원** | 대개 미지원 (BASE) |
| 규모 | 확장 패턴이 명확 | **TB~PB 규모** |
| 처리량 | 인덱스 조회가 빠름 | **IOPS 처리량이 매우 높음** |
| 생태계 | **성숙함** | 상대적으로 미성숙 |

### 판단의 출발점

> **"데이터가 관계를 갖는가"와 "트랜잭션이 필요한가"를 먼저 묻는다.**
> 둘 중 하나라도 예라면 SQL이 기본 선택이다. 규모와 처리량 요구가 관계형의 확장 한계를 넘어설 때 NoSQL을 고려한다.

성숙한 생태계 역시 실질적인 선택 요인이다. **도구와 인력을 구하기 쉬운 쪽이 유지보수에 유리하다.**

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

**SQL을 선택하는 이유**
- 구조화된 데이터
- 엄격한 스키마
- 관계형 데이터
- 복잡한 조인이 필요함
- 트랜잭션
- 확장에 대한 명확한 패턴
- 더 성숙함 — 개발자, 커뮤니티, 코드, 도구 등
- 인덱스를 통한 조회가 매우 빠름

**NoSQL을 선택하는 이유**
- 반정형 데이터
- 동적이거나 유연한 스키마
- 비관계형 데이터
- 복잡한 조인이 필요 없음
- 수 TB(또는 PB)의 데이터 저장
- 매우 데이터 집약적인 워크로드
- IOPS에 대한 매우 높은 처리량

**NoSQL에 잘 맞는 데이터의 예**
- 클릭스트림과 로그 데이터의 빠른 수집
- 리더보드 또는 점수 데이터
- 장바구니 같은 임시 데이터
- 자주 접근되는 '핫' 테이블
- 메타데이터/룩업 테이블

## 내가 정리한 내용

**1. SQL을 선택하는 이유**

**데이터가 관계를 갖거나 트랜잭션이 필요하면** SQL을 선택한다. 둘 중 하나라도 해당하면 기본 선택이다.

그 밖에도 **구조화된 데이터와 엄격한 스키마**를 다룰 때, **복잡한 조인**이 필요할 때, **인덱스를 통한 조회가 매우 빨라야** 할 때 적합하다. 또한 복제 → 페더레이션 → 샤딩으로 이어지는 **확장 패턴이 명확**하고, 개발자·커뮤니티·도구 등 **생태계가 성숙**하다는 것도 실질적인 장점이다.

**2. NoSQL을 선택하는 이유**

**데이터에 관계가 없고, 트랜잭션이 필요 없으며, 쓰기가 많거나 빠른 조회가 필요할 때** 선택한다.

구체적으로는 **반정형 데이터**를 다루거나 **동적·유연한 스키마**가 필요할 때, **복잡한 조인이 불필요**할 때, **수 TB~PB 규모**를 저장해야 할 때, **IOPS에 대한 매우 높은 처리량**이 필요할 때 적합하다.

대표적인 예로 클릭스트림·로그 수집, 리더보드·점수 데이터, 장바구니 같은 임시 데이터, 자주 접근되는 핫 테이블, 메타데이터·룩업 테이블이 있다.

**3. 실무에서의 판단**

각 DB가 잘하는 역할이 있으므로 **데이터 종류별로 알맞게 나누어 배치**한다. 즉 **저장소 하나를 고르는 것이 아니라 데이터의 생애주기에 따라 배치**하는 것이다(Polyglot Persistence).

예를 들어 쇼핑몰이라면 주문·결제는 트랜잭션이 필수이므로 SQL, 장바구니와 조회 로그는 NoSQL에 둔다. 장바구니는 **결제 시점에 SQL로 넘어가** 트랜잭션으로 묶인다 — **임시일 때는 NoSQL, 확정되면 SQL**이다.

## 검토 결과

### 확인된 부분

- **판단 기준을 두 질문으로 압축함** — "관계를 갖는가 / 트랜잭션이 필요한가". 15개 항목을 실전에서 쓸 수 있는 형태로 정리한 것.
- 실습 Q1(NoSQL 사례의 공통점)을 정확히 도출.
- 실습 Q2(쇼핑몰 배치)를 실무 정답 그대로 배치.
- **3번이 오늘 답변 중 가장 좋다.** "저장소 하나를 고르는 게 아니라 데이터 생애주기에 따라 배치한다" — 시스템 디자인 면접에서 가장 강한 관점.

### 보강 포인트

- **Q1·Q2는 판단 기준만 있고 근거가 얇았다.** 면접관은 "또 어떤 이유가 있죠?"를 되묻는다. **2~3개씩 더** 대야 설득력이 생긴다.
  - SQL 추가 근거: **복잡한 조인**, **인덱스 조회 속도**, **명확한 확장 패턴**, **성숙한 생태계**
  - NoSQL 추가 근거: **유연한 스키마**(반정형), **TB~PB 규모**, **IOPS 처리량**
- **"확장 패턴이 명확하다"는 의외로 강력한 SQL의 장점.** 관계형은 막혔을 때 뭘 해야 할지 정해져 있다(복제 → 나누기 → 튜닝). NoSQL은 더 잘 확장되지만 **길을 직접 찾아야 한다.**

### 심화: 쇼핑몰 배치의 근거 (Q2)

| 데이터 | 선택 | 결정적 이유 |
|---|---|---|
| **주문/결제** | **SQL** | **트랜잭션 필수** — 재고 차감 + 결제 + 주문 생성이 원자적으로 묶여야 함. 틀리면 돈이 걸림 |
| **장바구니** | **NoSQL** | **임시 데이터**. 관계 없고 사용자별로 독립적이며 자주 바뀜. 세션과 성격이 같음 |
| **상품 조회 로그** | **NoSQL** | **쓰기 폭발**. 구조 단순, 조인 불필요, 일부 유실돼도 무방 |

**주문/결제만 "틀리면 돈이 걸리는" 데이터다.** 나머지 둘은 조금 틀려도 아무도 다치지 않는다. → **오류의 비용이 선택을 결정한다.** [[2026-08-04-ai-data-classification-metrics]]

### 심화: 장바구니는 저장소 경계를 넘어간다

```text
[NoSQL] 장바구니 담기 → 수정 → 삭제 ...   ← 임시, 자유롭게
              ↓ 결제 버튼을 누르는 순간
[SQL]   주문 확정 + 재고 차감 + 결제       ← 트랜잭션으로 묶임
```

**같은 데이터가 상태에 따라 저장소를 옮긴다.** 장바구니일 땐 아무 보장이 필요 없지만, **주문이 되는 순간 ACID가 필수**가 된다.

> **임시일 때는 NoSQL, 확정되면 SQL.**

상품 조회 로그도 같다. 실시간 수집은 NoSQL로 받고 **분석은 배치로 데이터 웨어하우스에** 밀어 넣는다. → [[2026-08-09-backend-nosql-types]]의 "Redis로 카운트 받고 주기적으로 관계형에 밀어 넣기"와 같은 구조.

**면접에서는 저장소를 하나 고르는 것보다 데이터 생애주기에 따라 배치하는 답이 훨씬 강하다.**

### NoSQL 적합 사례 5가지의 공통점 (Q1)

| 예시 | 왜 |
|---|---|
| 클릭스트림·로그 수집 | 쓰기 폭발, 구조 단순 |
| 리더보드·점수 | 빠른 갱신 + 순위 조회 |
| 장바구니 같은 임시 데이터 | 영속성 요구 낮음, 빠르게 변함 |
| 자주 접근되는 '핫' 테이블 | 캐시 성격 |
| 메타데이터·룩업 테이블 | 단순 키 조회 |

> **관계가 없고, 트랜잭션이 필요 없고, 쓰기가 많거나 빠른 조회가 필요한 것들.**
