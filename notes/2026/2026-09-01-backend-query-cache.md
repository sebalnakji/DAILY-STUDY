| **Query Cache** | **LRU 캐시 자료구조** + **캐시 클러스터 분산 전략** |

[[2026-08-11-backend-cache]]에서 캐시를 **개념**으로 배웠다면, 여기서는 그 캐시를 **직접 만든다**.

### Step 1 — 유스케이스와 제약

#### 유스케이스(범위 안)

| 주체 | 유스케이스 |
|---|---|
| 사용자 | 검색 요청 → **캐시 적중(cache hit)** |
| 사용자 | 검색 요청 → **캐시 미스(cache miss)** |
| 서비스 | **고가용성(High Availability)** 을 갖는다 |

#### 가정과 제약

- 트래픽은 **고르게 분포하지 않는다**
  - **인기 쿼리는 거의 항상 캐시에 있어야** 한다
  - **만료·갱신 방법**을 정해야 한다
- 캐시에서 서빙하려면 **조회가 빨라야** 한다
- 머신 간 **지연이 낮다**
- **캐시 메모리가 제한적이다**
  - **무엇을 남기고 무엇을 버릴지** 정해야 한다
  - **수백만 개 쿼리**를 캐싱해야 한다
- 사용자 **1,000만 명**
- 월 **쿼리 100억 건**

#### Step 1 계산 — 어림 계산(Back-of-the-envelope)

캐시는 `key: 쿼리` → `value: 결과` 의 **순서 있는 목록**을 저장한다.

| 필드 | 크기 |
|---|---:|
| `query` | 50 bytes |
| `title` | 20 bytes |
| `snippet` | 200 bytes |
| **합계** | **270 bytes** |

| 항목 | 계산 | 결과 |
|---|---|---:|
| 전부 유일하고 전부 저장한다면 | 270 B × 100억 | **2.7 TB/월** |
| 평균 요청 | 100억 ÷ 250만 초 | **4,000 QPS** |

> ⚠️ **2.7 TB는 "저장하면 안 된다"는 신호다.** 제약에 "메모리가 제한적"이라고 적혀 있으므로, **무엇을 버릴지 정하는 것이 이 문제의 핵심**이 된다. 어림 계산이 곧바로 설계 방향(만료 정책 필요)을 지목한다.

환산 치트시트 — [[2026-08-19-backend-latency-numbers]]:

```text
1개월 ≈ 250만 초
1 req/s   = 월 250만 요청
40 req/s  = 월 1억 요청
400 req/s = 월 10억 요청
```

### Step 2 — 상위 수준 설계

```text
   Client ──▶ Web Server (리버스 프록시) ──▶ Query API
                                                │
                                    ┌───────────┴────────────┐
                                    ▼                        ▼
                            ┌──────────────┐         (캐시 미스 시)
                            │ Memory Cache │                │
                            │  (LRU)       │                ▼
                            └──────────────┘    ┌────────────────────────┐
                                                │ Reverse Index Service  │
                                                │ Document Service       │
                                                └────────────────────────┘
```

### Step 3 — 핵심 컴포넌트 설계

#### 캐시 적중 경로

인기 쿼리를 **Memory Cache**(Redis, Memcached)에서 서빙해 읽기 지연을 줄이고, **Reverse Index Service**와 **Document Service**의 과부하를 막는다.

> 메모리에서 1 MB 순차 읽기 ≈ **250 μs**, SSD는 **4배**, 디스크는 **80배** 느리다 — [[2026-08-19-backend-latency-numbers]]

캐시 용량이 제한적이므로 **LRU(Least Recently Used, 가장 오래 안 쓴 것부터 버림)** 방식으로 만료시킨다.

**흐름**

1. Client → **Web Server**(리버스 프록시)
2. Web Server → **Query API** 서버
3. Query API가 **쿼리를 파싱**한다
   - 마크업 제거
   - 텍스트를 **용어(term)** 단위로 분해
   - 오타 교정
   - 대소문자 정규화
   - 불리언 연산 형태로 변환
4. **Memory Cache**를 확인
   - **적중**: 해당 항목을 **LRU 목록 맨 앞으로 이동**시키고 캐시 내용 반환
   - **미스**:
     - **Reverse Index Service**로 매칭 문서를 찾고 **순위를 매겨 상위 결과**를 받음
     - **Document Service**로 제목·스니펫을 받음
     - 캐시를 갱신하고 항목을 **LRU 목록 맨 앞에 배치**

> 💡 **파싱을 캐시 조회 "전에" 하는 이유** — `"Machine Learning"`, `"machine learning"`, `"machien learning"`은 정규화하면 **같은 키**가 된다. 정규화 전에 조회하면 같은 의도의 쿼리가 캐시에서 전부 다른 항목이 되어 **적중률이 폭락**한다. 캐시 키 설계의 핵심이다.

#### LRU 캐시 자료구조 — 해시 테이블 + 이중 연결 리스트

**요구사항**: 조회 `O(1)`, 삽입 `O(1)`, 만료 대상 선택 `O(1)`.

| 자료구조 하나만 쓰면 | 문제 |
|---|---|
| 해시 테이블만 | 조회는 `O(1)`이지만 **"가장 오래 안 쓴 것"을 못 찾는다** — 순서 정보가 없음 |
| 연결 리스트만 | 순서는 알지만 **특정 쿼리 조회가 `O(n)`** |

**그래서 둘을 합친다.**

```text
해시 테이블 (lookup)          이중 연결 리스트 (LRU 순서)
  "python"  ──────┐
  "java"    ────┐ │      head ⇄ [python] ⇄ [java] ⇄ [rust] ⇄ tail
  "rust"    ──┐ │ │             최근 사용                오래됨
              │ │ │               ▲                        │
              └─┴─┴───────────────┘                        │
                                                    여기서 제거
```

- **head(앞)**: 새 항목·방금 쓴 항목을 붙인다
- **tail(뒤)**: 용량이 찼을 때 제거한다
- **해시 테이블**: 쿼리 → 노드 포인터. 리스트 중간 노드에 `O(1)`로 바로 접근
- **이중 연결(doubly-linked)인 이유**: 중간 노드를 떼어내려면 **앞 노드를 알아야** 한다. 단일 연결이면 앞 노드를 찾느라 `O(n)`

**핵심 동작**

```python
def get(self, query):
    """조회하면 그 항목이 LRU 목록 맨 앞으로 이동한다."""
    node = self.lookup[query]
    if node is None:
        return None
    self.linked_list.move_to_front(node)
    return node.results

def set(self, results, query):
    node = self.lookup[query]
    if node is not None:
        node.results = results
        self.linked_list.move_to_front(node)
    else:
        if self.size == self.MAX_SIZE:
            # 가장 오래된 항목을 리스트와 해시 테이블 양쪽에서 제거
            self.lookup.pop(self.linked_list.tail.query, None)
            self.linked_list.remove_from_tail()
        else:
            self.size += 1
        new_node = Node(query, results)
        self.linked_list.append_to_front(new_node)
        self.lookup[query] = new_node
```

> ⚠️ 제거할 때 **리스트와 해시 테이블 양쪽에서** 지워야 한다. 한쪽만 지우면 **댕글링 참조**가 남는다.

**Query API**는 전형적인 **cache-aside** 형태다.

```python
def process_query(self, query):
    query = self.parse_query(query)
    results = self.memory_cache.get(query)
    if results is None:
        results = self.reverse_index_service.process_search(query)
        self.memory_cache.set(query, results)
    return results
```

#### 캐시를 언제 갱신하는가

캐시된 결과가 **낡는(stale)** 경우가 있다.

| 갱신이 필요한 상황 |
|---|
| 페이지 **내용이 바뀜** |
| 페이지가 **삭제되거나 새 페이지가 추가됨** |
| 페이지 **랭크가 바뀜** |

가장 단순한 처리는 **TTL(Time To Live, 캐시 유효기간)** 을 두어 일정 시간이 지나면 갱신하는 것이다.

> 위 방식은 **cache-aside** 패턴이다 — [[2026-08-11-backend-cache]]에서 다룬 write-through, write-behind, refresh-ahead와 트레이드오프를 비교할 것.

**LRU와 TTL은 목적이 다르다.**

| | LRU | TTL |
|---|---|---|
| 해결하는 문제 | **용량 부족** — 메모리가 모자람 | **신선도** — 데이터가 낡음 |
| 버리는 기준 | 안 쓴 지 오래됨 | 넣은 지 오래됨 | 
| 없으면? | 메모리 초과 | 낡은 결과를 계속 서빙 |

**둘 다 필요하다.** 인기 쿼리는 LRU로는 영원히 안 버려지므로, TTL이 없으면 몇 달 된 검색 결과를 계속 보여주게 된다.

#### Memory Cache를 여러 머신으로 확장

4,000 QPS와 대용량 메모리를 감당하려면 **수평 확장**이 필요하다. 데이터를 클러스터에 어떻게 둘지 **세 가지 선택지**가 있다.

| 방식 | 설명 | 평가 |
|---|---|---|
| **각 머신이 자기만의 캐시를 가짐** | 로드밸런서가 보낸 요청을 각자 알아서 캐싱 | 단순하지만 **적중률이 낮다** — 같은 쿼리가 머신마다 따로 캐싱되어 중복 |
| **각 머신이 캐시 전체 복사본을 가짐** | 모든 머신이 같은 내용을 보유 | 단순하지만 **메모리 낭비가 심하다** — N대면 용량이 1/N |
| **캐시를 클러스터 전체에 샤딩** | `machine = hash(query)` 로 담당 머신 결정 | 더 복잡하지만 **가장 좋은 선택**. **일관된 해싱(consistent hashing)** 을 쓰는 것이 좋다 |

```text
① 각자 캐시            ② 전체 복사             ③ 샤딩
 M1: [a,b,c]           M1: [a,b,c]            M1: [a,d,g]
 M2: [a,b,d]           M2: [a,b,c]            M2: [b,e,h]
 M3: [a,c,e]           M3: [a,b,c]            M3: [c,f,i]
 "a"가 3중 중복        용량이 1/3             중복 없음, 용량 3배
 적중률 낮음           메모리 낭비            hash(query)로 위치 결정
```

> 💡 **일관된 해싱이 필요한 이유** — 단순 `hash(query) % N`을 쓰면 머신을 3대에서 4대로 늘릴 때 **거의 모든 키의 담당 머신이 바뀐다.** 캐시 전체가 미스가 되어 백엔드가 순간적으로 폭주한다. 일관된 해싱은 머신 추가·제거 시 **재배치되는 키를 약 1/N로 제한**한다. [[2026-08-31-backend-design-mint]]에서 샤딩의 리샤딩 문제로 이미 등장했다.

## 내가 정리한 내용

### 1. 어림 계산이 지목한 것

- 2.7 TB는 **메모리에 올릴 수 있는 크기가 아니기 때문에 저장하면 안 된다는 신호**다.
- 따라서 이 문제의 핵심은 **무엇을 버릴 것인가를 결정하는 만료 정책**이 필요하다는 것을 지목한다.

### 2. 파싱을 캐시 조회 전에 하는 이유

정규화 전에 조회하면 **같은 의도의 쿼리가 캐시에서 전부 다른 항목**이 되어 **적중률이 폭락**한다.

### 3. LRU 캐시 자료구조

- **연결 리스트**는 가장 오래 안 쓴 것을 **순서 정보**를 통해 제공한다.
- **해시 테이블**은 특정 쿼리 조회를 `O(1)`로 제공한다.
- 자료구조 하나로는 안 되고 둘 다 필요하다. 이 둘은 **노드 포인터**를 통해 이어진다 — 해시 테이블이 저장하는 값은 결과가 아니라 **리스트 노드를 가리키는 포인터**다.
- 리스트는 **이중 연결(doubly-linked)** 이어야 한다. 중간 노드를 떼어내 맨 앞으로 옮기려면 **앞 노드를 알아야** 하는데, 단일 연결이면 앞 노드를 찾느라 `O(n)`이 되어 포인터로 얻은 `O(1)`이 깨진다.

### 4. LRU와 TTL의 차이

- **LRU는 가장 오래 안 쓴(Least Recently Used)** 캐시를 정리하고, **TTL은 넣은 지 오래된** 캐시를 정리한다.
- LRU는 **마지막 사용 시각**을 보고, TTL은 **삽입 시각**을 본다.
- LRU는 **용량 부족** 문제를 해결하고 TTL은 **신선도(최신화)** 문제를 해결한다.

### 5. 캐시 클러스터 분산 세 방식

- **각자 캐시** → 단순하지만 적중률이 낮음
- **전체 복사** → 단순하지만 메모리 낭비
- **샤딩** → 복잡하지만 최적

**가용성 축**을 더하면: 머신 1대가 죽을 때 전체 복사는 **아무 일도 안 일어나고**, 샤딩은 **그 샤드의 키가 전부 미스가 되어 백엔드로 몰린다.** 전체 복사는 **읽기 처리량도 N배**다.

| 방식 | 용량 | 적중률 | 가용성 |
|---|---|---|---|
| 각자 캐시 | N배 | 낮음 | 부분 손실 |
| 전체 복사 | **1배** | 높음 | **최고** |
| 샤딩 | N배 | 높음 | **취약** |
| **샤딩 × 복제** | N배 | 높음 | 높음 |

그래서 실무는 하나를 고르지 않고 **샤딩(가로) × 복제(세로)를 겹친다.** 용량은 샤딩으로, 가용성은 복제로. Redis Cluster가 이 구조다.

## 검토 결과

### 확인된 부분

- **2.7 TB를 "용량 수치"가 아니라 "설계 방향을 지목하는 신호"로 읽었다.** 어림 계산의 목적이 숫자 자체가 아니라 **판단**이라는 걸 이해한 답이다.
- **캐시 키 정규화의 이유**를 정확히 짚었다 — 같은 의도의 쿼리가 다른 항목이 되면 적중률이 무너진다.
- **두 자료구조의 역할 분담**과 **노드 포인터로 이어진다**는 연결 고리까지 스스로 정리했다.
- **머신 1대 사망 시나리오**에 "복제는 커버 가능, 나머지는 데이터 손실"이라고 가용성 축을 정확히 답했다.

### 보강 포인트

#### ① LRU는 "가장 오래된"이 아니라 "가장 오래 안 쓴"

| | 내용 |
|---|---|
| **전** | LRU는 **가장 오래된** 캐시를 정리하고, TTL은 시간이 만료된 캐시를 정리함 |
| **후** | LRU는 **가장 오래 안 쓴(Least Recently Used)** 캐시를 정리하고, TTL은 **넣은 지 오래된** 캐시를 정리함 |

**이것이 LRU와 TTL을 가르는 바로 그 지점이다.**

```text
쿼리 "python" : 3개월 전에 캐싱, 방금 전에도 조회됨

LRU 관점 → "방금 썼네"        → head에 있음 → 절대 안 버림
TTL 관점 → "넣은 지 3개월"    → 만료        → 버림
```

**같은 항목을 놓고 정반대 판단**을 한다. "가장 오래된"이라고 하면 LRU가 TTL과 같은 기준을 쓰는 것처럼 읽히고, 그러면 "LRU는 용량, TTL은 최신화"라는 구분 자체가 성립하지 않는다.

**정확한 대비**: LRU는 **마지막 사용 시각**, TTL은 **삽입 시각**.

#### ② 이중 연결 리스트여야 하는 이유

포인터로 중간 노드에 **착지**하는 것까지는 됐는데, 착지한 다음 **떼어내는 동작**도 `O(1)`이어야 전체가 `O(1)`이 된다. 교정 후 내용은 위 `내가 정리한 내용` 3번에 반영.

#### ③ 분산 세 방식에 가용성 축과 하이브리드가 빠졌다

직전 대화에서 스스로 정확히 답한 내용인데 정리에서 누락됐다. 교정 후 내용은 위 `내가 정리한 내용` 5번에 반영.

### 심화: 해시 테이블이 저장하는 것은 "결과"가 아니라 "노드 포인터"

```text
lookup["java"] → 리스트 중간에 있는 [java] 노드를 가리키는 포인터
```

이게 두 자료구조를 잇는 핵심이다. 포인터를 갖고 있으니 리스트를 앞에서부터 훑지 않고 **중간 노드에 곧바로 착지**할 수 있다. 해시 테이블이 결과값만 갖고 있었다면 "이 쿼리에 해당하는 노드가 리스트 어디 있지?"를 찾느라 다시 `O(n)`이 된다.

그리고 착지한 다음이 **이중 연결이 필요한 지점**이다.

```text
단일 연결:  [a] → [b] → [c]     b를 빼려면? a를 알아야 하는데 못 감
이중 연결:  [a] ⇄ [b] ⇄ [c]     b.prev로 a에 바로 접근 → O(1)
```

| 하나만 쓰면 | 할 수 있는 것 | 못 하는 것 |
|---|---|---|
| 해시 테이블만 | 조회 `O(1)` | **"가장 오래 안 쓴 것"을 못 찾는다** — 순서 정보 없음 |
| 연결 리스트만 | 순서 관리 | **특정 쿼리 조회가 `O(n)`** |

> ⚠️ 제거할 때는 **리스트와 해시 테이블 양쪽에서** 지워야 한다. 리스트에서만 빼면 해시 테이블에 **죽은 노드를 가리키는 포인터**가 남는다.

### 심화: LRU만 있고 TTL이 없을 때의 역설

```text
인기 쿼리일수록 → 자주 조회됨 → 계속 head로 이동 → 영원히 tail에 안 감 → 절대 안 버려짐
                                                                          ↓
                                                            가장 많이 노출되는 결과가
                                                                  가장 낡았다
```

**LRU는 인기 있는 항목을 보호하도록 설계된 정책**이다. 그런데 신선도 관점에서는 그게 정확히 **최악의 결과**를 만든다. 하루에 백만 번 노출되는 검색어의 결과가 몇 달 전 것일 수 있다.

두 정책은 **서로를 보완하지 않고 각자 다른 축을 담당한다.** LRU는 "메모리가 모자랄 때 누구를 버릴까"에만 답하고, "이 데이터가 아직 맞나"에는 **아무 말도 하지 않는다.** 그 질문에 답하는 것이 TTL이다.

검색 결과가 낡는 경우: 페이지 **내용 변경**, 페이지 **삭제·추가**, 페이지 **랭크 변경**.

### 심화: 샤딩의 진짜 위험은 데이터 손실이 아니다

머신 1대가 죽었을 때 샤딩에서 벌어지는 일은 단순한 데이터 소실이 아니다. **그 샤드가 담당하던 키들이 전부 캐시 미스가 되어 백엔드(Reverse Index Service)로 한꺼번에 몰린다.**

캐시를 둔 이유가 백엔드 보호였는데, **캐시 머신 사망이 오히려 백엔드에 부하 스파이크를 만든다.**

복제 방식은 이 문제가 없고, **읽기 처리량도 N배**다 — 어떤 머신에 물어봐도 답이 나오니 요청을 완전히 균등하게 뿌릴 수 있다. 샤딩은 특정 인기 쿼리를 담당한 머신만 뜨거워질 수 있다.

```text
샤딩(가로) × 복제(세로)

        샤드1        샤드2        샤드3
주 노드 [a,d,g]     [b,e,h]     [c,f,i]
복제본  [a,d,g]     [b,e,h]     [c,f,i]   ← 주 노드가 죽으면 승격
```

### 심화: 일관된 해싱(Consistent Hashing)

단순 `hash(query) % N`을 쓰면 머신을 3대→4대로 늘릴 때 **거의 모든 키의 담당 머신이 바뀐다.** 캐시 전체가 미스가 되어 백엔드가 순간 폭주한다.

**일관된 해싱은 머신 추가·제거 시 재배치되는 키를 약 `1/N`로 제한한다.** [[2026-08-31-backend-design-mint]]에서 샤딩의 리샤딩 문제로 이미 등장했던 개념이 여기서 다시 나온다.

### 이전 학습과의 연결

- [[2026-08-11-backend-cache]] — 거기서 캐시를 **개념**으로 배웠다면 여기서는 **직접 만든다.** cache-aside 패턴이 `process_query`에 그대로 구현돼 있고, TTL·write-through·refresh-ahead 논의가 여기서 실물이 된다.
- [[2026-08-19-backend-latency-numbers]] — `1개월 ≈ 250만 초`로 4,000 QPS를 도출. 메모리 1 MB 순차 읽기 250 μs vs SSD 4배, 디스크 80배가 **캐시를 메모리에 두는 이유**다.
- [[2026-08-31-backend-design-mint]] — **샤딩과 일관된 해싱**이 두 문제 연속으로 등장. 거기서는 DB 샤드 키(`user_id`), 여기서는 캐시 샤드 키(`hash(query)`).
- [[2026-08-27-backend-design-web-crawler]] — 검색 파이프라인의 **앞단(수집)** 이 크롤러라면, 이 문제는 **뒷단(질의 응답)** 이다. Reverse Index Service가 둘을 잇는다.
- [[2026-08-28-backend-scaling-to-millions]] — "초기 설계에서 최종 설계로 바로 점프하지 말 것" 절차를 그대로 따랐다.
- [[2026-08-20-backend-design-pastebin]] — 둘 다 읽기 우세 문제. Pastebin은 저장이 목적이고 이 문제는 **캐싱 자체가 목적**이다.
