# 성능(Performance)과 확장성(Scalability)의 차이는 무엇인가?

## 출처

- 기준 레포: `donnemartin/system-design-primer`
- 원본 파일: `README.md` — `## Performance vs scalability` 섹션 (System design topics: start here의 첫 번째 주제)
- 영역: Backend / System Design

## 질문

> **Performance vs scalability** — 두 개념은 어떻게 다르며, 어떤 시스템을 "확장 가능하다(scalable)"고 말할 수 있는가?

## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

- **Performance(성능)**: 하나의 작업 단위를 얼마나 빠르게 처리하는가. 사용자 한 명 기준의 응답 속도.
- **Scalability(확장성)**: 자원을 추가한 만큼 성능이 **비례해서** 증가하는 성질. 자원을 2배 넣었는데 처리량이 1.1배면 확장성이 나쁜 것이다.
- **"더 많은 일" 두 가지 의미**
  - 단위 작업의 **개수**가 늘어나는 경우 (요청 수 증가)
  - 단위 작업의 **크기**가 커지는 경우 (데이터셋 증가)
- **증상으로 구분하기** — 문제를 진단할 때 가장 실용적인 기준
  - 사용자 1명일 때도 느리다 → **성능 문제**
  - 사용자 1명일 때는 빠른데 부하가 걸리면 느려진다 → **확장성 문제**
- **처방이 다르다**: 성능 문제는 알고리즘·쿼리·N+1·인덱스 등 단일 경로 최적화로 접근하고, 확장성 문제는 수평 확장·캐시·비동기화·병목 자원 분리로 접근한다.
- **모든 것은 트레이드오프**: 확장성을 얻기 위해 보통 복잡도, 일관성, 비용 중 무언가를 내준다.

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

어떤 서비스가 **scalable**하다는 것은, **추가한 자원에 비례하는 만큼 성능이 증가**한다는 뜻이다. 여기서 성능이 증가한다는 것은 보통 더 많은 작업 단위를 처리한다는 의미지만, 데이터셋이 커질 때처럼 **더 큰 작업 단위**를 처리하는 것을 뜻하기도 한다.

두 개념을 구분하는 또 다른 관점은 다음과 같다.

- **성능 문제**가 있다면, 시스템은 **사용자 한 명에 대해서도 느리다**.
- **확장성 문제**가 있다면, 시스템은 사용자 한 명에게는 빠르지만 **부하가 높아지면 느려진다**.

## 내가 정리한 내용

**1. 성능(Performance)이란?**

요청이 한 개일 때, 그 한 개의 요청을 처리하는 데 걸리는 시간.

**2. 확장성(Scalability)이란?**

서버 같은 자원을 늘렸을 때 **처리량(같은 시간에 소화하는 요청 수)이 그에 비례해 늘어나는 정도**를 뜻한다. 서버를 2배 늘렸을 때 처리량도 2배가 되면 확장성이 좋다고 하고, 1.1배에 그치면 확장성이 나쁘다고 한다.

주의할 점은 **자원을 늘려도 요청 한 건의 처리 속도 자체는 빨라지지 않는다**는 것이다. 늘어나는 것은 동시에 감당할 수 있는 양이다.

**3. 왜 둘을 구분해야 하는가?**

둘을 잘 구분하지 못하면 병목이 생기는 **원천적인 문제를 해결하지 못한 채 돈과 자원만 낭비**할 수 있기 때문이다.

## 검토 결과

### 확인된 부분

- 성능의 정의("요청 한 개일 때 걸리는 시간")를 정확히 서술함. 부하가 없는 상태를 기준으로 잡은 것이 핵심.
- 구분해야 하는 이유를 **"원천 문제 미해결 + 자원 낭비"** 로 짚음. 이 질문의 진짜 채점 포인트를 정확히 맞힘.
- 실습 Q1(평소 200ms → 오전 9시 3초)을 확장성 문제로 정확히 진단.

### 보강 포인트

- **확장성은 "속도"가 아니라 "처리량"의 문제다.** (최초 답변에서 속도로 서술 → 교정)
  - 요리사를 2명 → 4명으로 늘려도 파스타 한 접시는 여전히 5분이다. 대신 동시에 4접시를 만들 수 있다.
  - 검증법: 손님 한 명뿐인 한가한 식당에 요리사를 100명 붙여도 그 손님의 응답 시간은 그대로다.
  - 단, **이미 대기열이 긴 상황**에서는 자원을 늘리면 체감 응답 시간도 줄어든다. 그러나 이는 조리가 빨라진 게 아니라 **줄이 짧아진 것**이다. → 다음 주제 `Latency vs Throughput`으로 연결.
- **확장성 문제에 성능 처방을 쓰면 안 된다.** (Q2 오답 지점)
  - "서버 2대 → 4대인데 처리량 1.1배"에 알고리즘 개선으로 답했으나, 알고리즘을 2배 빠르게 해도 서버를 8대로 늘리면 또 1.1배다.
  - **알고리즘 개선은 천장의 높이만 올릴 뿐, 천장 자체를 없애지 못한다.**
- **병목은 "같이 쓰는 자원"에서만 생긴다.** 확장성 문제의 핵심 원리.
  - 서버마다 독립적인 것(CPU·메모리·로컬 캐시)은 서버를 늘리면 같이 늘어난다.
  - 안 늘어난 것 = 모두가 공유하는 것. 거기서만 줄이 생긴다.
  - 그래서 시선을 **늘린 자원(앱 서버)이 아니라 안 늘린 공유 자원(DB)** 으로 돌려야 한다.
- **의심 순서 체크리스트**
  1. DB 마스터 (1순위 — CPU / 커넥션 풀 / 락 대기)
  2. 전역 락·분산 락 (직렬 구간)
  3. 상태를 가진 서버 (스티키 세션으로 부하 쏠림)
  4. 외부 API rate limit
  5. 측정 오류 (부하 생성기나 로드밸런서가 먼저 포화)
- **Q1 정교화**: "서버 2배면 어느 정도 개선된다"에는 *병목이 앱 계층에 있다*는 가정이 숨어 있다. 병목이 DB 마스터라면 서버 증설 효과는 0이거나, 커넥션·경합 증가로 **오히려 악화**된다. 면접에서는 **"병목이 어디냐에 따라 다릅니다"** 가 만점 답.
- **암달의 법칙(Amdahl's law)**: 병렬화 불가능한 직렬 구간이 5%만 남아도 자원을 무한히 늘렸을 때 최대 20배에서 멈춘다. 확장성 논의가 항상 "병목이 어디냐"로 수렴하는 이유.

### 한 장 요약

| | 성능 | 확장성 |
|---|---|---|
| 질문 | 한 건이 얼마나 빠른가? | 자원을 늘린 만큼 처리량이 늘어나는가? |
| 증상 | 혼자 써도 느림 | 혼자 쓸 땐 빠른데 몰리면 느려짐 |
| 원인 | 느린 코드·쿼리 | 공유 자원(DB·락)의 경합 |
| 처방 | 코드·쿼리 최적화 | 서버 증설 + 공유 자원 병목 제거 |
| 비유 | 레시피가 느리다 | 창고가 하나다 |
