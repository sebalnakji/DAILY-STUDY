# 비동기 처리(Asynchronism) — 메시지 큐와 백프레셔

## 질문

> **비동기 워크플로는 무엇을 해결하는가? 메시지 큐와 태스크 큐는 어떻게 동작하며, 백프레셔는 왜 필요한가?**
>
> 원문: *Asynchronism / Message queues / Task queues / Back pressure*

## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

### 비동기 워크플로가 하는 일

- **비싼 연산의 요청 시간을 줄인다.** 인라인(동기)으로 수행하면 오래 걸릴 작업을 뒤로 뺀다.
- **시간이 오래 걸리는 작업을 미리 해둔다.** 예: 데이터의 주기적 집계(aggregation).

### 메시지 큐(Message Queue)

**메시지를 받고, 보관하고, 전달한다.** 인라인으로 수행하기엔 너무 느린 연산에 사용한다.

```text
① 애플리케이션이 큐에 작업을 게시(publish)하고, 사용자에게 작업 상태를 알린다
② 워커가 큐에서 작업을 가져와 처리하고, 완료를 알린다
```

- **사용자는 차단(block)되지 않고**, 작업은 백그라운드에서 처리된다.
- 이 시간 동안 클라이언트가 **작업이 완료된 것처럼 보이게 하는 약간의 처리**를 할 수도 있다.
  - 예: **트윗을 게시하면 내 타임라인에는 즉시 표시되지만, 모든 팔로워에게 실제로 전달되기까지는 시간이 걸릴 수 있다.**

**대표 도구**

| 도구 | 특징 |
|---|---|
| **Redis** | 단순한 메시지 브로커로 유용하지만 **메시지가 유실될 수 있다** |
| **RabbitMQ** | 인기 있지만 **AMQP 프로토콜에 적응**해야 하고 **노드를 직접 관리**해야 한다 |
| **Amazon SQS** | 호스팅형이지만 **지연시간이 높을 수 있고 메시지가 두 번 전달될 가능성**이 있다 |

### 태스크 큐(Task Queue)

**태스크와 관련 데이터를 받아 실행하고 결과를 전달한다.**

- **스케줄링을 지원**할 수 있고, **계산 집약적인 작업을 백그라운드로** 돌리는 데 쓴다.
- **Celery**: 스케줄링을 지원하며 주로 Python을 지원한다.

### 백프레셔(Back Pressure)

**큐가 크게 자라면 생기는 문제**가 있다.

> 큐 크기가 **메모리보다 커지면** 캐시 미스, 디스크 읽기가 발생해 **성능이 더 느려진다.**

**백프레셔는 큐 크기를 제한**해, 이미 큐에 있는 작업들에 대해 **높은 처리량과 좋은 응답 시간을 유지**한다.

- 큐가 가득 차면 클라이언트는 **`server busy` 또는 HTTP 503** 상태 코드를 받고 나중에 다시 시도한다.
- 클라이언트는 **지수 백오프(exponential backoff)** 로 재시도할 수 있다.

### 비동기 처리의 단점

- **저렴한 계산이나 실시간 워크플로는 동기 연산이 더 적합할 수 있다.** 큐를 도입하면 **지연과 복잡도가 추가**되기 때문.

### 정리

| | 동기 처리 | 비동기 처리 |
|---|---|---|
| 사용자 대기 | **기다림** | **기다리지 않음** |
| 적합한 작업 | 저렴한 계산, 실시간 | **비싼 연산, 오래 걸리는 작업** |
| 대가 | — | **지연과 복잡도 추가** |

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

**비동기 워크플로는 인라인으로 수행하면 오래 걸릴 비싼 연산의 요청 시간을 줄이는 데 도움이 된다.** 또한 데이터의 주기적 집계처럼 **시간이 오래 걸리는 작업을 미리 수행**하는 데도 유용하다.

**메시지 큐**는 메시지를 받고 보관하고 전달한다. 연산이 인라인으로 하기엔 너무 느릴 때 다음 흐름으로 사용한다. 애플리케이션이 큐에 작업을 게시하고 사용자에게 상태를 알리면, 워커가 큐에서 작업을 가져와 처리한 뒤 완료를 알린다. **사용자는 차단되지 않고 작업은 백그라운드에서 처리된다.** 이 동안 클라이언트가 작업이 완료된 것처럼 보이게 하는 약간의 처리를 할 수도 있다. 예를 들어 트윗을 게시하면 내 타임라인에는 즉시 게시되지만, 모든 팔로워에게 실제로 전달되기까지는 시간이 걸릴 수 있다.

도구로는 **Redis**(단순 브로커로 유용하나 메시지 유실 가능), **RabbitMQ**(인기 있으나 AMQP 적응과 노드 관리 필요), **Amazon SQS**(호스팅형이나 높은 지연과 중복 전달 가능성)가 있다.

**태스크 큐**는 태스크와 관련 데이터를 받아 실행하고 결과를 전달한다. 스케줄링을 지원할 수 있고 계산 집약적인 작업을 백그라운드로 돌리는 데 쓴다. **Celery**가 대표적이다.

**백프레셔**는 큐가 크게 자랄 때 필요하다. 큐 크기가 메모리보다 커지면 캐시 미스와 디스크 읽기가 발생해 성능이 더 느려진다. 백프레셔는 **큐 크기를 제한**해 이미 큐에 있는 작업의 높은 처리량과 좋은 응답 시간을 유지한다. 큐가 가득 차면 클라이언트는 `server busy`나 **HTTP 503**을 받고, **지수 백오프**로 나중에 재시도할 수 있다.

**단점**은 저렴한 계산이나 실시간 워크플로의 경우 큐 도입이 **지연과 복잡도를 더하므로** 동기 연산이 더 나을 수 있다는 점이다.

## 내가 정리한 내용

**1. 비동기 처리는 무엇을 해결하는가**

- **비싼 연산의 요청 시간을 줄인다.** 인라인으로 수행하면 오래 걸릴 작업을 뒤로 뺀다.
- **오래 걸리는 작업을 미리 해둔다.** 예: 데이터의 주기적 집계.

핵심은 **사용자가 차단(block)되지 않는다**는 것이다. 작업은 백그라운드에서 처리되고, 클라이언트는 완료된 것처럼 보이게 하는 처리를 할 수 있다(트윗은 내 타임라인에 즉시 표시되지만 팔로워 전달은 나중).

**2. 메시지 큐의 동작 흐름**

```text
사용자 요청 → 큐에 작업 게시 → 사용자에게 상태 응답
            → 워커가 큐에서 꺼내 처리 → 완료 신호
```

사용자는 응답을 받고 차단되지 않으며, 작업은 백그라운드에서 처리된다.

도구로는 **Redis**(단순하나 메시지 유실 가능), **RabbitMQ**(AMQP 적응·노드 관리 필요), **Amazon SQS**(호스팅형이나 높은 지연·중복 전달 가능)가 있다.

**3. 백프레셔란? 왜 필요한가**

**큐 크기를 제한하는 장치**다. 큐가 메모리보다 커지면 캐시 미스와 디스크 읽기가 발생해 **오히려 성능이 더 느려지기** 때문이다.

큐 크기를 제한하면 **이미 큐에 있는 작업들의 처리량과 응답 시간을 지킬 수 있다.** 즉 **일부 요청을 거절해서 나머지를 살리는 것**이다.

동작은 두 단계로 나뉜다.

- **서버**: 큐가 가득 차면 `server busy` 또는 **HTTP 503**을 반환하며 거절한다.
- **클라이언트**: 503을 받으면 **지수 백오프**로 나중에 재시도한다. 모두가 동시에 재시도하면 또 몰리므로 간격을 점점 늘린다.

## 검토 결과

### 확인된 부분

- 비동기 처리의 두 가지 효과(요청 시간 단축 / 미리 해두기)를 정확히 구분.
- 메시지 큐의 흐름을 간결하게 도식화.
- **백프레셔의 목적**(큐가 메모리를 넘으면 오히려 느려짐 → 크기 제한으로 기존 작업 보호)을 정확히 파악.

### 보강 포인트

- ⚠️ **백프레셔에서 "거절"과 "재시도"의 주체가 다르다.** (두 번 반복된 혼동 → 교정)

  ```text
  ① 서버:      큐가 가득 참 → HTTP 503 반환하며 거절
  ② 클라이언트: 503을 받음 → 지수 백오프로 나중에 재시도
  ```

  **서버는 거절만 하고 끝난다.** 언제 다시 올지는 클라이언트가 정한다. **백프레셔의 역할은 ①까지**이고 ②는 클라이언트의 동작이다.
  - 면접에서 뭉뚱그리면 "백프레셔가 재시도를 관리한다"로 오해되므로 **주체를 나눠 말할 것.**
  - **지수 백오프가 필요한 이유**: 거절당한 클라이언트들이 1초 뒤 일제히 다시 오면 또 몰려서 죽는다. 간격을 1초 → 2초 → 4초로 늘리고 **랜덤 지터**를 섞어 시간을 흩뜨린다. → 어제 배운 **썬더링 허드**와 같은 문제. [[2026-08-11-backend-cache]]

- **썸네일과 트위터는 비동기의 모양이 다르다.** (Q1 실습)
  - **트위터**: *"남들에게 언제 보이나"* — 팬아웃 지연
  - **썸네일**: *"파생물이 아직 존재하지 않는다"* — 결과물 부재

  ```text
  업로드 → [즉시] "업로드 완료!" 응답 + 원본 저장
             ↓ 큐에 썸네일 생성 작업 게시
          [백그라운드] 워커가 썸네일 생성
  ```

  **진짜 설계 질문: 썸네일이 아직 없는데 조회 요청이 오면?**

  | 방법 | 내용 |
  |---|---|
  | **원본 폴백** | 썸네일이 없으면 원본을 축소해 응답 (느리지만 보이긴 함) |
  | **플레이스홀더** | 회색 박스나 블러 이미지를 먼저 |
  | **알림** | 완료되면 웹소켓·폴링으로 갱신 |

  > **비동기로 뺀 순간 "아직 안 된 상태"를 UI가 다뤄야 한다.** 이것이 원문이 말한 **복잡도 추가**의 실체다. 백엔드만 바뀌는 게 아니라 프론트까지 대응해야 한다.

### 도구별 대가 — 공짜가 없다

| 도구 | 특징 | ⚠️ 대가 |
|---|---|---|
| **Redis** | 단순한 브로커로 유용 | **메시지 유실 가능** |
| **RabbitMQ** | 인기 있음 | **AMQP 적응 + 노드 직접 관리** |
| **Amazon SQS** | 호스팅형(관리 불필요) | **높은 지연 + 중복 전달 가능성** |

**SQS의 "중복 전달"이 특히 중요하다.** 같은 메시지가 두 번 올 수 있으므로 **워커가 멱등(idempotent)** 해야 한다. 결제 메시지가 두 번 와도 두 번 결제되면 안 된다.

### 메시지 큐 vs 태스크 큐

- **메시지 큐**: 메시지를 **받고 보관하고 전달**
- **태스크 큐**: 태스크와 데이터를 받아 **실행하고 결과를 전달**. **스케줄링을 지원**하고 계산 집약적 작업을 백그라운드로 돌린다. **Celery**가 대표(Python).

> **메시지 큐가 배관이면, 태스크 큐는 배관 + 실행기다.** 실제로 Celery는 내부적으로 Redis나 RabbitMQ를 브로커로 쓴다.

### 단점 — 만능이 아니다

> **저렴한 계산이나 실시간 워크플로는 동기 연산이 더 적합할 수 있다.** 큐를 도입하면 **지연과 복잡도가 추가**되기 때문.

10ms짜리 작업을 큐에 넣으면 큐 왕복 때문에 오히려 느려진다. 그리고 **실패 추적, 재시도, 중복 처리, 순서 보장**을 전부 새로 고민해야 한다.

- **Write-behind가 비동기 쓰기의 캐시 버전.** "빠르지만 유실 위험"이라는 성질이 동일하다. → [[2026-08-11-backend-cache]]
