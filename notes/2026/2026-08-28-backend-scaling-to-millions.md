## 질문

> **AWS에서 수백만 사용자까지 확장되는 시스템을 설계하라.**
>
> 원문: *Design a system that scales to millions of users on AWS*

## 핵심 개념

### Step 1. 제약과 가정

- 트래픽은 고르게 분포하지 않는다
- **관계형 데이터가 필요**하다
- **사용자 1명에서 수천만 명까지** 확장한다 (증가를 `Users+`, `Users++`, ... 로 표기)
- 사용자 **1천만 명**, 월 **10억 쓰기**, 월 **1,000억 읽기** → **읽기:쓰기 = 100:1**
- 쓰기당 콘텐츠 **1 KB**

**어림 계산**

```text
월 신규 콘텐츠 1 TB  (1KB × 10억)
3년이면 36 TB

평균 초당 쓰기    400건
평균 초당 읽기 40,000건
```

---

### Step 3. 단일 서버에서 시작한다

> **사용자가 1~2명이면 기본 설정만 있으면 된다.** 단순하게 **단일 박스**, 필요하면 **수직 확장**, 그리고 **병목을 찾기 위한 모니터링.**

- **EC2에 웹 서버** + 사용자 데이터 저장 + **MySQL 데이터베이스**
- **수직 확장(Vertical Scaling)**: 더 큰 박스를 고른다
  - CPU, 메모리, IO, 네트워크 등 **기본 모니터링으로 병목 파악** (CloudWatch, top, nagios 등)
  - ⚠️ **수직 확장은 매우 비싸질 수 있고, 이중화·페일오버가 없다**
- **관계형 데이터가 필요하다는 제약**이 있으니 **MySQL로 시작**한다
- **고정 공인 IP(Elastic IP)** 할당 — 재부팅해도 IP가 안 바뀌어 **페일오버에 유리**하다
- **DNS**(Route 53)로 도메인을 인스턴스 공인 IP에 매핑
- **보안**: 필요한 포트만 개방 (80/HTTP, 443/HTTPS, 22/SSH는 화이트리스트 IP만). **웹 서버의 아웃바운드 연결도 차단.**

---

### Step 4. 사용자 증가에 따른 단계별 확장

**모든 단계가 같은 형식을 따른다: 벤치마크·프로파일링으로 병목을 발견 → 목표 설정 → 조치 → 단점 인지.**

#### Users+ — 단일 박스의 한계

**발견된 병목**: **MySQL이 메모리와 CPU를 점점 더 많이 차지**하고, **사용자 콘텐츠가 디스크를 채운다.** 지금까지는 수직 확장으로 버텼지만 **비싸졌고, MySQL과 웹 서버를 독립적으로 확장할 수 없다.**

**조치**
- **정적 콘텐츠를 Object Store(S3)로 분리** — 사용자 파일, JS, CSS, 이미지, 비디오
- **MySQL을 별도 박스로 이동** (RDS 같은 관리형 서비스 고려 — 관리·확장이 쉽고 다중 가용 영역, 저장 시 암호화)
- **보안**: 전송 중·저장 시 암호화, **VPC 사용** — 웹 서버만 **퍼블릭 서브넷**, 나머지는 **프라이빗 서브넷**

**단점**: 복잡도 증가, 웹 서버 수정 필요, 새 컴포넌트에 대한 추가 보안 조치, AWS 비용 증가

#### Users++ — 웹 서버가 병목

**발견된 병목**: **피크 시간에 단일 웹 서버가 병목**이 되어 응답이 느려지고 때때로 다운된다. 서비스가 성숙하면서 **고가용성과 이중화**도 필요해졌다.

**조치**
- **수평 확장**으로 부하와 단일 장애점 해결
  - **로드밸런서**(ELB, HAProxy) 추가. 자체 구성 시 **active-active 또는 active-passive를 여러 가용 영역에**
  - **로드밸런서에서 SSL termination** — 백엔드 연산 부하를 줄이고 인증서 관리를 단순화
  - **여러 가용 영역에 웹 서버 분산**
  - **MySQL을 Master-Slave 페일오버**로 여러 가용 영역에 배치
- **웹 서버와 애플리케이션 서버를 분리** — 두 계층을 **독립적으로 확장·설정**. 웹 서버는 **리버스 프록시**로 동작. 예: **Read API용 앱 서버와 Write API용 앱 서버를 분리**
- **정적(및 일부 동적) 콘텐츠를 CDN(CloudFront)으로** 이동해 부하와 지연을 줄인다

#### Users+++ — 데이터베이스 읽기가 병목

**발견된 병목**: **읽기가 압도적으로 많고(쓰기와 100:1)**, 높은 읽기 요청 때문에 **데이터베이스 성능이 나빠졌다.**

**조치**
- **메모리 캐시(Elasticache)** 도입
  - MySQL에서 **자주 접근되는 콘텐츠**
  - ⭐ **먼저 MySQL의 자체 캐시 설정으로 충분한지 확인**한 뒤 메모리 캐시를 도입한다
  - **웹 서버의 세션 데이터** → 웹 서버가 **무상태**가 되어 **오토스케일링이 가능**해진다
- **MySQL 읽기 복제본** 추가로 쓰기 마스터의 부하를 줄인다
  - 웹 서버에 **읽기와 쓰기를 분리하는 로직** 추가
  - 읽기 복제본 앞에도 **로드밸런서** 배치
  - **대부분의 서비스는 쓰기보다 읽기가 많다**
- 웹 서버와 앱 서버를 더 추가

#### Users++++ — 오토스케일링

**발견된 병목**: **미국 업무 시간에 트래픽이 치솟고 퇴근 후 크게 떨어진다.** 실제 부하에 따라 서버를 자동으로 켜고 끄면 **비용을 줄일 수 있다.**

**조치**
- **오토스케일링** 도입 — 트래픽 스파이크 대응 + **미사용 인스턴스를 꺼서 비용 절감**
  - 웹 서버·앱 서버 유형별로 그룹을 만들고 **여러 가용 영역에 배치**
  - **최소·최대 인스턴스 수** 설정
  - CloudWatch로 스케일 트리거: **시간대 기반**(예측 가능한 부하) 또는 **지표 기반**(CPU, 지연시간, 네트워크 트래픽, 커스텀 지표)
  - ⚠️ **단점**: 복잡도 증가, **적절히 스케일업/다운되기까지 시간이 걸린다**
- **DevOps 자동화** (Chef, Puppet, Ansible)
- **지속적 모니터링**
  - **호스트 수준** — 개별 EC2 인스턴스
  - **집계 수준** — 로드밸런서 통계
  - **로그 분석** — CloudWatch, CloudTrail, Loggly, Splunk
  - **외부 사이트 성능** — Pingdom, New Relic
  - **알림·인시던트** — PagerDuty / **에러 리포팅** — Sentry

#### Users+++++ — 계속 반복

> **제약에 명시된 수치를 향해 성장하면서, 새 병목을 발견하고 해결하기 위해 벤치마크·프로파일링을 반복적으로 수행한다.**

- **MySQL이 너무 커지면** 일정 기간 데이터만 DB에 두고 나머지는 **데이터 웨어하우스(Redshift)** 로 옮긴다
- **초당 4만 읽기**의 인기 콘텐츠는 **메모리 캐시 확장**으로 대응한다. 고르지 않은 트래픽과 스파이크 처리에도 유용하다

---

### 이 문서의 진짜 교훈

> **처음부터 최종 설계를 그리지 않는다. 매 단계마다 "측정 → 병목 발견 → 조치 → 단점 인지"를 반복한다.**

각 단계의 **가정(Assumptions) 항목이 전부 "벤치마크와 프로파일링이 ~을 가리킨다"** 로 시작하는 것에 주목할 것. **추측이 아니라 측정이 다음 조치를 결정한다.**

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

**Step 3 — 단일 박스로 시작**: 사용자가 1~2명이면 EC2 위의 웹 서버와 MySQL을 한 박스에 두고, 필요하면 **수직 확장**하며 모니터링으로 병목을 파악한다. 수직 확장은 **매우 비싸지고 이중화가 없다**는 한계가 있다. 고정 공인 IP와 DNS를 두고, 필요한 포트만 개방한다.

**Users+**: MySQL이 메모리·CPU를 잡아먹고 콘텐츠가 디스크를 채운다. **정적 콘텐츠를 S3로 분리**하고 **MySQL을 별도 박스로 이동**해 **독립적 확장**을 가능하게 한다. VPC로 퍼블릭/프라이빗 서브넷을 나눈다.

**Users++**: 피크 시간에 단일 웹 서버가 병목이 된다. **로드밸런서를 추가하고 웹 서버를 여러 가용 영역에 분산**하며, MySQL은 **Master-Slave 페일오버**로 둔다. **웹 서버와 애플리케이션 서버를 분리**해 독립적으로 확장하고, 정적 콘텐츠를 **CDN**으로 옮긴다. **로드밸런서에서 SSL termination**을 수행한다.

**Users+++**: 읽기가 쓰기의 100배라 DB 읽기가 병목이다. **메모리 캐시**를 도입하되 **먼저 MySQL 자체 캐시로 충분한지 확인**한다. **세션 데이터를 캐시로 옮기면 웹 서버가 무상태**가 되어 오토스케일링이 가능해진다. **MySQL 읽기 복제본**을 추가하고 웹 서버에 읽기·쓰기 분리 로직을 넣는다.

**Users++++**: 트래픽이 업무 시간에 몰린다. **오토스케일링**으로 스파이크에 대응하고 미사용 인스턴스를 꺼 비용을 줄인다. 단, **복잡도가 늘고 스케일에 시간이 걸린다.** DevOps를 자동화하고 호스트·집계·로그·외부 성능 수준에서 **지속적으로 모니터링**한다.

**Users+++++**: MySQL이 너무 커지면 일부만 DB에 두고 나머지는 **데이터 웨어하우스**로 옮긴다. 인기 콘텐츠 읽기는 **메모리 캐시 확장**으로 대응한다.

**전체를 관통하는 원칙은 "벤치마크·프로파일링으로 병목을 발견하고, 조치하고, 반복한다"** 이다.

## 내가 정리한 내용

**1. 확장의 절차**

**단일 박스에서 시작해** 병목이 나타날 때마다 하나씩 추가한다. 처음부터 최종 설계를 그리지 않는다.

각 단계는 **측정 → 조치 → 대가** 구조로 진행되며, **모든 단계의 가정이 벤치마크·프로파일링 결과로 시작**한다. 즉 **추측이 아니라 데이터가 다음 조치를 결정**한다.

**2. 단계별 병목과 조치**

- **MySQL이 메모리·CPU를 잠식하고 콘텐츠가 디스크를 채움** → **정적 콘텐츠를 S3로 분리**하고 **MySQL을 별도 박스로 이동**해 독립적 확장을 가능하게 함
- **피크 시간에 단일 웹 서버가 병목, 때때로 다운** → **로드밸런서 추가 + 여러 가용 영역에 웹 서버 분산**, **웹 서버와 애플리케이션 서버 분리**, CDN 도입
- **읽기가 쓰기의 100배, DB가 읽기 부하로 죽어남** → **메모리 캐시 도입**(단, 먼저 MySQL 자체 캐시로 충분한지 확인), **읽기 복제본 추가 + 웹 서버에 읽기/쓰기 분리 로직**
- **업무 시간에 트래픽이 몰리고 퇴근 후 급감** → **오토스케일링**으로 스파이크 대응 및 비용 절감

**3. 무상태(stateless)가 중요한 이유**

**오토스케일링의 본질은 "서버를 함부로 죽여도 되게 만드는 것"** 이다. 세션이 서버 메모리에 있으면 그 서버를 끌 때 세션이 소실되어 사용자가 로그아웃되므로 **서버를 함부로 끌 수 없고, 스케일 다운이 불가능**하다.

**세션을 캐시로 빼 서버를 무상태로 만들어야** 아무 서버나 켜고 꺼도 무해해져 **오토스케일링이 가능**해진다. 무상태는 있으면 좋은 것이 아니라 **오토스케일링의 전제 조건**이다.

## 검토 결과

### 확인된 부분

- **문서의 메타 구조(측정 → 조치 → 대가)를 정확히 포착**하고, "추측이 아니라 데이터가 다음 조치를 결정한다"는 핵심 메시지를 뽑아냈다.
- 병목과 조치를 **인과 쌍으로** 정리해, 각 컴포넌트가 어떤 문제의 답인지 명확히 했다.
- **무상태가 오토스케일링의 전제**라는 인과 사슬을 정확히 서술.

### 보강 포인트

- **"단일 박스에서 시작한다"는 출발점**을 명시할 것. 처음부터 최종 설계를 그리지 않는다는 것이 이 문서의 첫 메시지다.

### 심화: 왜 처음부터 최종 설계를 그리면 안 되나 (Q1)

복잡도와 자원 낭비 외에 **근본적인 문제**가 있다.

> **병목을 모른 채 만든 구조는 실제 병목과 안 맞을 수 있다.**

**각 컴포넌트는 특정 병목의 해답**이다.

| 컴포넌트 | 어떤 병목의 답인가 |
|---|---|
| 로드밸런서 | 웹 서버가 부족할 때 |
| 캐시 | DB 읽기가 많을 때 |
| 읽기 복제본 | 캐시 미스가 많을 때 |
| 샤딩 | 쓰기가 한계일 때 |

**병목이 다른 데 있다면?** 실제 문제가 **느린 쿼리 하나**였다면 로드밸런서를 10대 붙여도 여전히 느리다. → *"성능 문제에 서버를 늘려봐야 소용없다."* [[2026-07-20-backend-performance-vs-scalability]]

**면접에서도 그대로 갈린다.** 처음부터 최종 설계를 그리면 *"왜 이게 필요하죠?"* 에 답을 못 한다. **각 컴포넌트가 어떤 병목을 푸는지** 말할 수 있어야 한다.

그래서 원문이 매번 **"Do not simply jump right into the final design"** 을 굵게 강조한다.

### 심화: 무상태가 오토스케일링의 전제인 이유 (Q2)

```text
세션이 서버 메모리에 있음
   ↓
그 서버를 끄면 → 세션 소실 → 사용자 로그아웃 💥
   ↓
서버를 함부로 못 끔
   ↓
오토스케일링 불가 (스케일 다운을 못 함)
```

**세션을 캐시로 빼면**

```text
아무 서버나 꺼도 무해
아무 서버나 켜도 즉시 투입 가능
   ↓
오토스케일링 가능 ✅
```

**sticky session이 차선책인 이유**가 *"그 서버가 죽으면 세션이 통째로 날아간다"* 였다. **오토스케일링은 서버가 죽는 것을 전제로 하는 기능**이므로 무상태가 필수 조건이 된다. → [[2026-07-30-backend-load-balancer]]

> **무상태는 "있으면 좋은 것"이 아니라 오토스케일링의 입장권이다.**

### 단계별 상세

**Step 3 — 단일 박스**
- EC2 한 대에 **웹 서버 + MySQL**, 필요하면 **수직 확장**
- ⚠️ **수직 확장은 매우 비싸질 수 있고 이중화·페일오버가 없다**
- 고정 공인 IP(Elastic IP), DNS(Route 53), 필요한 포트만 개방(80/443/22 화이트리스트)

**Users+ — DB와 정적 파일 분리**
- 정적 콘텐츠 → **S3** / MySQL → **별도 박스(RDS)**
- **VPC**로 퍼블릭(웹 서버)/프라이빗(나머지) 서브넷 분리
- → [[2026-08-20-backend-design-pastebin]]의 *"큰 파일은 Object Store에, DB는 가볍게"*

**Users++ — 수평 확장**
- 로드밸런서 + 여러 가용 영역 분산, **로드밸런서에서 SSL termination**
- MySQL **Master-Slave 페일오버**
- ⭐ **웹 서버와 애플리케이션 서버 분리** — 웹 서버는 리버스 프록시, 앱 서버는 **Read API용/Write API용으로 분리 가능**
- **CDN**으로 정적 콘텐츠 이동
- → [[2026-08-03-backend-application-layer]]의 계층 분리

**Users+++ — 캐시와 읽기 복제본**
- ⭐ **먼저 MySQL 자체 캐시 설정으로 충분한지 확인**한 뒤 메모리 캐시 도입
  - **새 컴포넌트를 추가하기 전에 기존 것의 설정부터** 보라는 조언. → [[2026-08-06-backend-sql-tuning-nosql]]의 "측정이 먼저"
- **세션 데이터를 캐시로** → 웹 서버 무상태 → 오토스케일링 가능
- 읽기 복제본 + 웹 서버에 읽기/쓰기 분리 로직

**Users++++ — 오토스케일링**
- 스파이크 대응 + **미사용 인스턴스를 꺼 비용 절감**
- 최소·최대 인스턴스 수 설정, CloudWatch 트리거(시간대 기반 / 지표 기반)
- ⚠️ **복잡도 증가, 스케일에 시간이 걸림**
- **4단계 모니터링**: 호스트 / 집계(로드밸런서) / 로그 / 외부 성능

**Users+++++ — 반복**
- MySQL이 너무 커지면 **일정 기간만 DB에, 나머지는 데이터 웨어하우스(Redshift)로**
- 인기 콘텐츠 읽기는 **메모리 캐시 확장**

### 실전 4종 비교 — 이 문서만 다르다

| | Pastebin / Twitter / Crawler | **Scaling to Millions** |
|---|---|---|
| 초점 | **무엇을 만들 것인가** | **어떻게 키울 것인가** |
| Step 4 | 최종 구성 나열 | **단계별 진화 과정** |
| 교훈 | 도메인별 병목 | **절차 그 자체** |
