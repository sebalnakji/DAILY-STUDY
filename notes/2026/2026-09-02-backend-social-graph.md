## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

### 이 문제의 성격 — 데이터가 한 대에 안 들어가는 그래프

지금까지 푼 실전 문제와 결정적으로 다른 점이 있다.

| 문제 | 데이터 접근 패턴 |
|---|---|
| [[2026-08-20-backend-design-pastebin]] | 키 하나로 값 하나 조회 — **1회 조회** |
| [[2026-08-31-backend-design-mint]] | `user_id`로 한 샤드 조회 — **1회 조회** |
| [[2026-09-01-backend-query-cache]] | `hash(query)`로 한 머신 조회 — **1회 조회** |
| **Social Graph** | 친구의 친구의 친구… — **탐색 중에 조회가 계속 발생** |

앞의 문제들은 **어느 샤드로 갈지 미리 알 수 있었다.** 이 문제는 **가 봐야 다음에 어디로 갈지 알 수 있다.** 이 차이가 설계 전체를 지배한다.

### Step 1 — 유스케이스와 제약

#### 유스케이스(범위 안)

| 주체 | 유스케이스 |
|---|---|
| 사용자 | 누군가를 검색해 **자신으로부터 그 사람까지의 최단 경로**를 본다 |
| 서비스 | **고가용성(High Availability)** 을 갖는다 |

#### 가정과 제약

- 트래픽은 **고르게 분포하지 않는다** — 어떤 검색은 인기가 많고, 어떤 것은 딱 한 번 실행된다
- **그래프 데이터가 한 대에 안 들어간다**
- 그래프 간선에 **가중치가 없다(unweighted)**
- 사용자 **1억 명**
- 사용자당 **평균 친구 50명**
- 월 **친구 검색 10억 건**

#### Step 1 계산 — 어림 계산

| 항목 | 계산 | 결과 |
|---|---|---:|
| 친구 관계(간선) 수 | 1억 × 50 | **50억 개** |
| 평균 검색 요청 | 10억 ÷ 250만 초 | **400 QPS** |

환산 치트시트 — [[2026-08-19-backend-latency-numbers]]:

```text
1개월 ≈ 250만 초
400 req/s = 월 10억 요청
```

> 💡 **"간선에 가중치가 없다"** 는 제약이 알고리즘을 지목한다. 가중치가 있으면 다익스트라(Dijkstra)가 필요하지만, **가중치가 없으면 BFS(Breadth-First Search, 너비 우선 탐색)로 충분**하다. BFS는 출발점에서 가까운 순서대로 훑으므로, 목적지에 처음 도달한 경로가 곧 최단 경로다.

### Step 3 — 핵심 컴포넌트 설계

#### 한 대에 다 들어간다면 — 그냥 BFS

제약이 없다면 평범한 BFS면 끝난다.

```python
def _shortest_path(self, source, dest):
    queue = deque()
    queue.append(source)
    prev_node_keys = {source.key: None}     # 각 노드에 어디서 왔는지 기록
    source.visit_state = State.visited
    while queue:
        node = queue.popleft()
        if node is dest:
            return prev_node_keys
        for adj_node in node.adj_nodes.values():
            if adj_node.visit_state == State.unvisited:
                queue.append(adj_node)
                prev_node_keys[adj_node.key] = node.key
                adj_node.visit_state = State.visited
    return None
```

경로 자체를 얻으려면 `prev_node_keys`를 **목적지에서 거꾸로 따라가** 뒤집으면 된다.

#### 문제 — 사용자가 여러 머신에 흩어져 있다

1억 명을 한 대에 못 담으므로 **Person Server**들에 **샤딩**하고, 어느 서버에 있는지 알려 주는 **Lookup Service**를 둔다.

```text
Client → Web Server(리버스 프록시) → Search API → User Graph Service
                                                       │
                                          ┌────────────┴────────────┐
                                          ▼                         ▼
                                  ┌───────────────┐        ┌─────────────────┐
                                  │ Lookup Service│        │ Person Server 1 │
                                  │ id → 서버 위치 │        │ Person Server 2 │
                                  └───────────────┘        │ Person Server 3 │
                                                           └─────────────────┘
```

**흐름**

1. Client → Web Server → **Search API** → **User Graph Service**
2. User Graph Service가:
   - **Lookup Service**로 현재 사용자가 있는 **Person Server**를 찾는다
   - 그 서버에서 사용자의 `friend_ids` 목록을 받는다
   - 사용자를 `source`, `friend_ids`를 인접 노드로 삼아 **BFS**를 돌린다
   - **인접 노드를 실제로 가져오려면 — 매번 다시 Lookup Service에 물어봐야 한다**

**마지막 줄이 이 문제의 핵심 병목이다.** 원문도 여기에 *"potential for optimization"* 이라고 달아 두었다.

```text
BFS 한 홉마다:
  Lookup Service 호출 (이 친구는 어느 서버에?)
  → Person Server 호출 (그 친구 데이터 줘)
  → 다음 홉에서 또 반복…
```

메모리 안에서 포인터를 따라가면 **나노초** 단위인 작업이, 여기서는 **네트워크 왕복 2회**가 된다. **머신 점프(machine jump)가 비용의 전부**다.

#### 왜 이게 재앙인가 — 분기 계수

```text
친구 평균 50명 → BFS의 분기 계수(branching factor) = 50

깊이 1: 50명
깊이 2: 50² = 2,500명
깊이 3: 50³ = 125,000명
깊이 4: 50⁴ = 625만 명
깊이 5: 50⁵ = 3억 1천만 명
깊이 6: 50⁶ = 156억 명       ← 전 세계 인구보다 많다
```

**6단계 분리(six degrees of separation)** 이론대로 대부분의 사람이 6홉 안에 연결돼 있다면, 최악의 경우 **156억 번의 머신 점프**가 발생한다. 네트워크 왕복 1ms만 잡아도 계산이 안 되는 수치다.

### Step 4 — 설계 확장하기

> ⚠️ 초기 설계에서 최종 설계로 바로 점프하지 말 것. ① 벤치마크·부하 테스트 → ② 프로파일링 → ③ 대안·트레이드오프 비교 → ④ 반복 — [[2026-08-28-backend-scaling-to-millions]]

400 QPS(피크는 더 높음)를 감당하기 위해, 사람 데이터를 **Memory Cache**(Redis/Memcached)에서 서빙해 응답 시간과 하위 서비스 트래픽을 줄인다. **연속해서 여러 번 검색하는 사용자**와 **친구가 아주 많은 사람**에게 특히 효과적이다.

#### 최적화 기법들

| 기법 | 내용 |
|---|---|
| **BFS 순회 결과 캐싱** | 완료된(또는 부분) BFS 순회를 **Memory Cache**에 저장해 이후 조회를 가속 |
| **오프라인 배치 사전 계산** | 미리 순회를 계산해 **NoSQL Database**에 저장 |
| **같은 서버 친구 묶어 조회** | 같은 Person Server에 있는 친구들을 **한 번에 배치 조회**해 머신 점프를 줄인다 |
| **위치 기반 샤딩** | Person Server를 **지역별로 샤딩**한다. **친구는 대체로 가까이 산다**는 성질을 이용 → 위 배치 조회 효과가 커진다 |
| **양방향 BFS** | 출발점과 도착점에서 **동시에** BFS를 돌려 중간에서 만나면 경로를 합친다 |
| **허브부터 탐색** | **친구가 아주 많은 사람**부터 탐색한다. 분리 단계를 줄일 가능성이 높다 |
| **탐색 제한** | 시간·홉 수에 상한을 두고, 넘으면 **계속할지 사용자에게 묻는다** |
| **그래프 DB** | 제약이 없다면 **Neo4j**나 **GraphQL** 사용 |

#### 양방향 BFS의 위력 — 숫자로 보기

```text
단방향 BFS (깊이 6)        양방향 BFS (양쪽에서 깊이 3)

    ●                         ●              ●
   ╱│╲                       ╱│╲            ╱│╲
  … … …  깊이 6까지         … … …   ⟷    … … …
                            깊이 3         깊이 3
   50⁶ = 156억                 50³ + 50³ = 25만
```

| | 방문 노드 수 | 비율 |
|---|---:|---:|
| 단방향 6홉 | **156억** | 1× |
| 양방향 3홉 + 3홉 | **25만** | **약 1/62,500** |

**같은 답을 6만 배 적은 작업으로 얻는다.** 지수 함수의 지수를 절반으로 자르는 것이 얼마나 강력한지 보여주는 사례다.

## 내가 정리한 내용

### 1. 이 문제의 병목 — 다른 설계 문제와 뭐가 다른가

이전 문제들은 **어느 샤드로 갈지 미리 알 수 있었다면**, 이 문제는 **일단 가 봐야 다음에 어디로 갈지 알 수 있다.**

BFS로 인접 노드를 실제로 가져오려면 **매번 다시 Lookup Service에 물어봐야** 한다. 한 홉마다 **Lookup Service + Person Server 왕복 2회**가 발생하고, 이 **머신 점프(machine jump)가 비용의 전부**다.

### 2. 분기 계수 문제 — 숫자로 왜 심각한가

BFS의 탐색량은 **깊이에 대해 지수적**으로 늘어난다 — 분기 계수 `b`, 깊이 `d`일 때 **`O(b^d)`**.

```text
분기 계수 50 (친구 평균 50명)

깊이 3: 125,000
깊이 4: 625만
깊이 5: 3억 1천만
깊이 6: 156억      ← 전 세계 인구보다 많다
```

다만 `visited` 집합이 재방문을 막으므로 실제 상한은 **`O(V+E)` = 노드 1억 + 간선 50억**이다.

**진짜 재앙은 이 숫자에 네트워크 왕복이 곱해진다는 것.** 메모리에서 포인터를 따라가면 나노초인 작업이 여기서는 왕복 2회다.

### 3. 최적화 기법 — 성격별 묶음

**총 비용 = 홉 개수 × 홉당 비용**으로 놓고 보면 이렇게 갈린다.

| 성격 | 기법 | 무엇을 하나 |
|---|---|---|
| **미리 계산해 두기** | BFS 순회 캐싱<br>오프라인 배치 사전 계산 | **탐색 시점을 앞당긴다** — 요청 때 계산하지 않는다 |
| **머신 점프 줄이기** | 같은 서버 친구 묶어 조회<br>위치 기반 샤딩 | **홉당 비용을 낮춘다** — 왕복 횟수 감소 |
| **탐색량 줄이기** | 양방향 BFS<br>허브부터 탐색 | **홉의 개수를 줄인다** — 알고리즘 개선 |
| **문제 범위 줄이기** | 탐색 제한 | **답을 포기할 수 있게 한다** — 제품 결정 |

### 4. 양방향 BFS

- **이득**: 같은 답을 단방향보다 매우 적은 작업으로 얻는다.

| | 방문 노드 수 |
|---|---:|
| 단방향 6홉 | **156억** |
| 양방향 3+3홉 | **25만** |
| 비율 | **약 1/62,500** |

- **성립 조건**: 도착점에서도 뻗으려면 **"이 사람을 친구로 둔 사람"** 을 알아야 한다. 친구 관계는 **무방향(대칭)** 이라 같은 `friend_ids`를 그대로 쓸 수 있다. 팔로우처럼 방향이 있는 관계였다면 **역방향 인덱스를 따로 저장**해야 했다.
- **만남 판정**: 양쪽이 각자 `visited` 집합을 유지하고, 새 노드를 방문할 때마다 **상대편 집합에 있는지 확인**한다. 발견하면 양쪽 `prev` 맵을 그 노드에서 이어 붙이고 한쪽을 뒤집는다.
- **대가**: 자료구조 2배, 매 노드마다 교차 확인, **분산 환경에서의 조율**, 확장 순서 결정(보통 프런티어가 작은 쪽을 먼저 확장).

## 검토 결과

### 확인된 부분

- **이 문제의 핵심 차이**를 정확히 짚었다 — **"미리 알 수 있다 vs 가 봐야 안다"**. 이 한 줄이 왜 기존 샤딩 전략이 안 통하는지를 설명한다.
- **양방향 BFS의 이득과 네 가지 비용**을 모두 정리했다.
- **위치 기반 샤딩의 근거**("친구는 대체로 가까이 산다")를 정확히 짚었다.

### 보강 포인트

#### ① `O(n²)`가 아니라 `O(b^d)` — 제곱이 아니라 지수다

| | 내용 |
|---|---|
| **전** | 최악의 경우 **`O(n²)`** 이다 |
| **후** | 탐색량은 **깊이에 대해 지수적**이다 — **`O(b^d)`**, 여기서는 `50⁶ = 156억`. `visited` 집합 덕에 실제 상한은 **`O(V+E)`** |

```text
n = 100 으로 비교하면
제곱   n² = 10,000
지수   2ⁿ = 1,267,650,600,228,229,401,496,703,205,376
```

**둘의 차이는 결정적이다.** 제곱은 감당할 수 있지만 지수는 못 한다.

그리고 **Lookup Service 왕복은 Q1의 병목(홉당 비용)이고, 분기 계수는 Q2의 문제(홉 개수)** 다. **둘이 곱해져야** 재앙의 크기가 나온다.

```text
156억 번 × 네트워크 왕복 → 계산 자체가 무의미한 수치
```

#### ② 최적화 기법을 나열만 하고 묶지 않았다

일곱 개를 빠짐없이 적었지만 **성격별 분류**가 없었다. 교정 후 내용은 위 `내가 정리한 내용` 3번에 반영.

**이 묶음이 중요한 이유**: 면접에서 일곱 개를 순서대로 읊으면 암기처럼 들린다. **"비용 = 홉 개수 × 홉당 비용"** 이라는 식을 먼저 세우고 **"첫 항을 줄이는 법 / 둘째 항을 줄이는 법 / 아예 계산을 피하는 법"** 으로 나누면 **구조를 이해했다는 신호**가 된다.

```text
총 비용 = 홉 개수 × 홉당 비용
           ↑          ↑
      양방향 BFS   배치 조회
      허브 탐색    위치 샤딩

그 바깥:  미리 계산해 두기 (요청 시점에 아예 안 함)
          탐색 제한 (최악의 경우를 포기)
```

#### ③ 양방향 BFS의 성립 조건과 만남 판정이 빠졌다

교정 후 내용은 위 `내가 정리한 내용` 4번에 반영. **"친구 관계가 대칭이라서 공짜로 되는 것"** 이라는 조건을 짚어야, "팔로우 그래프에서도 되나요?"라는 꼬리 질문에 답할 수 있다.

### 심화: 위치 기반 샤딩과 배치 조회는 상하 관계다

**위치 기반 샤딩은 혼자서는 아무것도 하지 않는다.**

| 기법 | 역할 |
|---|---|
| **같은 서버 친구 묶어 조회** | **메커니즘** — 여러 친구를 한 번의 호출로 가져온다 |
| **위치 기반 샤딩** | **그 메커니즘이 잘 먹히도록 데이터를 재배치** |

배치 조회 기능만 만들어 놓고 친구들이 서버 100대에 흩어져 있으면 **묶을 게 없다.** 친구 50명이 50대에 하나씩 있으면 배치 조회를 해도 왕복 50회다.

```text
무작위 샤딩                        위치 기반 샤딩
친구 50명 → 서버 50대에 분산       친구 50명 → 서버 3~4대에 몰림
배치 조회해도 왕복 50회            배치 조회로 왕복 3~4회
                                    ↑ 10배 이상 절감
```

**하나는 "어떻게 가져올까", 다른 하나는 "어디에 둘까"에 답한다.**

이것은 [[2026-08-31-backend-design-mint]]에서 샤드 키를 `user_id`로 잡은 것과 같은 사고다 — **조회 패턴에 맞춰 데이터를 배치하면 조회 1건이 닿는 샤드 수가 준다.** 거기서는 1개로 줄였고, 여기서는 50개를 3~4개로 줄인다.

### 심화: 양방향 BFS의 만남 판정과 경로 재구성

```text
출발점 쪽 visited : {나, 친구A, 친구B, 친구C, …}
도착점 쪽 visited : {타깃, 친구X, 친구Y, 친구C, …}
                                        ↑
                          C가 양쪽에 다 있다 → 여기서 만났다!
```

**경로 재구성**

```text
출발점 쪽 prev 맵으로  나 → … → C     경로를 얻고
도착점 쪽 prev 맵으로  타깃 → … → C   경로를 얻어 뒤집어서
두 개를 C에서 이어 붙인다
```

분산 환경에서 가장 아픈 비용은 **두 탐색이 다른 서버에서 돌 때 상태를 공유해야 한다**는 점이다. `visited` 집합 교차 확인이 네트워크를 타면 그 자체가 병목이 될 수 있다.

### 심화: "탐색 제한"은 최적화가 아니라 제품 결정이다

나머지 기법은 전부 **"같은 답을 더 빨리"** 를 목표로 한다. 탐색 제한은 다르다 — **"답을 못 찾을 수도 있다는 걸 인정하고 그 상황을 어떻게 다룰 것인가"** 에 대한 답이다.

**왜 필요한가?**

```text
두 사람이 아예 연결돼 있지 않다면?
→ BFS는 "없다"고 확신하려면 연결된 노드를 전부 훑어야 한다
→ 어떤 최적화로도 못 줄인다. 없다는 걸 증명하려면 다 봐야 하니까
```

양방향 BFS도, 캐싱도, 위치 샤딩도 이 경우엔 도움이 안 된다. **알고리즘으로 풀 수 없는 문제다.**

| | 나머지 최적화 | 탐색 제한 |
|---|---|---|
| 다루는 것 | 평균 경우 | **최악의 경우** |
| 방법 | 알고리즘·인프라 | **제품 결정** |
| 사용자에게 | 투명 (모름) | **통제권을 넘김** |
| 보장 | 같은 답, 더 빨리 | **답을 포기할 수 있음** |

**"모든 요청에 답한다"가 항상 요구사항인 건 아니다.** 최악의 경우를 감당하려고 시스템 전체를 과하게 키우는 대신, **우아하게 물러나는(graceful degradation)** 선택지가 있다.

### 이전 학습과의 연결

- [[2026-08-31-backend-design-mint]] — **조회 패턴에 맞춰 데이터를 배치한다**는 샤딩 사고가 동일하다. 거기서는 `user_id` 샤드 키로 조회 1건이 1개 샤드에 닿게 했고, 여기서는 위치 기반 샤딩으로 친구 50명이 3~4대에 모이게 한다.
- [[2026-09-01-backend-query-cache]] — 여기서도 **Memory Cache**가 앞단에 붙는다. 특히 "연속해서 여러 번 검색하는 사용자"와 "친구가 아주 많은 사람"에 효과적이라는 점이 인기 쿼리 캐싱과 같은 논리다.
- [[2026-08-21-backend-design-twitter]] — 같은 소셜 도메인이지만 **다루는 관계가 다르다.** 트위터는 팔로우(방향 있음) 기반 팬아웃, 여기는 친구(대칭) 기반 경로 탐색. 그래서 양방향 BFS가 여기서는 공짜지만 트위터 그래프에서는 역방향 인덱스가 필요하다.
- [[2026-08-19-backend-latency-numbers]] — `1개월 ≈ 250만 초`로 400 QPS를 도출. 메모리 접근과 네트워크 왕복의 자릿수 차이가 이 문제의 병목을 설명한다.
- [[2026-08-28-backend-scaling-to-millions]] — 벤치마크 → 프로파일링 → 병목 해소 → 반복 절차를 그대로 따랐다.
- [[2026-08-27-backend-design-web-crawler]] — 크롤러도 BFS로 링크를 훑고 `visited` 집합으로 중복을 막는다. **그래프 순회**라는 뼈대가 같다.
