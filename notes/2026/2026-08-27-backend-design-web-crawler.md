## 핵심 개념

### Step 1. 사용 사례와 제약

**범위에 포함**
- 서비스가 **URL 목록을 크롤링**한다
  - 검색어를 포함한 페이지로의 **역색인(reverse index)** 생성
  - 페이지의 **제목과 스니펫** 생성 (검색어에 따라 바뀌지 않는 **정적** 값)
- 사용자가 검색어를 입력하면 **제목과 스니펫이 붙은 관련 페이지 목록**을 본다
- 서비스는 **고가용성**을 갖는다

**범위 밖**: 검색 분석, 개인화 검색 결과, 페이지랭크

**가정**
- 트래픽은 고르게 분포하지 않는다 — **어떤 검색은 매우 인기 있고, 어떤 것은 딱 한 번 실행된다**
- 익명 사용자만 지원
- 검색 결과 생성은 빨라야 한다
- ⚠️ **웹 크롤러가 무한 루프에 빠지면 안 된다** — **그래프에 사이클이 있으면** 무한 루프에 빠진다
- **크롤링할 링크 10억 개**
  - 신선도를 위해 **정기적으로 재크롤링**해야 한다
  - 평균 **주 1회 갱신**, 인기 사이트는 더 자주 → **월 40억 링크 크롤링**
  - 페이지당 평균 저장 크기 **500 KB**
- **월 1,000억 검색**

> 원문 지시: **solr나 nutch 같은 기존 시스템을 쓰지 말고** 전통적인 시스템으로 직접 설계할 것.

### 어림 계산

```text
월 저장 페이지 콘텐츠  2 PB    (500KB × 40억)
3년이면              72 PB

초당 쓰기 요청       1,600건
초당 검색 요청      40,000건
```

### Step 3. 핵심 컴포넌트

#### 사용 사례 ①: URL 목록 크롤링

**두 개의 테이블**을 쓴다.

| 테이블 | 용도 |
|---|---|
| `links_to_crawl` | 크롤링할 링크. **사이트 인기도 기준으로 순위**가 매겨져 있다 |
| `crawled_links` | 처리된 링크와 그 **페이지 서명(signature)** |

- 둘 다 **키-값 NoSQL 데이터베이스**에 저장할 수 있다.
- `links_to_crawl`의 순위 매겨진 링크는 **Redis의 정렬 집합(sorted set)** 으로 관리할 수 있다. → [[2026-08-09-backend-nosql-types]]
- 초기 목록이 없다면 **Yahoo, DMOZ처럼 외부 콘텐츠로 링크가 많은 인기 사이트**를 시드로 삼는다.

**Crawler Service의 루프**

```text
① 가장 높은 순위의 링크를 꺼낸다
② crawled_links에서 비슷한 페이지 서명이 있는지 확인
   - 비슷한 페이지가 있으면 → 링크의 우선순위를 낮춘다
       → 이것이 사이클(무한 루프)을 방지한다
       → 다음으로 continue
   - 없으면 → 링크를 크롤링한다
       - Reverse Index Service 큐에 역색인 생성 작업 추가
       - Document Service 큐에 제목·스니펫 생성 작업 추가
       - 페이지 서명 생성
       - links_to_crawl에서 링크 제거
       - crawled_links에 링크와 서명 삽입
```

> **핵심: 이미 본 것과 "비슷한" 페이지면 우선순위를 낮춘다.** 이것이 무한 루프 방지 장치다.

#### 중복 제거

**URL 중복 제거**
- 작은 목록이면 `sort | unique`
- **10억 링크면 MapReduce**로 **빈도가 1인 항목만** 출력한다

```python
class RemoveDuplicateUrls(MRJob):
    def mapper(self, _, line):
        yield line, 1

    def reducer(self, key, values):
        total = sum(values)
        if total == 1:
            yield key, total
```

**중복 콘텐츠 탐지는 더 복잡하다**
- **페이지 내용을 기반으로 서명을 생성**하고 두 서명의 **유사도를 비교**한다.
- 가능한 알고리즘: **자카드 지수(Jaccard index)**, **코사인 유사도(cosine similarity)** → [[2026-08-03-ai-data-embeddings]]

#### 크롤 결과를 언제 갱신하나

- 신선도를 위해 정기적으로 크롤링해야 한다. 크롤 결과에 **`timestamp` 필드**를 두어 마지막 크롤 시각을 기록한다.
- **기본 기간(예: 1주)** 이 지나면 모든 페이지를 갱신한다. **자주 갱신되거나 인기 있는 사이트는 더 짧은 주기**로.
- 데이터 마이닝으로 **특정 페이지가 갱신되기까지의 평균 시간**을 구해, 그 통계로 재크롤 주기를 정할 수도 있다.
- **`Robots.txt`를 지원**해 웹마스터가 크롤 빈도를 통제하게 할 수도 있다.

#### 사용 사례 ②: 검색

```text
클라이언트 → 웹 서버(리버스 프록시) → Query API
  ① 쿼리 파싱
     - 마크업 제거 / 텍스트를 용어로 분해 / 오타 수정
     - 대소문자 정규화 / 불리언 연산으로 변환
  ② Reverse Index Service로 매칭 문서를 찾고 랭킹해 상위 결과 반환
  ③ Document Service로 제목과 스니펫을 반환
```

**공개 API는 REST, 내부 통신은 RPC.** → [[2026-08-14-backend-rpc-rest]]

### Step 4. 규모 확장

> ⚠️ **초기 설계에서 최종 설계로 바로 뛰어들지 말 것.**

- **인기 쿼리는 메모리 캐시(Redis/Memcached)로 서빙**해 응답 시간을 줄이고 Reverse Index Service와 Document Service의 과부하를 막는다. **고르지 않은 트래픽과 스파이크 처리**에도 유용하다.
  - 원문 인용: 메모리에서 1MB 순차 읽기 250us, SSD는 4배, 디스크는 80배 → [[2026-08-19-backend-latency-numbers]]
- **Reverse Index Service와 Document Service는 샤딩과 페더레이션을 많이 쓰게 될 것**이다. → [[2026-08-05-backend-federation-sharding]]
- ⭐ **DNS 조회가 병목이 될 수 있다.** Crawler Service가 **자체 DNS 조회 캐시를 두고 주기적으로 갱신**할 수 있다. → [[2026-07-28-backend-domain-name-system]]
- **커넥션 풀링** — 많은 연결을 열어두면 성능이 개선되고 메모리 사용이 줄어든다. **UDP로 전환하면 성능이 더 오를 수 있다.** → [[2026-08-13-backend-http-tcp-udp]]
- **웹 크롤링은 대역폭 집약적**이므로 높은 처리량을 지탱할 **충분한 대역폭**을 확보해야 한다.

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

**Step 1**: 서비스가 URL 목록을 크롤링해 **역색인**과 **정적 제목·스니펫**을 생성하고, 사용자가 검색어로 관련 페이지 목록을 본다. **크롤링할 링크 10억 개**, 신선도를 위해 **평균 주 1회 재크롤링**(월 40억 링크), 페이지당 **500KB**, **월 1,000억 검색**을 가정한다. ⚠️ **그래프에 사이클이 있으면 무한 루프에 빠지므로 이를 막아야 한다.** 월 **2PB**, 3년 **72PB** 저장, **초당 쓰기 1,600건 / 검색 4만 건**이다.

**Step 3**: `links_to_crawl`(인기도로 순위)과 `crawled_links`(처리된 링크와 페이지 서명) 두 테이블을 **키-값 NoSQL**에 둔다. 순위 링크는 **Redis 정렬 집합**으로 관리할 수 있다.

Crawler Service는 루프에서 **최상위 링크를 꺼내 `crawled_links`에 비슷한 서명이 있는지 확인**한다. **비슷한 페이지가 있으면 우선순위를 낮춰 사이클을 방지**하고, 없으면 크롤링해 **역색인 생성 작업과 제목·스니펫 생성 작업을 각각 큐에 넣고**, 서명을 생성해 `crawled_links`에 삽입한다.

**URL 중복 제거**는 작은 목록이면 `sort | unique`, 10억 링크면 **MapReduce로 빈도가 1인 항목만** 출력한다. **중복 콘텐츠 탐지는 더 복잡해**, 페이지 내용 기반 서명을 만들고 **자카드 지수나 코사인 유사도**로 비교한다.

**갱신 시점**은 `timestamp` 필드로 관리하며 기본 1주, 인기 사이트는 더 짧게 한다. 데이터 마이닝으로 페이지별 평균 갱신 주기를 구해 활용할 수 있고, **`Robots.txt`** 로 웹마스터가 빈도를 통제하게 할 수도 있다.

**검색**은 쿼리를 파싱·토큰화한 뒤 **Reverse Index Service**로 매칭·랭킹하고 **Document Service**로 제목과 스니펫을 반환한다.

**Step 4**: **인기 쿼리는 메모리 캐시로 서빙**해 응답 시간을 줄이고 과부하를 막는다. Reverse Index Service와 Document Service는 **샤딩과 페더레이션**이 많이 필요하다. **DNS 조회가 병목이 될 수 있어 Crawler Service가 자체 DNS 캐시**를 둘 수 있고, **커넥션 풀링**과 **UDP 전환**으로 성능을 높일 수 있다. 크롤링은 **대역폭 집약적**이라 충분한 대역폭이 필요하다.

## 내가 정리한 내용

**1. 무한 루프 문제와 해법**

웹은 **그래프 구조**라 `A→B→C→A` 같은 **순환이 흔하다.** 그냥 링크를 따라가면 무한 루프에 빠진다.

**해법**: 크롤링 전에 `crawled_links`에서 **비슷한 페이지 서명이 있는지 확인**한다. 비슷하면 **우선순위를 낮추고 넘어가고**, 아니면 크롤링을 진행한다.

URL이 아니라 **내용(서명)으로 판단**하는 이유는, URL이 달라도 내용이 같은 경우가 많고, 특히 달력 페이지처럼 **URL이 무한히 생성되는 크롤러 트랩**은 URL 기반으로 막을 수 없기 때문이다.

**2. 중복 제거 — 두 층위**

- **URL 중복**: URL을 기반으로 제거한다. 작은 목록이면 `sort | unique`, **10억 개 규모면 MapReduce로 빈도가 1인 항목만** 출력한다.
- **콘텐츠 중복**: 더 복잡하다. **페이지 내용 기반 서명**을 만들고 **유사도를 비교**한다. **자카드 지수(Jaccard index)** 나 **코사인 유사도**를 쓴다.

**3. 크롤러 특유의 최적화 포인트**

- ⭐ **DNS 조회 병목** — 크롤러는 매번 다른 도메인에 접속해 **DNS 캐시 적중률이 낮다.** Crawler Service가 **자체 DNS 캐시**를 두고 주기적으로 갱신한다.
- **커넥션 풀링** — 많은 연결을 열어두어 성능을 높이고 메모리 사용을 줄인다. **UDP 전환**도 성능 향상 수단이다.
- **인기 쿼리는 메모리 캐시**로 서빙해 Reverse Index/Document Service 과부하를 막는다.
- **Reverse Index Service와 Document Service는 샤딩·페더레이션**이 많이 필요하다.
- **웹 크롤링은 대역폭 집약적**이므로 충분한 대역폭을 확보해야 한다.

## 검토 결과

### 확인된 부분

- **무한 루프의 원인(그래프의 순환)과 해법(서명 기반 우선순위 하향)을 정확히 서술.**
- **중복 제거를 URL / 콘텐츠 두 층위로 정확히 구분.**
- 실습 Q2에서 DNS 병목의 이유(매번 다른 도메인 → 왕복 비용 누적)를 정확히 파악.

### 보강 포인트

- **Q3 초기 답변에서 DNS 최적화가 누락 → 추가.** 크롤러 **특유의** 최적화라 이것이 오히려 핵심이다. 일반 웹 서비스에서는 안 보이던 병목이 크롤러에서는 1순위가 된다.
- **중복 제거에 규모별 방법**을 명시할 것. `sort | unique` vs **MapReduce**, 그리고 유사도 알고리즘 이름(**자카드 지수, 코사인 유사도**).

### 심화: URL로는 절대 못 막는 함정 — 크롤러 트랩 (Q1)

**같은 페이지의 다른 URL** (흔한 수준)

```text
example.com/page
example.com/page?utm_source=twitter
example.com/page#section
www.example.com/page
```

**진짜 함정 — 무한히 생성되는 URL** ⚠️

```text
site.com/calendar?month=2026-01
site.com/calendar?month=2026-02
site.com/calendar?month=2026-03
...
site.com/calendar?month=9999-12   ← 끝이 없다
```

**달력 페이지**가 대표적이다. "다음 달" 링크를 계속 따라가면 **URL이 무한히 생성**된다.

> **URL은 전부 다르다.** 그래서 *"이미 본 URL인가?"* 로는 **절대 못 막는다.** 영원히 새 URL이기 때문.

**내용으로 보면 잡힌다** — 2087년 3월 달력이나 2088년 3월 달력이나 **서명이 비슷**하므로 우선순위가 낮아져 자연히 밀려난다.

이를 **크롤러 트랩(crawler trap)** 이라 한다. 세션 ID가 URL에 붙는 사이트도 같은 문제를 일으킨다.

### 심화: DNS가 크롤러에서만 병목인 이유 (Q2)

핵심은 **캐시 적중률**이다.

| | 접속 도메인 | DNS 캐시 적중률 |
|---|---|---|
| **일반 웹 서비스** | **소수**를 반복 (`api.myservice.com` 등) | **거의 100%** |
| **크롤러** | **매번 새 도메인** | **거의 0%** |

**일반 서비스는 DNS를 사실상 안 쓴다.** OS와 브라우저 캐시가 다 흡수한다(TTL 덕). → [[2026-07-28-backend-domain-name-system]]

**크롤러는 반대다.** 10억 개 링크가 수백만 도메인에 흩어져 있어 **캐시가 도움이 안 된다.**

```text
크롤링 1건 = DNS 조회 1회 + HTTP 요청 1회
             ↑ 이것이 절반을 차지할 수도
```

**그래서 자체 DNS 캐시를 둔다** — 캐시 원리를 **크롤러 내부에** 적용하는 것. → [[2026-08-11-backend-cache]]

> **같은 구성요소(DNS)가 시스템 성격에 따라 병목이 되기도, 안 되기도 한다.** 그래서 *"프로파일링이 먼저"* 다. → [[2026-08-06-backend-sql-tuning-nosql]]

### 크롤러 루프 상세

```text
① 가장 높은 순위의 링크를 꺼낸다
② crawled_links에서 비슷한 페이지 서명이 있는지 확인
   - 있으면 → 우선순위를 낮추고 continue   ← 사이클 방지
   - 없으면 → 크롤링
       - Reverse Index Service 큐에 역색인 생성 작업 추가
       - Document Service 큐에 제목·스니펫 생성 작업 추가
       - 페이지 서명 생성
       - links_to_crawl에서 제거 / crawled_links에 삽입
```

**두 테이블**

| 테이블 | 내용 | 저장소 |
|---|---|---|
| `links_to_crawl` | 크롤링할 링크 (**인기도 순위**) | **Redis 정렬 집합** |
| `crawled_links` | 처리된 링크 + **페이지 서명** | 키-값 NoSQL |

→ [[2026-08-09-backend-nosql-types]]

### 신선도 관리

- `timestamp` 필드로 마지막 크롤 시각 기록. **기본 1주**, 인기 사이트는 더 자주.
- **데이터 마이닝으로 페이지별 평균 갱신 주기**를 구해 적응적으로 재크롤할 수 있다.
- **`Robots.txt`** 를 지원해 웹마스터가 크롤 빈도를 통제하게 할 수 있다.

### 세 실전 문제 비교 — 유형이 다르다

| | Pastebin | Twitter | **Web Crawler** |
|---|---|---|---|
| 규모(3년) | 450 GB | 5.4 PB | **72 PB** |
| 고유 문제 | — | **팬아웃** | **무한 루프, 중복** |
| 병목 | DB 쓰기 | 팬아웃 서비스 | **DNS, 대역폭** |
| 핵심 자료구조 | 해시 테이블 | 타임라인 리스트 | **그래프 + 서명** |

> **같은 4단계 절차를 쓰지만, 문제의 성격이 다르면 병목도 해법도 달라진다.** → [[2026-08-20-backend-design-pastebin]], [[2026-08-21-backend-design-twitter]]
