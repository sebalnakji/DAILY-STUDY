# NoSQL의 네 가지 종류와 각각의 용도

## 질문

> **NoSQL에는 어떤 종류가 있고, 각각 어떤 추상화와 용도를 갖는가?**
>
> 원문: *Key-value store / Document store / Wide column store / Graph database*

## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

### ① 키-값 저장소 (Key-Value Store)

> **추상화: 해시 테이블**

- 일반적으로 **O(1) 읽기·쓰기**를 제공하며, 보통 **메모리나 SSD**에 저장된다.
- 키를 **사전순(lexicographic order)** 으로 유지할 수 있어 **키 범위 조회**가 효율적이다.
- 값과 함께 **메타데이터**를 저장할 수 있다.
- **고성능**을 제공하며, **단순한 데이터 모델**이나 **빠르게 변하는 데이터**(예: 인메모리 캐시 계층)에 자주 쓰인다.
- ⚠️ **제공하는 연산이 제한적**이라, 추가 연산이 필요하면 **복잡도가 애플리케이션 계층으로 넘어간다.**
- **문서 저장소나 일부 그래프 DB의 기반**이 되는 가장 기본적인 형태다.
- 예: Redis, Memcached

### ② 문서 저장소 (Document Store)

> **추상화: 값으로 문서를 저장하는 키-값 저장소**

- **문서(XML, JSON, 바이너리 등)** 를 중심으로 하며, 하나의 문서가 **한 객체의 모든 정보**를 담는다.
- **문서 내부 구조를 기준으로 질의**할 수 있는 API나 질의 언어를 제공한다.
- 문서는 컬렉션, 태그, 메타데이터, 디렉터리로 조직된다. 다만 **문서마다 필드가 완전히 다를 수 있다.** (스키마 유연성)
- MongoDB, CouchDB는 복잡한 질의를 위한 **SQL 유사 언어**도 제공한다. DynamoDB는 **키-값과 문서를 모두** 지원한다.
- **높은 유연성**을 제공하며, **가끔 변하는 데이터**에 자주 쓰인다.
- 참고: 많은 키-값 저장소가 값의 메타데이터를 다루는 기능을 포함해, **두 유형의 경계가 흐릿하다.**

### ③ 와이드 컬럼 저장소 (Wide Column Store)

> **추상화: 중첩 맵** `ColumnFamily<RowKey, Columns<ColKey, Value, Timestamp>>`

- 기본 데이터 단위는 **컬럼(이름/값 쌍)** 이다.
- 컬럼은 **컬럼 패밀리**(SQL 테이블에 해당)로 묶이고, **슈퍼 컬럼 패밀리**가 컬럼 패밀리를 더 묶는다.
- **행 키(row key)로 각 컬럼에 독립적으로 접근**할 수 있고, 같은 행 키를 가진 컬럼들이 하나의 행을 이룬다.
- 각 값은 **타임스탬프**를 포함해 **버저닝과 충돌 해결**에 사용된다.
- 구글이 **Bigtable**로 처음 소개했고, 이것이 하둡 생태계의 **HBase**와 페이스북의 **Cassandra**에 영향을 주었다.
- Bigtable, HBase, Cassandra는 **키를 사전순으로 유지**해 선택적 키 범위 조회가 효율적이다.
- **높은 가용성과 높은 확장성**을 제공하며, **매우 큰 데이터셋**에 자주 쓰인다.

### ④ 그래프 데이터베이스 (Graph Database)

> **추상화: 그래프**

- **각 노드가 레코드**이고 **각 간선(arc)이 두 노드 사이의 관계**다.
- **외래 키가 많거나 다대다(many-to-many) 관계가 많은** 복잡한 관계를 표현하는 데 최적화되어 있다.
- **소셜 네트워크**처럼 관계가 복잡한 데이터 모델에서 고성능을 낸다.
- ⚠️ **비교적 새로운 기술이라 아직 널리 쓰이지 않는다.** 개발 도구와 자료를 찾기 어려울 수 있으며, 많은 그래프 DB는 **REST API로만 접근**할 수 있다.
- 예: Neo4j, FlockDB

### 한 장 비교

| | 추상화 | 강점 | 대표 용도 | 예시 |
|---|---|---|---|---|
| **키-값** | 해시 테이블 | **O(1) 성능** | 캐시, 빠르게 변하는 단순 데이터 | Redis, Memcached |
| **문서** | 값이 문서인 키-값 | **유연성** | 가끔 변하는 데이터, 객체 저장 | MongoDB, CouchDB |
| **와이드 컬럼** | 중첩 맵 | **가용성·확장성** | 매우 큰 데이터셋 | Bigtable, HBase, Cassandra |
| **그래프** | 그래프 | **복잡한 관계** | 소셜 네트워크 | Neo4j, FlockDB |

> **키-값이 가장 단순한 기반이고, 문서 저장소는 그 위에 얹힌 형태다.** 뒤로 갈수록 표현력이 커지는 대신 단순함을 잃는다.

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

**키-값 저장소**는 **해시 테이블**을 추상화한 것이다. 일반적으로 O(1) 읽기·쓰기를 제공하며 보통 메모리나 SSD를 기반으로 한다. 데이터 저장소가 키를 사전순으로 유지하면 키 범위를 효율적으로 조회할 수 있고, 값과 함께 메타데이터를 저장할 수 있다. 고성능을 제공하며 단순한 데이터 모델이나 인메모리 캐시 계층처럼 빠르게 변하는 데이터에 자주 쓰인다. **제한된 연산만 제공하므로 추가 연산이 필요하면 복잡도가 애플리케이션 계층으로 넘어간다.** 키-값 저장소는 문서 저장소와 일부 그래프 DB 같은 더 복잡한 시스템의 기반이 된다.

**문서 저장소**는 **값으로 문서를 저장하는 키-값 저장소**를 추상화한 것이다. XML, JSON, 바이너리 같은 문서를 중심으로 하며, 하나의 문서가 주어진 객체의 모든 정보를 담는다. 문서 내부 구조를 기준으로 질의할 수 있는 API나 질의 언어를 제공한다. 문서는 컬렉션·태그·메타데이터·디렉터리로 조직되지만, 문서마다 필드가 완전히 다를 수 있다. MongoDB와 CouchDB는 SQL 유사 언어도 제공하고, DynamoDB는 키-값과 문서를 모두 지원한다. **높은 유연성**을 제공하며 가끔 변하는 데이터에 자주 쓰인다.

**와이드 컬럼 저장소**의 기본 데이터 단위는 **컬럼(이름/값 쌍)** 이다. 컬럼은 SQL 테이블에 해당하는 컬럼 패밀리로 묶이고, 슈퍼 컬럼 패밀리가 이를 더 묶는다. 행 키로 각 컬럼에 독립적으로 접근할 수 있으며 같은 행 키의 컬럼들이 행을 이룬다. **각 값은 버저닝과 충돌 해결을 위한 타임스탬프**를 포함한다. 구글의 Bigtable이 최초이며 HBase와 Cassandra에 영향을 주었다. **높은 가용성과 확장성**을 제공하며 매우 큰 데이터셋에 쓰인다.

**그래프 데이터베이스**는 **각 노드가 레코드이고 각 간선이 두 노드 사이의 관계**다. 외래 키가 많거나 다대다 관계가 많은 복잡한 관계를 표현하는 데 최적화되어 있다. 소셜 네트워크처럼 관계가 복잡한 데이터 모델에서 고성능을 낸다. 다만 **비교적 새로워 아직 널리 쓰이지 않으며**, 개발 도구와 자료를 찾기 어렵고 많은 그래프 DB가 REST API로만 접근 가능하다.

## 내가 정리한 내용

**1. NoSQL 4종**

- **키-값** (추상화: **해시 테이블**) — 가장 단순하고 **O(1)로 가장 빠르다.** 캐시 계층이나 빠르게 변하는 단순 데이터에 쓴다. 단, **제공하는 연산이 제한적**이라 더 필요하면 복잡도가 애플리케이션으로 넘어간다. (Redis, Memcached)
- **문서** (추상화: **값이 문서인 키-값**) — **문서 내부 구조를 기준으로 질의**할 수 있고, **문서마다 필드가 달라도 되는** 스키마 유연성을 갖는다. 가끔 변하는 데이터에 적합. (MongoDB, CouchDB)
- **와이드 컬럼** (추상화: **중첩 맵**) — 기본 단위가 컬럼이며 컬럼 패밀리로 묶인다. **각 값에 타임스탬프**가 있어 버저닝·충돌 해결에 쓰인다. **높은 가용성과 확장성**을 제공해 매우 큰 데이터셋에 쓴다. (Bigtable, HBase, Cassandra)
- **그래프** (추상화: **그래프**) — 노드가 레코드, 간선이 관계다. **외래 키가 많거나 다대다 관계가 많은 복잡한 관계**에서 고성능. 다만 **비교적 새로워 생태계가 약하고** 자료·도구를 찾기 어렵다. (Neo4j)

**2. 키-값 저장소의 강점과 대가**

- **강점**: 가장 단순하고 **O(1) 읽기·쓰기로 가장 빠르다.** 메모리·SSD 기반이며 키를 사전순으로 유지하면 범위 조회도 가능하다.
- **대가**: **제공하는 연산이 제한적**이다. key로 넣고 key로 꺼내는 것 외의 기능(집계, 정렬, 조건 검색)이 필요하면 **복잡도가 애플리케이션 계층으로 넘어간다.**

**3. 그래프 DB가 필요한 상황**

**외래 키가 많거나 다대다 관계가 많은 복잡한 관계**를 다룰 때. 소셜 네트워크의 "몇 다리 건너 아는 사이" 같은 탐색이 대표적이다.

관계형 DB로는 **다리 수만큼 JOIN이 필요하고 결과가 곱셈으로 폭발**하며, 깊이를 미리 모르면 쿼리를 작성하기도 어렵다. 그래프 DB는 **간선을 따라가기만** 하면 되므로 전체 데이터 크기와 무관하게 탐색할 수 있다.

## 검토 결과

### 확인된 부분

- **4종을 추상화 + 강점 + 대가 구조로 일관되게 정리함.** 각 유형의 정체성을 "추상화" 한 줄로 잡은 것이 좋다.
- 키-값의 대가(연산 제한 → 앱으로 복잡도 이전)를 정확히 파악.
- 실습 Q2(그래프)에서 조인 횟수 문제를 정확히 지목.

### 보강 포인트

- **문서 저장소의 결정적 차이는 "내부 구조로 질의 가능"이다.** 스키마 유연성만으로는 키-값과 구분이 약하다.
  ```text
  키-값:  user:123 → (불투명한 덩어리)         안을 못 봄
  문서:   user:123 → {age: 30, city: "서울"}   age > 30 검색 가능 ✅
  ```
  원문도 많은 키-값 저장소가 메타데이터 기능을 갖춰 **두 유형의 경계가 흐릿하다**고 언급한다.
- **와이드 컬럼의 타임스탬프**를 명시할 것. 각 값이 타임스탬프를 가져 **버저닝과 충돌 해결**에 쓰인다. → BASE의 최종 일관성이 실제로 구현되는 방식. [[2026-08-06-backend-sql-tuning-nosql]]
- **그래프 DB의 단점은 "정보를 찾기 어렵다"보다 "생태계가 아직 약하다"** 가 정확하다. 비교적 새로운 기술이라 개발 도구·자료가 부족하고, 많은 그래프 DB가 REST API로만 접근 가능하다.

### ⚠️ 교정: "유연성"의 의미 (Q1 실습)

조회수 집계에 **문서 저장소**를 고르고 근거를 *"상품이 추가·삭제될 수 있어 유연성이 중요"* 로 들었으나, **유연성의 의미가 다르다.**

| | 뜻 |
|---|---|
| ❌ 오해 | 데이터(레코드)를 추가·삭제할 수 있음 |
| ⭕ 실제 | **문서마다 필드 구조가 달라도 됨** (스키마 유연성) |

**레코드 추가·삭제는 모든 DB가 한다.** 문서 저장소의 유연성은 이런 것:

```json
{ "id": 1, "name": "노트북", "cpu": "i7", "ram": "16GB" }
{ "id": 2, "name": "티셔츠", "size": "L", "color": "블랙" }
     // 같은 컬렉션인데 필드가 완전히 다름
```

**조회수 집계의 정답은 키-값 저장소다.**

```text
데이터 모델:  product:123 → 8,472        ← 이보다 단순할 수 없음
쓰기 패턴:    조회 한 번마다 +1          ← 폭발적으로 많음
필요한 것:    O(1) 쓰기                  ← 키-값의 정확한 강점
```

조회수는 **숫자 하나**라 문서 저장소의 유연성이 쓸 데가 없다. 게다가 Redis는 **`INCR`이라는 원자적 카운터 연산**을 제공해 동시에 1000명이 조회해도 카운트가 꼬이지 않는다.

**그 선택의 대가**:
```text
"지난 7일간 조회수 추이"   → ❌
"조회수 상위 100개 상품"   → ❌ (기본으로는)
"카테고리별 평균 조회수"   → ❌
```
→ 실무에서는 **Redis로 실시간 카운트를 받고, 주기적으로 관계형 DB나 분석용 저장소에 밀어 넣는** 하이브리드 구성을 쓴다.

> **하나로 다 하려 하지 말고, 각 저장소를 잘하는 일에 쓴다.**

### 심화: 관계형으로 그래프 탐색이 왜 치명적인가 (Q2)

**① 비용이 곱셈으로 늘어난다**

```text
1단계: 친구 100명
2단계: 100 × 100 = 10,000명
3단계: 1,000,000명
4단계: 100,000,000명   ← 폭발
```

JOIN이 하나 늘 때마다 결과가 100배가 된다. **덧셈이 아니라 곱셈.**

**② 깊이를 모르면 쿼리를 쓸 수조차 없다**

"몇 다리 건너인지"는 **답이 나와봐야 아는 값**인데, SQL은 **JOIN 개수를 미리 적어야** 한다. 재귀 CTE로 흉내는 낼 수 있지만 매우 느리다.

**그래프 DB는 간선 포인터를 따라가기만 하면 된다.** 탐색 비용이 **전체 데이터 크기와 무관**하고 이웃 수에만 비례한다. 이를 **인덱스 없는 인접성(index-free adjacency)** 이라고 한다.

> **관계형은 "찾아서 맞추고", 그래프는 "따라간다".**

### 4종 한 장 비교

| | 추상화 | 강점 | 대표 용도 | 예시 |
|---|---|---|---|---|
| **키-값** | 해시 테이블 | **O(1) 성능** | 캐시, 카운터, 세션 | Redis, Memcached |
| **문서** | 값이 문서인 키-값 | **유연성 + 내부 질의** | 객체 저장, 가끔 변하는 데이터 | MongoDB, CouchDB |
| **와이드 컬럼** | 중첩 맵 | **가용성·확장성** | 매우 큰 데이터셋 | Bigtable, HBase, Cassandra |
| **그래프** | 그래프 | **복잡한 관계** | 소셜 네트워크, 추천 | Neo4j, FlockDB |

> **키-값이 가장 단순한 기반이고, 문서 저장소는 그 위에 얹힌 형태다.** 뒤로 갈수록 표현력이 커지는 대신 단순함을 잃는다.

**와이드 컬럼 vs 관계형의 차이**: SQL 테이블은 모든 행이 **같은 컬럼**을 가져야 하지만, 와이드 컬럼은 **행마다 컬럼이 달라도 된다.** 그래서 "wide" — 컬럼이 수만 개가 될 수 있고 각 행은 그중 일부만 쓴다.

### 이전 학습과의 연결

- **BASE와 최종 일관성이 실제로 구현되는 곳.** 와이드 컬럼의 타임스탬프 기반 충돌 해결이 그 예. → [[2026-08-06-backend-sql-tuning-nosql]]
- **"조인은 앱이 처리한다"** — 키-값의 연산 제한이 그 구체적 사례. → [[2026-08-05-backend-federation-sharding]]
- **조회수 집계를 관계형으로 하면 안 되는 이유**(행 잠금 경쟁, 쓰기 폭탄)와 키-값이 답인 이유가 이어진다. → [[2026-08-06-backend-sql-tuning-nosql]]
- **Redis는 캐시 계층으로도 등장했다** — 수평 확장 시 세션을 서버 밖 중앙 저장소에 두는 그 자리. → [[2026-07-30-backend-load-balancer]]
