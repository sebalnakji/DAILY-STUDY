## 질문

> **LLM에서 토크나이제이션이란 무엇인가?**
>
> 원문: *What is tokenization in LLMs?*

## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

- **정의**: 텍스트를 모델이 처리할 수 있는 최소 단위인 **토큰(token)** 으로 쪼개고, 각 토큰을 **정수 ID**로 바꾸는 과정.
- **왜 필요한가**: 신경망은 문자열을 직접 못 다룬다. **숫자만** 처리할 수 있으므로 텍스트 → 숫자 변환이 필수다.
  ```text
  "안녕하세요"  →  ["안녕", "하세요"]  →  [15496, 8917]  →  임베딩 벡터
     원문            토큰 분할            토큰 ID          모델 입력
  ```
- **왜 단어 단위가 아닌가 (subword를 쓰는 이유)**
  - **단어 단위**: 어휘 사전이 너무 커지고, 사전에 없는 단어(**OOV, Out-Of-Vocabulary**)를 처리 못 한다.
  - **글자 단위**: 사전은 작지만 시퀀스가 너무 길어지고 의미 단위가 사라진다.
  - **서브워드(subword)**: 둘의 절충. 자주 쓰는 단어는 통째로, 드문 단어는 조각으로 쪼갠다. → **OOV가 없다**(모르는 단어도 조각으로 표현 가능).
- **대표 알고리즘**
  - **BPE(Byte Pair Encoding)**: 가장 자주 함께 등장하는 문자 쌍을 반복적으로 병합해 어휘를 만든다. GPT 계열이 사용.
  - **WordPiece**: BERT 계열. 병합 기준이 빈도가 아니라 **우도(likelihood)**.
  - **SentencePiece**: 공백까지 하나의 기호로 다뤄 **언어 독립적**. 한국어·일본어처럼 띄어쓰기 규칙이 다른 언어에 유리.
- **실무에서 중요한 이유**
  - **비용과 한도가 토큰 단위**: API(Application Programming Interface) 과금, 컨텍스트 윈도우 모두 글자 수가 아니라 **토큰 수** 기준.
  - **언어별 불균형**: 영어는 토큰 효율이 좋지만, 한국어는 같은 의미에 **더 많은 토큰**이 필요해 비용·컨텍스트에서 불리하다.
  - **도메인 용어 분해 문제**: 전문 용어가 의미 없는 조각으로 쪼개지면 성능이 떨어진다.
  - **글자 단위 작업에 약한 이유**: 모델은 토큰만 보므로 *"strawberry에 r이 몇 개?"* 같은 문제에 취약하다.

## 기준 답변

> ⚠️ 이 기준 레포는 질문에 대해 텍스트 답변 대신 외부 영상/글 링크를 제공한다. 아래는 표준적인 LLM 개념을 바탕으로 재구성한 답변이다.

**토크나이제이션은 텍스트를 모델이 다룰 수 있는 최소 단위인 토큰으로 분할하고, 각 토큰을 정수 ID로 매핑하는 전처리 과정**이다.

신경망은 문자열을 직접 처리할 수 없고 숫자만 다룰 수 있으므로, LLM에 텍스트를 넣기 위해서는 반드시 이 변환이 필요하다. 토큰 ID는 이후 임베딩 벡터로 변환되어 모델에 입력된다.

토큰의 단위는 보통 단어보다 작고 글자보다 큰 **서브워드(subword)** 다. 단어 단위는 어휘 사전이 지나치게 커지고 사전에 없는 단어를 처리하지 못하며, 글자 단위는 시퀀스가 너무 길어지기 때문이다. 서브워드 방식은 자주 쓰는 단어는 통째로 두고 드문 단어는 조각으로 나누어, **모르는 단어도 조각의 조합으로 표현**할 수 있다.

대표적인 알고리즘으로 **BPE**(GPT 계열), **WordPiece**(BERT 계열), **SentencePiece**(언어 독립적)가 있다.

## 내가 정리한 내용

**1. 토크나이제이션이란?**

모델은 글자를 못 읽고 숫자만 처리 가능하다. 그래서 **텍스트를 토큰 단위로 쪼개고 각 토큰을 정수 ID로 바꿔주는** 과정이 토크나이제이션이다.

**2. 왜 서브워드인가**

BPE는 **인접한 쌍(pair)의 빈도**를 세어 자주 붙는 것부터 병합하며 스스로 토큰 사전을 만든다. 그 결과물이 서브워드다. 자주 쓰는 단어는 통째로, 드문 단어는 조각으로 남는다.

`<unk>`가 없는 이유는, 서브워드가 사전에 없으면 **최소 단위인 바이트로 내려가기** 때문이다. 바이트는 256개뿐이라 표현하지 못하는 입력이 없다.

**3. 한국어가 불리한 이유 (3겹)**

1. 한글은 UTF-8에서 **3바이트**라 출발부터 3배 무겁다.
2. 학습된 한국어 양이 영어보다 압도적으로 적어 병합이 덜 되고 **바이트로 파편화**되기 쉽다.
3. **교착어**라 조사·어미가 계속 붙어(학교가/학교를/학교에서) 같은 어간이 활용형마다 흩어진다.

①②는 데이터가 늘면 나아지지만 ③은 문법 자체라 구조적이다.

## 검토 결과

### 확인된 부분

- **byte fallback을 정확히 소화함** — "서브워드가 사전에 없으면 최소 단위인 바이트를 사용". 현대 BPE에 `<unk>`가 없는 이유의 핵심.
- 토크나이제이션의 필요성(신경망은 숫자만 처리)을 정확히 짚음.
- 한국어 불리 요인 중 바이트 크기와 학습량 부족을 스스로 도출함.
- Q2(산수 문제)에서 자릿수 경계가 무너진다는 원리를 정확히 파악.

### 보강 포인트

- **정의에 "토큰 단위"를 명시할 것.** "문자를 숫자로" → "**텍스트를 토큰으로 쪼개** 정수 ID로".
- **"문자의 빈도" → "인접한 쌍(pair)의 빈도".** BPE가 세는 것은 개별 문자가 아니라 붙어 나오는 두 조각. 이름 자체가 Byte **Pair** Encoding.
- **`<unk>`는 단어 사전 시절의 유물.** 초기 답변("조각마저 없으면 `<unk>`")은 현대 byte-level BPE에서는 발생하지 않는다. 모든 입력은 결국 바이트 나열이고 256개 바이트가 전부 어휘에 있으므로 **표현 불가능한 입력이 원천적으로 없다.**
- **한국어 불리 요인 3번(교착어)이 누락됐다가 추가됨.** 가장 근본적인 층위. ①②는 데이터가 늘면 개선되지만 ③은 문법 구조라 남는다.
- **산수 문제의 진짜 원인은 "한 자리씩 쪼개져서"가 아니라 "일관성 없이 쪼개져서"다.**
  ```text
  12345 → ["123", "45"]
  67890 → ["678", "90"]   ← 자릿수가 서로 안 맞는다
  ```
  한 자리씩 쪼개지면 오히려 자릿수가 정렬되어 낫다. 그래서 최신 모델은 숫자를 강제로 한 자리씩 분리한다. 또한 `"123"`은 모델에게 하나의 기호일 뿐 "백이십삼"이라는 크기 정보가 없다.

### 심화 1. BPE는 실제로 어떻게 동작하나

> **가장 자주 붙어 나오는 쌍을 하나로 합친다. 원하는 어휘 크기가 될 때까지 반복.** (원래 데이터 압축 알고리즘)

코퍼스: `low ×5`, `lower ×2`, `newest ×6`, `widest ×3` (`_`는 단어 끝)

```text
시작:  l o w _ / l o w e r _ / n e w e s t _ / w i d e s t _
1회차: (e,s)=9로 최다  →  "es" 병합
2회차: (es,t)=9        →  "est" 병합
3회차: (est,_)=9       →  "est_" 병합
4~5회차: (l,o)=7 → "lo",  (lo,w)=7 → "low" 병합
```

결과: `low`는 흔하니 **통째로 한 토큰**, `est`는 여러 단어에 공통이라 **재사용 조각**, `lower`는 어휘에 없어도 `low`+`e`+`r`로 **조립 가능**.

> **자주 나오는 건 통째로, 드문 건 조각으로. 그리고 규칙은 사람이 아니라 데이터가 정한다.**
> → 토크나이저조차 규칙 기반이 아니라 학습 기반이다. [[2026-07-21-ai-data-ml-vs-traditional-programming]]

### 심화 2. 세 알고리즘 비교

| | BPE | WordPiece | SentencePiece |
|---|---|---|---|
| 병합 기준 | **빈도** | **우도(likelihood)** — 합쳤을 때 전체 확률이 오르는 쌍 | (BPE/Unigram을 감싸는 틀) |
| 공백 | 전처리로 분리 | 전처리로 분리 | **공백도 문자로 취급**(`▁`) |
| 대표 | GPT 계열 | BERT 계열 | T5, LLaMA |

- WordPiece가 우도를 쓰는 이유: `"th"`는 자주 나오지만 합쳐도 정보가 없다. 덜 자주 나와도 **의미 단위가 되는** 쌍이 더 가치 있다.
- SentencePiece가 한국어에 유리한 이유: BPE/WordPiece는 **"공백으로 단어를 나눈다"는 영어의 전제**를 깔고 있다. SentencePiece는 공백조차 문자로 취급해 원문을 그대로 먹으므로 언어 가정이 없고 되돌리기(detokenize)도 완벽하다.

### 심화 3. 특수 토큰

| 토큰 | 역할 |
|---|---|
| `<\|endoftext\|>` / `</s>` | 문서·생성의 끝 |
| `<pad>` | 배치 길이 맞추기 |
| `<unk>` | 알 수 없는 토큰 (단어 사전 시절의 유물) |
| `<\|im_start\|>`, `<\|im_end\|>` | **대화 역할 구분**(system/user/assistant) |

채팅 모델이 "누가 한 말인지" 구분하는 방식이 이 특수 토큰이다. 사용자가 입력에 이 문자열을 그대로 넣으면 모델이 시스템 메시지 경계를 착각할 수 있다(**프롬프트 인젝션**). 실무에서 사용자 입력의 특수 토큰을 **제거(sanitize)** 하는 이유.

### 심화 4. 실무 함정

- **숫자 분해**: 자릿수 경계를 무시하고 빈도대로 쪼개짐 → 산수 취약.
- **공백 하나가 다른 토큰**: `"hello"` ≠ `" hello"`. 프롬프트 끝 공백이 동작을 바꿀 수 있다.
- **도메인 용어 파괴**: 전문 용어가 의미 없는 조각이 되면 성능 저하 → 토크나이저에 용어 추가.
- **NFC(Normalization Form Composed, 완성형) / NFD(Normalization Form Decomposed, 조합형)**: `"한"`(완성형 1글자) vs `"ㅎ+ㅏ+ㄴ"`(조합형 3글자)은 눈에 같아 보여도 토큰이 다르다. macOS 파일명이 NFD라 토큰이 3배로 튀는 사고가 실제로 발생 → 입력 앞단에서 **NFC 정규화**.
- **토큰 수는 미리 셀 수 있다** (`tiktoken` 등) → 비용·컨텍스트 예측.

### 심화 5. 왜 "학교" + "가"로 안 쪼개지나 (형태소 vs 서브워드)

**BPE는 형태소를 찾지 않는다.** 문법 개념 자체가 없고, 결과가 형태소와 겹치면 우연이다.

```text
형태소 분석: 먹(어간) + 었(과거) + 습니다(어미)
BPE 결과:   ["먹었", "습니다"]   ← "먹었"이 경계를 걸침
```

**왜 조사가 깔끔히 분리되지 않는가 — 세 가지 이유**

1. **BPE의 목표는 문법이 아니라 압축.** `["학교","가"]`(2토큰)보다 `["학교가"]`(1토큰)가 압축률이 좋으므로, 자주 나오면 통째로 병합해버린다.
2. **어휘 예산 부족 (핵심).** 영어 `school`은 1칸이면 끝나지만 한국어는 `학교가/학교를/학교에/학교와/학교의/학교에서…` 수십 칸이 필요하다. 어휘 사전(~10만)을 전 세계 언어가 나눠 쓰므로 한국어 몫은 일부다. → 아주 흔한 조합만 통째 토큰이 되고, 나머지는 파편화된다.
3. **병합 순서가 고정이고 탐욕적.** `"교에"`가 먼저 병합됐다면 `"학교에서"` → `["학","교에","서"]`로 경계를 침범한다. 되돌리는 기능이 없다.

**과거에는 형태소 분석기를 썼다** (`원문 → Mecab/Khaiii → 형태소 → 서브워드 → 모델`, 예: KoBERT). LLM이 이를 버린 이유: 규칙·사전 기반이라 신조어·오타에 취약, 오류 전파, 언어별 전용이라 다국어 불가, 속도 저하. → **"문법 규칙을 사람이 적어주는 방식"에서 "데이터가 알아서 쪼개는 방식"으로 이동.**

**해결책은 한국어 전용 토크나이저** (어휘 10만을 전부 한국어에). 대신 다국어 능력을 잃는다. → 또 하나의 트레이드오프.

### 심화 6. 그럼 왜 최신 모델은 한국어를 잘하나

**가장 중요한 구분: 토크나이저 효율 ≠ 모델 성능.**

`"학교에서"`가 `["학","교에","서"]`로 지저분하게 쪼개져도, 모델은 **어텐션으로 조각을 다시 조립해** 의미를 파악한다. 조각이 많아지면 계산이 늘 뿐 의미가 사라지지 않는다.

> **토크나이저 비효율 = 비용·컨텍스트 문제 / 모델 성능 = 학습의 문제. 둘은 별개 축이다.**

**성능 향상의 주역 — 교차언어 전이(cross-lingual transfer)**

모델은 지식을 언어별로 따로 배우지 않는다. **개념을 한 번 배우고 여러 언어를 거기에 연결한다.** `"사과"`, `"apple"`, `"りんご"`는 다른 토큰이지만 내부 표현 공간에서는 거의 같은 위치에 놓인다. 그래서 영어로 배운 지식이 한국어 질문에 그대로 쓰인다. 한국어 데이터는 주로 **"한국어라는 표현 방식"** 을 배우는 데 쓰이고, 내용 지식은 전체 데이터에서 공유된다.

| 요인 | 기여 |
|---|---|
| 교차언어 전이 + 데이터·규모 확대 | 성능의 대부분 ⭐ |
| 사후학습(한국어 정렬) | 자연스러운 말투·지시 이행 |
| 토크나이저 개선(어휘 확대: 5만→10만→20만) | **비용·컨텍스트** 개선 (성능 아님) |

**여전히 남은 것**: 같은 내용에 한국어가 토큰을 더 먹는다(비용·컨텍스트 불리), 글자 단위 작업(글자 수 세기, 끝말잇기)은 여전히 약하다, NFD 입력은 토큰이 폭증한다.

→ **실무 함의**: "요즘 모델은 한국어 잘하니 신경 안 써도 된다"는 품질에 대해서는 맞지만 **비용에 대해서는 틀리다.** 긴 시스템 프롬프트를 영어로 쓰는 전략은 지금도 유효.

### 이전 학습과의 연결

- LLM이 "한 **토큰**씩" 예측한다고 배운 그 토큰의 정체. → [[2026-07-22-ai-data-what-is-an-llm]]
- LLM이 *"strawberry에 r이 몇 개?"* 를 틀리는 이유: 모델은 글자가 아니라 토큰 덩어리만 본다. **버그가 아니라 토크나이저의 구조적 결과.**
- 어휘 크기는 곧 **출력층 크기**다. 모델은 매 스텝 어휘 전체에 대한 확률분포를 계산하므로, 사전이 50만이면 매 토큰마다 50만 개 확률 계산이 필요하다. **사전 크기 = 속도와 비용.**
