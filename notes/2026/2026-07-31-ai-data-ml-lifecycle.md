## 질문

> 원문: *What are stages of building machine learning models?*

## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

### 전체 흐름

```text
① 문제 정의 → ② 데이터 수집 → ③ 탐색·전처리 → ④ 특징 공학
   → ⑤ 모델 선택·학습 → ⑥ 평가·검증 → ⑦ 배포 → ⑧ 모니터링·재학습
                                                        └──── 다시 ① 또는 ⑤로 ────┘
```

**핵심: 직선이 아니라 순환(cycle)이다.** 배포는 끝이 아니라 다음 반복의 시작이다.

### 단계별 내용

1. **문제 정의(Problem Framing)**
   - 비즈니스 문제를 **ML 문제로 번역**한다. "이탈을 줄이자" → "이탈 확률을 예측하는 이진 분류".
   - 여기서 **정답(레이블)의 정의**를 확정한다. "이탈 = 90일 미접속"처럼 사람이 기준을 정해야 레이블이 생긴다.
   - **성공 기준(평가지표)** 과 **ML이 정말 필요한지**도 이 단계에서 판단한다. 규칙으로 풀 수 있으면 규칙이 낫다. → [[2026-07-21-ai-data-ml-vs-traditional-programming]]

2. **데이터 수집(Data Collection)**
   - 데이터 확보·레이블링. **레이블링 비용이 최대 병목**이다.
   - 대표성 확인: 학습 데이터가 실제 서비스 환경을 반영하는가.

3. **탐색적 데이터 분석 및 전처리(EDA & Preprocessing)**
   - 분포 확인, 결측치 처리, 이상치 처리, 스케일링, 인코딩.
   - **데이터 분할도 여기서** — train / validation / test. 전처리 기준은 **train에서만** 만들어 나머지에 적용해야 누수가 없다.

4. **특징 공학(Feature Engineering)**
   - 원시 데이터에서 예측에 유용한 변수를 만든다. 전통 ML에서 성능을 가장 크게 좌우하는 단계.
   - 딥러닝·LLM은 이 단계를 상당 부분 모델이 대신한다(표현 학습).

5. **모델 선택 및 학습(Model Selection & Training)**
   - 문제 유형(회귀/분류)에 맞는 알고리즘 선택 → 학습.
   - **베이스라인(baseline)** 을 먼저 만든다. 단순 모델·규칙보다 나은지가 첫 관문.

6. **평가 및 검증(Evaluation & Validation)**
   - validation으로 하이퍼파라미터 튜닝, **test로는 최종 한 번만** 측정. → [[2026-07-30-ai-data-validation]]
   - 지표는 문제에 맞게 선택(정확도만 보면 안 됨).

7. **배포(Deployment)**
   - 실제 서비스에 연결. 배치 예측 / 실시간 API 등 형태 결정.
   - 오프라인 지표가 좋아도 **온라인 성과는 다를 수 있어** A/B 테스트로 확인한다.

8. **모니터링 및 재학습(Monitoring & Retraining)**
   - **ML 시스템은 코드를 안 고쳐도 성능이 저하된다.** 데이터 드리프트·컨셉 드리프트 때문. → [[2026-07-21-ai-data-ml-vs-traditional-programming]]
   - 성능·입력 분포를 모니터링하고 주기적으로 재학습한다.

### 면접에서 강조할 포인트

- **가장 시간이 많이 드는 단계는 ②~④(데이터 관련)** 이지 모델링이 아니다. 흔히 전체의 70~80%.
- **배포가 끝이 아니다.** 전통 소프트웨어와 ML의 결정적 차이.
- 각 단계는 앞으로만 가지 않고 **되돌아간다.** 평가가 나쁘면 특징 공학이나 데이터 수집으로 회귀.

## 기준 답변

> ⚠️ 이 기준 레포는 질문 목록만 제공하고 답변은 싣지 않는다. 아래는 표준적인 ML 라이프사이클 기준으로 재구성한 답변이다.

머신러닝 모델 구축은 크게 **문제 정의 → 데이터 수집 → 전처리 → 특징 공학 → 모델 학습 → 평가 → 배포 → 모니터링**의 단계를 거친다.

먼저 비즈니스 문제를 ML 문제로 번역하고 레이블과 성공 기준을 정의한다. 그다음 데이터를 수집·레이블링하고, 탐색적 분석과 전처리를 거쳐 학습에 쓸 수 있는 형태로 만든다. 이때 데이터를 train/validation/test로 분할한다. 이어서 예측에 유용한 특징을 만들고, 문제 유형에 맞는 모델을 골라 학습시킨다.

평가 단계에서는 validation으로 하이퍼파라미터를 조정하고 test로 최종 성능을 한 번만 측정한다. 이후 실제 서비스에 배포하며, 오프라인 지표와 온라인 성과가 다를 수 있으므로 A/B 테스트로 확인한다.

마지막으로 **배포는 끝이 아니다.** 데이터 드리프트와 컨셉 드리프트로 인해 코드를 바꾸지 않아도 성능이 저하되므로, 지속적으로 모니터링하고 주기적으로 재학습해야 한다. 즉 이 과정은 직선이 아니라 **순환**이다.

## 내가 정리한 내용

**1. ML 모델 구축 단계**

1. **문제 정의** — 비즈니스 문제를 ML 문제로 번역하고, 레이블 정의와 성공 기준을 정한다
2. 데이터 수집
3. 데이터 라벨링
4. 데이터 전처리 (+ 특징 공학, train/validation/test 분할)
5. 모델 학습
6. 모델 평가 및 검증
7. 모델 배포
8. 모델 모니터링 및 재학습

**2. 이 과정의 특징 — 순환**

직선이 아니라 순환이다. 평가(6번)까지 진행한 뒤 결과가 나쁘면 **다시 데이터 구간(2~4번)으로 돌아올 수 있다.** 배포도 끝이 아니라, 드리프트로 성능이 저하되면 재학습을 위해 다시 앞 단계로 돌아간다.

**3. 가장 오래 걸리는 구간 — 데이터 관련(2~4번)**

- 데이터가 여기저기 흩어져 있어 필요한 것과 불필요한 것을 구분해야 하고, **정보보안(개인정보) 처리**도 해야 한다
- **라벨링을 사람이 직접** 해야 한다
- 현실 데이터는 결측치·이상치 등으로 더러워 **전처리 작업**이 많다
- 전체의 70~80%를 차지하며, **모델을 바꾸는 건 코드 몇 줄이지만 데이터를 고치는 건 몇 주**다

## 검토 결과

### 확인된 부분

- **순환 구조를 정확히 파악하고, 되돌아가는 지점(평가 → 데이터 구간)까지 구체적으로 짚음.**
- 가장 오래 걸리는 구간을 데이터 관련으로 정확히 지목하고, 이유를 **흩어진 데이터 / 라벨링 / 더러운 데이터** 세 갈래로 나눠 설명함.
- **정보보안(개인정보) 처리**를 스스로 추가함. 실무에서 실제로 큰 시간을 잡아먹는 부분으로, 교재에는 잘 안 나오는 현실적 포인트.
- 실습 Q1에서 전처리 누수를 정확히 진단(`train`에서만 기준 계산 → 나머지에 적용).

### 보강 포인트

- **① 문제 정의(Problem Framing)가 누락됨 → 추가.** 가장 중요하면서 가장 많이 건너뛰는 단계.
  - 여기서 정하는 것: 문제 유형 확정("이탈을 줄이자" → "이탈 확률 이진 분류"), **레이블 정의**("이탈 = 90일 미접속"), 성공 기준, 그리고 **애초에 ML이 필요한가**.
  - **레이블 정의가 없으면 라벨링 단계를 시작조차 못 한다.**
  - 건너뛰면 **엉뚱한 문제를 열심히 푸는 사고**가 나고, 그 사실은 배포 후에야 드러난다.
  - 면접 감별점: "이탈 예측 모델을 만들어보세요"에 바로 모델 얘기 → 주니어 / **"이탈을 어떻게 정의하나요?"** 되물음 → 시니어. → [[2026-07-21-ai-data-ml-vs-traditional-programming]]
- **특징 공학(Feature Engineering)을 따로 언급하면 깊이가 더해진다.** 전통 ML에서 성능을 가장 크게 좌우하는 단계이며, **딥러닝·LLM은 이 단계를 모델이 대신한다**(표현 학습).
- **답변 습관 메모**: 구체적 작업부터 시작하고 **프레이밍(정의) 단계를 건너뛰는 패턴**이 반복됨. → [[2026-07-30-backend-load-balancer]]에서도 정의 없이 효과만 나열. 지식이 아니라 구성 습관의 문제.

### 심화: 전처리 누수 (Q1)

전체 데이터의 평균/표준편차로 정규화하면, **그 평균에 test 데이터의 정보가 섞인다.** 모델이 test로 학습하지 않았어도 **전처리가 test를 훔쳐본** 셈이다.

**왜 반칙인가**: 실전에서는 **미래 데이터의 평균을 알 수 없다.** 내일 들어올 요청의 평균으로 오늘 정규화할 수 없다. 그래서 검증 점수만 낙관적으로 부풀고 실전에서 무너진다. → [[2026-07-30-ai-data-validation]]

**실무 앵커 — `scikit-learn`의 `fit` / `transform` 분리**

```python
scaler.fit_transform(X_train)   # fit(기준 학습) + transform  ← train에만
scaler.transform(X_test)        # transform만                 ← 기준은 train 것 재사용
```

**`fit`은 train에만, `transform`은 전체에.** `X_test`에 `fit_transform`을 쓰는 것이 초심자의 대표적 실수다.

### 심화: 왜 데이터 구간이 오래 걸리나 (Q3)

| 이유 | 내용 |
|---|---|
| 수집 자체가 어렵다 | 여러 시스템에 흩어져 있고 권한·개인정보 문제가 얽힘 |
| 라벨링이 비싸다 | 사람이 일일이 달아야 함 → [[2026-07-20-ai-data-supervised-learning]] |
| 현실 데이터는 더럽다 | 결측치, 이상치, 포맷 불일치, 중복 |
| 반복이 많다 | 성능이 안 나오면 모델이 아니라 **데이터로 되돌아옴** |

> **모델을 바꾸는 건 코드 몇 줄이지만, 데이터를 고치는 건 몇 주다.**

그래서 최근에는 모델을 고정하고 데이터를 개선하는 **데이터 중심 AI(Data-Centric AI)** 접근이 강조된다.

### 면접에서 강조할 두 가지

1. **시간의 70~80%는 모델링이 아니라 데이터에 들어간다.** "모델 튜닝보다 데이터 품질이 성능을 더 좌우한다"는 감각.
2. **배포가 끝이 아니다** — 전통 소프트웨어와의 결정적 차이.

   | | 전통 소프트웨어 | ML 시스템 |
   |---|---|---|
   | 배포 후 | 그대로 동작 | **저절로 썩음**(드리프트) |
   | 유지보수 | 버그 나면 고침 | **주기적 재학습 필수** |
