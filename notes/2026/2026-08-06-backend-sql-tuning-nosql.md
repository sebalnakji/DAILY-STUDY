## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

### SQL 튜닝의 출발점 — 측정이 먼저다

원문이 가장 먼저 강조하는 것은 기법이 아니라 **측정**이다.

- **벤치마크(Benchmark)**: `ab` 같은 도구로 **고부하 상황을 시뮬레이션**한다.
- **프로파일(Profile)**: **슬로우 쿼리 로그(slow query log)** 등을 켜서 성능 문제를 추적한다.

> **벤치마크와 프로파일링이 어떤 최적화를 할지 알려준다.** 추측으로 튜닝하지 않는다.

### ① 스키마를 조인다 (Tighten up the schema)

- 고정 길이 필드는 `VARCHAR` 대신 **`CHAR`** — `CHAR`는 빠른 임의 접근이 가능하지만, `VARCHAR`는 문자열 끝을 찾아야 다음으로 넘어간다.
- 블로그 글 같은 큰 텍스트는 **`TEXT`** — 불리언 검색이 가능하며, 디스크에는 텍스트 블록 위치를 가리키는 포인터가 저장된다.
- 큰 수는 **`INT`** (최대 2³², 약 40억)
- **통화는 `DECIMAL`** — 부동소수점 표현 오차를 피한다.
- 큰 `BLOB` 저장을 피하고 **객체의 위치(경로)를 저장**한다.
- `VARCHAR(255)`는 **8비트로 셀 수 있는 최대 문자 수**라 일부 RDBMS에서 바이트 활용을 최대화한다.
- 가능한 곳에 **`NOT NULL` 제약**을 걸어 검색 성능을 높인다.

### ② 좋은 인덱스를 쓴다 (Use good indices)

- `SELECT`, `GROUP BY`, `ORDER BY`, `JOIN`에 쓰이는 컬럼은 인덱스로 빨라질 수 있다.
- 인덱스는 보통 **자가 균형 B-트리**로 구현되어, 데이터를 정렬 상태로 유지하며 **검색·순차 접근·삽입·삭제를 로그 시간**에 처리한다.
- ⚠️ **대가**
  - 인덱스를 두면 데이터가 메모리에 상주해 **공간을 더 쓴다.**
  - **쓰기가 느려진다** — 인덱스도 함께 갱신해야 하기 때문.
  - 대량 데이터를 적재할 때는 **인덱스를 껐다가 적재 후 재구축**하는 편이 빠를 수 있다.

### ③ 비싼 조인을 피한다

- 성능이 요구되면 **비정규화**한다. → [[2026-08-05-backend-federation-sharding]]

### ④ 테이블을 분할한다 (Partition tables)

- **핫스팟(자주 접근되는 부분)을 별도 테이블로** 떼어내 메모리에 유지되게 한다.

### ⑤ 쿼리 캐시를 튜닝한다

- 경우에 따라 **쿼리 캐시가 오히려 성능 문제를 일으킬 수 있다.**

### NoSQL

**키-값 저장소, 문서 저장소, 와이드 컬럼 저장소, 그래프 데이터베이스**로 표현되는 데이터 항목의 모음이다.

- 데이터는 **비정규화**되어 있고, **조인은 보통 애플리케이션 코드에서** 수행한다. → [[2026-08-05-backend-federation-sharding]]에서 본 앱 레벨 조인과 같은 이야기
- 대부분의 NoSQL 저장소는 **진정한 ACID 트랜잭션이 없고 최종 일관성을 선호**한다.

### BASE — NoSQL의 속성

**CAP 정리와 비교하면 BASE는 일관성보다 가용성을 택한다.** → [[2026-07-22-backend-availability-vs-consistency]]

| | 뜻 | 설명 |
|---|---|---|
| **BA** — Basically Available | 기본적 가용성 | 시스템이 **가용성을 보장**한다 |
| **S** — Soft state | 유연한 상태 | **입력이 없어도** 시간이 지나며 상태가 변할 수 있다 |
| **E** — Eventual consistency | 최종 일관성 | 일정 시간이 지나면 **결국 일관된 상태가 된다** (그동안 입력이 없다는 전제) |

### ACID vs BASE

| | ACID (관계형) | BASE (NoSQL) |
|---|---|---|
| 우선하는 것 | **일관성** | **가용성** |
| CAP 선택 | CP 성향 | **AP 성향** |
| 일관성 | 강한 일관성 | **최종 일관성** |
| 조인 | DB가 처리 | **애플리케이션이 처리** |
| 데이터 형태 | 정규화 | **비정규화** |

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

**SQL 튜닝**은 방대한 주제이지만, 핵심은 **벤치마크와 프로파일링으로 병목을 드러내는 것**이다. `ab` 같은 도구로 고부하를 시뮬레이션하고, 슬로우 쿼리 로그 같은 도구로 성능 문제를 추적한다. 이 측정이 어떤 최적화를 할지 알려준다.

주요 최적화는 다음과 같다.

- **스키마 조이기**: 고정 길이엔 `CHAR`, 큰 텍스트엔 `TEXT`, 통화엔 `DECIMAL`(부동소수점 오차 방지), 큰 `BLOB` 대신 위치 저장, 가능한 곳에 `NOT NULL`
- **좋은 인덱스**: 조회에 쓰이는 컬럼에 인덱스를 건다. 인덱스는 보통 **자가 균형 B-트리**로 로그 시간 연산을 제공한다. 다만 **공간을 더 쓰고 쓰기가 느려지며**, 대량 적재 시에는 인덱스를 껐다가 재구축하는 편이 빠를 수 있다.
- **비싼 조인 회피**: 필요하면 비정규화
- **테이블 분할**: 핫스팟을 별도 테이블로 분리해 메모리에 유지
- **쿼리 캐시 튜닝**: 경우에 따라 오히려 성능 문제를 유발할 수 있다

**NoSQL**은 키-값 저장소, 문서 저장소, 와이드 컬럼 저장소, 그래프 데이터베이스로 표현되는 데이터 항목의 모음이다. 데이터는 비정규화되며 조인은 대개 애플리케이션 코드에서 처리한다. 대부분 진정한 ACID 트랜잭션이 없고 **최종 일관성을 선호**한다.

NoSQL의 속성을 설명할 때 **BASE**를 쓴다. CAP 정리와 비교하면 **BASE는 일관성보다 가용성을 택한다.**

- **Basically available**: 시스템이 가용성을 보장한다
- **Soft state**: 입력이 없어도 시간이 지나며 상태가 변할 수 있다
- **Eventual consistency**: 그 기간 동안 입력이 없다면 시간이 지나 결국 일관된 상태가 된다

## 내가 정리한 내용

**1. SQL 튜닝은 무엇부터 시작하는가**

**벤치마크와 프로파일링부터 시작한다.** `ab` 같은 도구로 고부하 상황을 시뮬레이션하고, 슬로우 쿼리 로그 등으로 근본적인 병목 원인을 찾은 뒤, **원인에 맞는 튜닝**을 한다. 추측으로 튜닝하지 않는다.

이후의 최적화로는 스키마 조이기(고정 길이엔 `CHAR`, 통화엔 `DECIMAL`, 큰 `BLOB` 대신 위치 저장), 인덱스, 비정규화, 테이블 분할, 쿼리 캐시 튜닝이 있다.

**2. 인덱스의 효과와 대가**

- **효과**: `SELECT`, `GROUP BY`, `ORDER BY`, `JOIN`에 쓰이는 컬럼의 **읽기가 빨라진다.** 보통 **자가 균형 B-트리**로 구현되어 검색·삽입·삭제를 **로그 시간**에 처리한다.
- **대가**: **공간을 더 쓰고**(인덱스가 메모리에 상주), **쓰기가 느려진다**(데이터와 함께 인덱스도 갱신해야 함). 대량 적재 시에는 인덱스를 껐다가 재구축하는 편이 빠를 수 있다.
- 즉 **인덱스는 읽기를 위해 쓰기를 희생한다.** 안 쓰이는 인덱스는 이득 없이 비용만 발생하므로, 실제 쿼리 패턴을 보고 설계해야 한다.

**3. BASE란? ACID와의 차이**

- **BA(Basically Available)**: 가용성을 보장한다.
- **S(Soft state)**: 입력이 없어도 상태가 변할 수 있다.
- **E(Eventual consistency)**: 시간이 지나면 결국 일관해진다.

ACID에 비해 **일관성보다 가용성을 우선**하고, **강한 일관성보다 최종 일관성**을 택한다. CAP으로 보면 ACID는 CP 성향, BASE는 **AP 성향**이다. 또한 조인을 ACID(관계형)는 DB가 처리하지만 **BASE(NoSQL)는 애플리케이션이 처리**하며, 데이터는 비정규화되어 있다.

## 검토 결과

### 확인된 부분

- **BASE 정의를 완전하게 서술하고, ACID와의 차이를 다층으로 비교함**(일관성 우선순위, CAP 성향, 조인 처리 주체, 정규화 여부). 이 항목은 보강할 것이 없다.
- SQL 튜닝의 출발점을 **"측정 후 원인에 맞는 튜닝"** 으로 정확히 잡음.
- 실습 Q1에서 인덱스의 대가 세 가지를 모두 지적.
- 실습 Q2에서 조회수 집계를 NoSQL 대상으로 정확히 판단하고 근거(가용성·최종 일관성)를 제시.

### 보강 포인트

- **벤치마크가 초기 답변에서 누락 → 추가.** 원문은 벤치마크와 프로파일을 짝으로 제시한다.

  | | 하는 일 |
  |---|---|
  | **벤치마크** | 고부하 상황을 **만들어본다** (`ab` 등) |
  | **프로파일** | 그때 **어디가 느린지 추적한다** (슬로우 쿼리 로그) |

  **부하를 걸어야 병목이 드러난다.** 한가할 땐 안 보이던 문제가 부하 상태에서 나타난다. → [[2026-07-20-backend-performance-vs-scalability]]
- **인덱스 정리에 공간 비용과 B-트리 언급을 추가.** 구현 구조를 한마디 붙이면 원리를 아는 답변이 된다.
- **실무 함정: 안 쓰는 인덱스는 순수 손해다.** "혹시 모르니 걸어두자"가 흔한 실수. 조회에 안 쓰이면 **이득 0, 비용 100%**. 인덱스가 많으면 옵티마이저가 엉뚱한 것을 고르기도 한다. → **인덱스는 "추가"가 아니라 "설계"다.**
- **"조회수 집계"는 읽기 기능처럼 보이지만 사실 쓰기 폭탄이다.** (Q2 심화)
  ```text
  상품 페이지 조회 1000만 번 = UPDATE 1000만 번
  ```
  인기 상품 하나에 조회가 몰리면 **같은 행에 쓰기가 집중**되어 행 잠금(row lock) 경쟁이 발생한다. 관계형 DB에는 최악의 워크로드이며, Redis 같은 키-값 저장소로 빼는 것이 정석. → [[2026-08-04-backend-database-rdbms]]
- **결제·주문에 ACID가 필수인 이유**

  | 속성 | 없으면 |
  |---|---|
  | 원자성 | 출금은 됐는데 주문이 안 생김 → **돈만 사라짐** |
  | 격리성 | 재고 1개를 동시에 2명이 구매 → **초과 판매** |
  | 지속성 | 결제 완료 알림 직후 서버 다운 → **결제 증발** |

  > **틀리면 돈이 걸린 것은 ACID, 조금 틀려도 되는 것은 BASE.** 오류의 비용이 선택을 결정한다. → [[2026-08-04-ai-data-classification-metrics]]

## 심화: B-트리와 B+트리

### 1. 출발점 — 디스크는 느리다

```text
메모리 접근:  약 100 나노초
디스크 접근:  약 10 밀리초  = 약 100,000배 느림
```

> **"디스크를 몇 번 읽느냐"가 성능을 결정한다.** 계산량이 아니라 **접근 횟수**가 병목이다.

또한 디스크는 **블록(페이지) 단위**로 읽는다. 1바이트를 읽든 4KB를 읽든 비용이 같다. **이 두 사실이 B-트리 설계를 전부 결정한다.**

### 2. 이진 탐색 트리로는 왜 안 되나

```text
100만 건을 이진 트리로 저장하면
높이 = log₂(1,000,000) ≈ 20
→ 최악의 경우 디스크 접근 20회 ≈ 200ms
```

게다가 노드 하나에 키가 딱 하나라, 4KB 블록을 읽어와 **키 하나만 보고 버리는 낭비**가 발생한다.

> **문제: 트리가 너무 높고, 블록을 낭비한다.**

### 3. B-트리의 해법 — 노드를 뚱뚱하게

**한 노드에 키를 여러 개 담는다.** 노드 하나가 **디스크 블록 하나에 딱 맞게** 설계된다.

```text
        [ 30 | 60 ]              ← 키 2개, 자식 3개
       /     |     \
  [10|20] [40|50] [70|80]
```

키가 `n`개면 자식은 `n+1`개이며, 각 자식은 키 사이 구간을 담당한다.

**노드 하나에 키 100개를 담으면(팬아웃 100)**

```text
높이 1:        100개 키
높이 2:     10,000개
높이 3:  1,000,000개  ← 100만 건이 높이 3
```

| | 이진 트리 | B-트리 (팬아웃 100) |
|---|---|---|
| 100만 건의 높이 | **20** | **3** |
| 디스크 접근 | 20회 (~200ms) | **3회 (~30ms)** |

> **B-트리의 본질: 트리를 넓고 낮게 만들어 디스크 접근 횟수를 줄인다.**

실제로는 팬아웃이 수백이라 **수십억 건도 높이 4** 정도면 커버된다.

### 4. 자가 균형(Self-balancing)

한쪽으로 치우치면 이진 트리처럼 높아지므로, 삽입·삭제 때마다 스스로 균형을 맞춘다.

**삽입 — 노드가 꽉 차면 분할(Split)**

```text
[10|20|30] 에 25 삽입 (최대 3개 가정)
        ↓
      [20]           ← 가운데 키가 위로 올라감
     /    \
 [10]    [25|30]
```

**삭제 — 노드가 너무 비면 병합(Merge)** 하거나 형제에게서 빌려온다.

> **모든 리프의 깊이가 항상 같다.** 그래서 최악의 경우에도 **로그 시간이 보장**된다. 원문의 "정렬 상태를 유지하며 로그 시간에 처리"가 이 뜻이다.

### 5. 실제 DB는 B+트리를 쓴다 ⭐

MySQL InnoDB, PostgreSQL 등 대부분이 **B+트리**를 사용한다.

| | B-트리 | **B+트리** |
|---|---|---|
| 데이터 위치 | 모든 노드 | **리프에만** |
| 내부 노드 | 키 + 데이터 | **키만** (이정표) |
| 리프 연결 | 없음 | **연결 리스트로 이어짐** |

```text
       [ 30 | 60 ]              ← 내부: 키만 (길 안내)
      /     |      \
 [10|20]→[30|40]→[60|70]        ← 리프: 실제 데이터 + 옆으로 연결
```

**B+트리가 나은 두 가지 이유**

1. **팬아웃이 더 크다** — 내부 노드에 데이터를 안 넣으니 같은 블록에 키를 더 많이 담는다 → 트리가 더 낮아진다.
2. **범위 검색이 압도적으로 빠르다**
   ```sql
   SELECT * FROM users WHERE age BETWEEN 20 AND 30;
   ```
   B-트리는 20과 30을 각각 트리를 타고 찾아야 하지만, B+트리는 **20을 찾은 뒤 리프 연결 리스트를 따라 옆으로 읽으면** 끝난다.
   → **`ORDER BY`, `BETWEEN`, `>`, `<` 가 인덱스로 빨라지는 이유**가 이 리프 연결이다.

### 6. 왜 인덱스가 쓰기를 느리게 하나 (구조로 보기)

`INSERT` 한 번에 일어나는 일:

```text
① 테이블에 행 추가
② 인덱스 B+트리에서 들어갈 위치 탐색
③ 리프에 키 삽입 (정렬 유지)
④ 꽉 찼으면 노드 분할 → 부모도 갱신 → 연쇄될 수 있음
```

**인덱스가 10개면 ②~④를 10번 반복한다.**

> **읽기는 "이미 정렬된 걸 찾는" 일이고, 쓰기는 "정렬을 유지하는" 일이다.** 후자가 훨씬 비싸다.

**대량 적재 시 인덱스를 껐다 재구축하는 게 빠른 이유**도 여기 있다. 한 건씩 넣으며 매번 분할하는 것보다, 다 넣고 **한 번에 정렬해 트리를 구축**하는 편이 효율적이다.

### 7. 인덱스가 안 타는 경우 ⚠️

B+트리 구조를 알면 **왜 안 타는지**가 보인다. 면접 단골.

**① 앞에 와일드카드**
```sql
WHERE name LIKE '%김'    -- ❌ 인덱스 못 탐
WHERE name LIKE '김%'    -- ✅ 탐
```
정렬은 **앞글자 기준**이다. 앞이 `%`면 시작점을 못 찾아 전부 뒤져야 한다. 사전에서 "끝이 '김'인 단어"를 찾는 것과 같다.

**② 컬럼에 함수를 씌움**
```sql
WHERE YEAR(created_at) = 2026        -- ❌
WHERE created_at >= '2026-01-01'     -- ✅
```
인덱스는 `created_at` **원본값**으로 정렬돼 있다. 함수를 씌운 값은 정렬 순서가 다르다.

**③ 복합 인덱스의 왼쪽 접두사 규칙**
```sql
-- INDEX (a, b, c) 가 있을 때
WHERE a = 1              -- ✅
WHERE a = 1 AND b = 2    -- ✅
WHERE b = 2              -- ❌ a 없이는 못 탐
```
`(a, b, c)` 순으로 정렬됐으므로 **`a`부터** 봐야 한다. 전화번호부가 `성 → 이름` 순인데 이름만으로는 못 찾는 것과 같다.

**④ 카디널리티가 낮음**
`성별`처럼 값이 2~3개뿐이면 인덱스를 타도 절반을 읽어야 한다. 옵티마이저가 "차라리 전체 스캔이 낫다"고 판단해 인덱스를 무시한다.

> **인덱스는 값이 다양할수록(카디널리티가 높을수록) 효과적이다.**

### B-트리 한 장 요약

| 개념 | 핵심 |
|---|---|
| **왜 트리?** | 디스크 접근 횟수를 줄이려고 |
| **왜 B-트리?** | 노드를 뚱뚱하게 → **넓고 낮은 트리** |
| **자가 균형** | 분할·병합으로 모든 리프 깊이를 동일하게 → 로그 시간 보장 |
| **B+트리** | 데이터는 리프에만 + 리프 연결 → **범위 검색이 빠름** |
| **쓰기가 느린 이유** | 정렬 유지 + 노드 분할, 인덱스 개수만큼 반복 |
| **안 타는 경우** | 앞 와일드카드, 함수 적용, 복합 인덱스 순서 위반, 낮은 카디널리티 |
