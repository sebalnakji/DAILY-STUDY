# 백엔드 보안의 기본 원칙 네 가지

> ℹ️ 원문은 이 섹션이 짧다고 밝히며 **"보안 배경이 없다면 기본만 알면 된다"** 고 명시한다. 아래 `핵심 개념`은 그 네 가지 기본을 이해에 필요한 만큼 확장한 것이다.

## 질문

> **백엔드 개발자가 알아야 할 보안의 기본은 무엇인가?**
>
> 원문: *Security*

## 핵심 개념

원문이 제시하는 네 가지 기본은 다음과 같다.

1. **전송 중(in transit)과 저장 시(at rest) 암호화하라.**
2. **XSS와 SQL 인젝션을 막기 위해 모든 사용자 입력과 사용자에게 노출되는 입력 파라미터를 검증(sanitize)하라.**
3. **SQL 인젝션을 막기 위해 파라미터화 쿼리를 사용하라.**
4. **최소 권한 원칙(principle of least privilege)을 사용하라.**

### ① 전송 중·저장 시 암호화

| 구분 | 뜻 | 수단 |
|---|---|---|
| **전송 중(in transit)** | 네트워크를 이동하는 동안 | **TLS/HTTPS** |
| **저장 시(at rest)** | 디스크에 저장된 상태 | 디스크 암호화, 컬럼 암호화 |

- **왜 둘 다인가**: 통신만 암호화하면 **DB가 유출됐을 때 무방비**이고, 저장만 암호화하면 **중간에서 가로채기(MITM)** 에 무방비다.
- **SSL termination**을 로드밸런서·리버스 프록시에서 처리하면 백엔드가 암복호화 부담을 덜지만, **그 이후 구간이 평문**이 된다는 점을 인지해야 한다. → [[2026-07-31-backend-reverse-proxy]]
- **비밀번호는 암호화가 아니라 해시**한다(bcrypt, Argon2 등). 복호화할 필요가 없기 때문.

### ② 입력 검증 — XSS와 SQL 인젝션

**모든 사용자 입력은 신뢰할 수 없다**는 것이 대전제다.

**XSS(Cross-Site Scripting)**
- 공격자가 **악성 스크립트를 페이지에 삽입**해 다른 사용자의 브라우저에서 실행시킨다.
- 예: 댓글에 `<script>` 태그를 넣어 다른 사용자의 세션 쿠키를 탈취.
- **대응**: 출력 시 이스케이프, 입력 검증, `Content-Security-Policy` 헤더, 쿠키에 `HttpOnly`

**SQL 인젝션**
- 입력값이 **SQL 문법으로 해석**되어 쿼리 구조 자체를 바꾼다.

```python
# 취약 — 문자열을 이어붙임
query = "SELECT * FROM users WHERE id = '" + user_input + "'"
# user_input = "' OR '1'='1"  →  모든 사용자가 조회됨
```

### ③ 파라미터화 쿼리(Parameterized Query)

**SQL 인젝션의 근본 대책.**

```python
# 안전 — 값과 구문을 분리
cursor.execute("SELECT * FROM users WHERE id = %s", (user_input,))
```

- **왜 안전한가**: 쿼리의 **구조를 먼저 확정**하고 값을 나중에 바인딩하므로, 입력에 무엇이 들어와도 **데이터로만 취급**된다. 문법으로 해석될 여지가 없다.
- 이스케이프 처리로 막으려는 시도는 **누락이 생기기 쉬워** 근본 대책이 못 된다.

### ④ 최소 권한 원칙(Principle of Least Privilege)

**각 주체는 자기 일에 필요한 최소한의 권한만 가져야 한다.**

- 조회만 하는 서비스의 DB 계정에 **쓰기·삭제 권한을 주지 않는다.**
- 애플리케이션이 **DB 관리자 계정으로 접속하지 않는다.**
- **왜**: 어딘가 뚫렸을 때 **피해 범위를 제한**한다. 침입을 못 막아도 **확산을 막는다.**

> 이는 **방어의 마지막 겹**이다. 앞의 세 가지가 침입을 막는 것이라면, 최소 권한은 **뚫린 뒤의 피해를 줄인다.**

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

원문은 **보안이 넓은 주제**이며, **상당한 경험이나 보안 배경이 있거나 보안 지식을 요구하는 직무에 지원하는 것이 아니라면 기본 이상을 알 필요는 없을 것**이라고 전제한다. 그 기본은 다음 네 가지다.

- **전송 중과 저장 시 암호화하라.**
- **XSS와 SQL 인젝션을 방지하기 위해 모든 사용자 입력 또는 사용자에게 노출되는 입력 파라미터를 검증(sanitize)하라.**
- **SQL 인젝션을 방지하기 위해 파라미터화 쿼리를 사용하라.**
- **최소 권한 원칙을 사용하라.**

원문은 더 깊은 학습을 위해 **API 보안 체크리스트**, **개발자를 위한 보안 가이드**, **OWASP Top Ten**을 참고 자료로 제시한다.

## 내가 정리한 내용

**1. 백엔드 보안의 기본 원칙 네 가지**

- **전송 중(in transit)과 저장 시(at rest) 암호화** — 하나만 하면 반대쪽이 무방비다. 전송만 하면 DB 유출에, 저장만 하면 중간 가로채기에 취약하다.
- **모든 사용자 입력 검증(sanitize)** — XSS와 SQL 인젝션을 막기 위해. 대전제는 **모든 사용자 입력을 신뢰하지 않는 것**이다.
- **파라미터화 쿼리 사용** — SQL 인젝션의 근본 대책.
- **최소 권한 원칙 사용** — 각 주체가 자기 일에 필요한 최소 권한만 갖게 한다.

**2. 파라미터화 쿼리가 근본 대책인 이유**

**쿼리의 구조를 먼저 확정하고 값을 나중에 바인딩**하므로, 입력값이 무엇이 들어와도 **그냥 문자열 데이터로 취급**되어 **문법으로 해석될 여지가 사라진다.**

또한 이스케이프 방식은 **한 곳이라도 빠뜨리면 뚫리고** DB별 문법 차이나 인코딩 우회 같은 함정도 있지만, 파라미터화는 **구조적으로 불가능**하게 만든다. **규율이 아니라 구조로 막는 것**이다.

**3. 최소 권한 원칙이 필요한 이유**

**최소 권한은 침입을 전제한 방어**다. 침입을 당하더라도 권한을 제한해두면 **최소한의 피해로 막을 수 있다.** 이를 **심층 방어(Defense in Depth)** 라고 한다.

예를 들어 SQL 인젝션이 성공해도, 읽기 전용 계정이라면 데이터 유출은 발생하지만 **삭제·변조는 막힌다.** 또한 서버 한 대가 뚫려도 그 계정으로 다른 시스템에 넘어갈 수 없어 **피해 확산(횡적 이동)을 차단**한다.

## 검토 결과

### 확인된 부분

- **네 가지 원칙을 정확히 나열**하고, 각각이 무엇을 막는지 연결함.
- **파라미터화 쿼리의 메커니즘**(구조 확정 → 값 바인딩 → 데이터로만 취급)을 정확히 설명.
- **최소 권한을 "침입을 전제한 방어"** 로 정확히 규정. 앞의 세 원칙과 성격이 다르다는 점을 파악했다.

### 보강 포인트

- **파라미터화의 실무적 이유를 덧붙일 것.** 기술적 메커니즘만으로는 "이스케이프도 제대로 하면 되지 않나"에 답이 안 된다.

  ```python
  # 이스케이프 방식 — 100곳 중 99곳을 잘해도 1곳이 뚫리면 끝
  query = "... " + escape(user_input) + " ..."   # ← 여기 하나 빠뜨리면?
  ```

  코드 리뷰로 100% 잡기 어렵다. 급하게 짠 코드 한 줄, 신입이 추가한 쿼리 하나에서 샌다. 또한 **DB마다 이스케이프 문법이 다르고, 멀티바이트 인코딩으로 우회**하는 고전적 공격도 있다.

  > **보안의 원칙: 규율에 의존하지 말고 구조로 막아라.**
  > *"조심하면 안전하다"* 보다 *"실수해도 안전하다"* 가 낫다.

- **심층 방어(Defense in Depth)** 라는 용어를 붙이면 개념이 명확해진다.

### 심화: 최소 권한의 효과 규모

```text
SQL 인젝션이 성공했을 때

DB 관리자 계정:  전체 조회 + 수정 + 삭제 + 다른 DB 접근  → 회사가 끝남
읽기 전용 계정:  조회만 가능                             → 유출은 되지만 파괴는 막힘
```

**같은 공격, 완전히 다른 결말이다.** 또한 **횡적 이동(lateral movement)** 을 막는다 — 서버 한 대가 뚫려도 그 계정으로 다른 시스템에 못 넘어가면 피해가 거기서 멈춘다.

### 지금까지 배운 것과 같은 사고방식

| 영역 | 전제 |
|---|---|
| 가용성 | **서버는 반드시 죽는다** → 이중화 → [[2026-07-25-backend-availability-patterns]] |
| 마이크로서비스 | **네트워크는 실패한다** → 회로 차단기 → [[2026-08-03-backend-application-layer]] |
| 캐시 | **캐시는 죽는다** → 썬더링 허드 대비 → [[2026-08-11-backend-cache]] |
| **보안** | **언젠가 뚫린다** → **최소 권한** |

> **"완벽하게 막는다"가 아니라 "실패를 전제하고 피해를 가둔다"** — 시스템 설계 전반을 관통하는 태도다.

### 각 원칙 상세

**① 암호화 — 두 곳 다**

| 구분 | 언제 | 수단 |
|---|---|---|
| **전송 중** | 네트워크를 이동할 때 | **TLS/HTTPS** |
| **저장 시** | 디스크에 있을 때 | 디스크·컬럼 암호화 |

⚠️ **SSL termination을 로드밸런서에서 하면** 백엔드는 편해지지만 **그 이후 구간은 평문**이다. → [[2026-07-31-backend-reverse-proxy]]

**비밀번호는 예외** — 암호화가 아니라 **해시**(bcrypt, Argon2). 되돌릴 필요가 없기 때문.

**② XSS와 SQL 인젝션**

- **XSS(Cross-Site Scripting)**: 공격자가 악성 스크립트를 페이지에 삽입해 **다른 사용자의 브라우저**에서 실행시킨다. 댓글에 스크립트를 넣어 세션 쿠키를 탈취하는 식. **피해자가 내가 아니라 다른 사용자**라는 것이 특징.
  - 대응: 출력 시 이스케이프, `Content-Security-Policy` 헤더, 쿠키 `HttpOnly`
- **SQL 인젝션**: 입력값이 SQL 문법으로 해석되어 쿼리 구조를 바꾼다.

  ```python
  query = "SELECT * FROM users WHERE id = '" + user_input + "'"
  # user_input = "' OR '1'='1"
  # → SELECT * FROM users WHERE id = '' OR '1'='1'
  # → 전체 사용자 조회 💥
  ```

**③ 파라미터화 쿼리**

```python
# 취약: 문자열 이어붙이기
"SELECT * FROM users WHERE id = '" + user_input + "'"

# 안전: 값과 구문을 분리
cursor.execute("SELECT * FROM users WHERE id = %s", (user_input,))
```

**④ 최소 권한**

- 조회만 하는 서비스의 DB 계정에 **쓰기·삭제 권한을 주지 않는다**
- 애플리케이션이 **DB 관리자 계정으로 접속하지 않는다**

| | 목적 |
|---|---|
| ①②③ | **침입을 막는다** |
| ④ | **뚫린 뒤 피해를 줄인다** |
