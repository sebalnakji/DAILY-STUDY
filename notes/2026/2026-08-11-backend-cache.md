## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

### 왜 쓰는가

- **페이지 로드 시간을 개선**하고 **서버·데이터베이스 부하를 줄인다.**
- 요청이 전에도 있었는지 먼저 조회해, 이전 결과를 반환함으로써 **실제 실행을 아낀다.**
- **불균등한 부하를 흡수한다** — 데이터베이스는 파티션 전반에 읽기·쓰기가 **고르게 분산**될 때 유리한데, **인기 항목이 분포를 치우치게 해 병목**을 만든다. DB 앞에 캐시를 두면 이런 쏠림과 트래픽 급증을 완충한다.

### 캐시를 둘 수 있는 위치

| 위치 | 설명 |
|---|---|
| **클라이언트 캐싱** | OS나 브라우저 |
| **CDN 캐싱** | CDN도 캐시의 한 종류 → [[2026-07-29-backend-content-delivery-network]] |
| **웹 서버 캐싱** | 리버스 프록시와 Varnish 같은 캐시가 정적·동적 콘텐츠를 **직접 제공**. 앱 서버에 접촉하지 않고 응답 → [[2026-07-31-backend-reverse-proxy]] |
| **데이터베이스 캐싱** | DB 기본 설정에 이미 일정 수준의 캐싱이 포함. 사용 패턴에 맞게 조정하면 성능이 더 오름 |
| **애플리케이션 캐싱** | Memcached·Redis 같은 **인메모리 캐시**를 앱과 저장소 사이에 둠 |

### 애플리케이션 캐싱

- 데이터가 **RAM에 있어** 디스크 기반 DB보다 훨씬 빠르다.
- RAM은 디스크보다 제한적이므로, **LRU(Least Recently Used)** 같은 **캐시 무효화 알고리즘**으로 '차가운' 항목을 밀어내고 '뜨거운' 데이터를 유지한다.
- **Redis의 추가 기능**: 영속성(persistence) 옵션, 정렬 집합·리스트 같은 **내장 자료구조**

### 캐싱 수준 — 두 범주

**데이터베이스 쿼리**와 **객체**로 나뉜다.

- 행(row) 수준
- 쿼리 수준
- 완전히 형성된 직렬화 가능 객체
- 완전히 렌더링된 HTML

> **파일 기반 캐싱은 일반적으로 피해야 한다.** 복제와 오토스케일링이 어려워지기 때문. → [[2026-07-30-backend-load-balancer]]의 무상태 원칙

### 쿼리 수준 캐싱의 문제

쿼리를 해시해 키로 삼고 결과를 저장하는 방식인데, **만료 문제**가 있다.

- **복잡한 쿼리는 캐시된 결과를 지우기 어렵다.**
- 테이블 셀 하나가 바뀌면, **그 셀을 포함할 수 있는 모든 캐시 쿼리를 지워야 한다.**

### 객체 수준 캐싱

데이터를 애플리케이션 코드처럼 **객체로 본다.** DB에서 가져온 데이터셋을 클래스 인스턴스나 자료구조로 조립한다.

- 기반 데이터가 바뀌면 **그 객체를 캐시에서 제거**한다.
- **비동기 처리가 가능해진다** — 워커가 최신 캐시 객체를 소비하며 객체를 조립한다.

**캐싱하기 좋은 것들**: 사용자 세션, 완전히 렌더링된 웹 페이지, 활동 스트림, 사용자 그래프 데이터

## 캐시 갱신 전략 4가지

저장 가능한 데이터가 제한적이므로, 용도에 맞는 갱신 전략을 정해야 한다.

### ① Cache-aside (= Lazy loading)

**애플리케이션이 저장소 읽기·쓰기를 책임진다. 캐시는 저장소와 직접 상호작용하지 않는다.**

```text
① 캐시에서 항목을 찾는다 → 캐시 미스
② 데이터베이스에서 항목을 읽는다
③ 캐시에 항목을 추가한다
④ 항목을 반환한다
```

```python
def get_user(self, user_id):
    user = cache.get("user.{0}", user_id)
    if user is None:
        user = db.query("SELECT * FROM users WHERE user_id = {0}", user_id)
        if user is not None:
            key = "user.{0}".format(user_id)
            cache.set(key, json.dumps(user))
    return user
```

- Memcached가 보통 이 방식으로 쓰인다.
- **요청된 데이터만 캐싱**되므로 요청되지 않는 데이터로 캐시가 차는 것을 피한다.

**단점**
- **캐시 미스마다 3번의 왕복**이 발생해 눈에 띄는 지연이 생길 수 있다.
- DB에서 갱신되면 **데이터가 낡을 수 있다.** TTL(Time To Live)을 설정하거나 write-through를 함께 써서 완화한다.
- **노드가 죽으면 빈 노드로 교체**되어 지연이 증가한다.

### ② Write-through

**애플리케이션이 캐시를 주 저장소처럼 쓰고, 캐시가 DB 읽기·쓰기를 책임진다.**

```text
① 애플리케이션이 캐시에 항목을 추가/갱신
② 캐시가 데이터 저장소에 동기적으로 기록
③ 반환
```

```python
# 애플리케이션 코드
set_user(12345, {"foo": "bar"})

# 캐시 코드
def set_user(user_id, values):
    user = db.query("UPDATE Users WHERE id = {0}", user_id, values)
    cache.set(user_id, user)
```

- 쓰기 연산 때문에 **전체적으로 느리지만**, 방금 쓴 데이터의 **후속 읽기는 빠르다.**
- **사용자는 읽기보다 갱신에서의 지연에 관대하다.**
- **캐시의 데이터가 낡지 않는다.**

**단점**
- 장애나 확장으로 **새 노드가 생기면, DB에서 갱신되기 전까지 그 노드는 캐시가 비어 있다.** cache-aside와 함께 쓰면 완화된다.
- **쓴 데이터 대부분이 읽히지 않을 수 있다.** TTL로 최소화한다.

### ③ Write-behind (= Write-back)

```text
① 캐시에 항목을 추가/갱신
② 데이터 저장소에는 비동기로 기록  → 쓰기 성능 향상
```

**단점**
- **캐시가 저장소에 반영되기 전에 죽으면 데이터가 유실**될 수 있다.
- cache-aside나 write-through보다 **구현이 복잡하다.**

### ④ Refresh-ahead

**최근 접근된 캐시 항목을 만료 직전에 자동으로 갱신**하도록 설정한다.

- 캐시가 **앞으로 필요할 항목을 정확히 예측**할 수 있다면 read-through 대비 **지연시간이 줄어든다.**

**단점**
- **예측이 부정확하면 오히려 성능이 떨어진다.**

### 전략 비교

| | 쓰기 시점 | 읽기 속도 | 데이터 신선도 | 주 위험 |
|---|---|---|---|---|
| **Cache-aside** | 캐시 미스 시 채움 | 첫 요청 느림 | **낡을 수 있음** | stale, 미스 시 3회 왕복 |
| **Write-through** | 쓰기와 동시(동기) | 빠름 | **항상 최신** | 쓰기 느림, 안 읽힐 데이터 |
| **Write-behind** | 쓰기 후 비동기 | 빠름 | 최신 | **유실 위험**, 복잡 |
| **Refresh-ahead** | 만료 전 미리 | 빠름 | 최신 | **예측 실패 시 손해** |

## 캐시의 단점

- **캐시와 진실의 원천(DB) 사이의 일관성을 유지**해야 한다 — 캐시 무효화(cache invalidation)
- **캐시 무효화는 어려운 문제**이며, 언제 갱신할지에 대한 복잡도가 추가된다.
- Redis나 Memcached를 추가하는 등 **애플리케이션 변경**이 필요하다.

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

**캐싱은 페이지 로드 시간을 개선하고 서버·데이터베이스 부하를 줄인다.** 요청이 이전에 있었는지 먼저 조회해 이전 결과를 반환함으로써 실제 실행을 절약한다. 또한 데이터베이스는 파티션 전반에 읽기·쓰기가 고르게 분산될 때 유리한데 **인기 항목이 분포를 치우치게 해 병목을 만들므로**, DB 앞의 캐시가 불균등한 부하와 트래픽 급증을 흡수한다.

**캐시 위치**는 클라이언트(OS·브라우저), CDN, 웹 서버(리버스 프록시·Varnish), 데이터베이스, 애플리케이션(Memcached·Redis)이 있다. 애플리케이션 캐시는 데이터가 RAM에 있어 디스크 기반 DB보다 훨씬 빠르지만 RAM이 제한적이므로 **LRU** 같은 알고리즘으로 차가운 항목을 밀어낸다.

**캐싱 수준**은 데이터베이스 쿼리와 객체 두 범주로 나뉜다. **쿼리 수준**은 쿼리를 해시해 키로 쓰지만, 복잡한 쿼리의 캐시를 지우기 어렵고 셀 하나가 바뀌면 그것을 포함할 수 있는 모든 캐시를 지워야 하는 만료 문제가 있다. **객체 수준**은 데이터를 객체로 보고 조립하며, 기반 데이터가 바뀌면 객체를 제거한다. 파일 기반 캐싱은 복제와 오토스케일링을 어렵게 하므로 피한다.

**갱신 전략**은 네 가지다.

- **Cache-aside(lazy loading)**: 애플리케이션이 읽기·쓰기를 책임진다. 캐시 미스 시 DB에서 읽어 캐시에 넣는다. 요청된 데이터만 캐싱되지만, **미스마다 3번의 왕복**이 필요하고 **데이터가 낡을 수 있으며**(TTL이나 write-through로 완화) 노드 장애 시 빈 노드가 되어 지연이 증가한다.
- **Write-through**: 애플리케이션이 캐시에 쓰면 캐시가 DB에 **동기적으로** 기록한다. 전체적으로 느리지만 후속 읽기가 빠르고 **데이터가 낡지 않는다.** 새 노드는 갱신 전까지 비어 있고, 쓴 데이터가 안 읽힐 수 있다.
- **Write-behind(write-back)**: DB에 **비동기로** 기록해 쓰기 성능을 높인다. 캐시가 죽으면 **데이터 유실** 위험이 있고 구현이 복잡하다.
- **Refresh-ahead**: 최근 접근된 항목을 **만료 전에 자동 갱신**한다. 예측이 정확하면 지연이 줄지만, 부정확하면 오히려 성능이 나빠진다.

**캐시의 단점**은 캐시와 진실의 원천 사이의 **일관성 유지(캐시 무효화)** 가 어렵다는 것, 언제 갱신할지에 대한 복잡도, 그리고 애플리케이션 변경이 필요하다는 점이다.

## 내가 정리한 내용

**1. 캐시를 쓰는 이유**

- **페이지 로드 시간 개선 + 서버와 DB 부하 감소**
- **인기 항목이 만드는 불균등한 부하를 앞에서 막아줌.** DB는 파티션 전반에 부하가 고르게 분산될 때 유리한데, 인기 항목이 분포를 치우치게 해 병목을 만든다. 캐시가 이 쏠림과 트래픽 급증을 흡수한다.

**2. 갱신 전략 4가지**

- **Cache-aside**: 요청된 데이터만 캐싱돼 낭비가 없음. 대신 **미스마다 3번 왕복**하고, DB가 갱신되면 **낡은 데이터**가 남는다(TTL이나 write-through로 완화). 노드가 죽으면 빈 노드로 교체되어 한동안 전부 미스 상태가 된다.
- **Write-through**: 쓸 때 캐시와 DB를 **동시에(동기)** 갱신해 **데이터가 항상 최신**이다. 대신 쓰기가 느리다. 사용자는 읽기보다 갱신 지연에 관대하므로 합리적인 거래다.
- **Write-behind**: DB에 **비동기로** 써 쓰기가 빠르다. 대신 캐시가 죽으면 **DB에 안 간 데이터가 사라진다.** 트랜잭션이 중요한 데이터에는 사용 금지.
- **Refresh-ahead**: 캐시 만료 직전에 미리 갱신한다. 예측이 맞으면 미스를 겪지 않지만 **틀리면 자원 낭비**다.

**3. 캐시의 위험**

- **캐시와 DB(진실의 원천) 사이의 일관성 유지가 어렵다.** 언제 갱신할지 결정하는 **캐시 무효화**의 복잡도가 추가된다.
- ⚠️ **캐시가 죽으면 시스템 전체가 죽을 수 있다.** 캐시가 막아주던 부하가 한꺼번에 DB로 몰려(**썬더링 허드**) 연쇄 장애로 이어진다. 캐시는 단순한 성능 개선 장치가 아니라 **시스템이 그 존재를 전제하는 구성요소**가 된다. 캐시 워밍, 요청 병합, 캐시 이중화로 대비한다.
- Redis나 Memcached 도입 등 **애플리케이션 변경**이 필요하다.

## 검토 결과

### 확인된 부분

- **갱신 전략 4가지를 장단점까지 빠짐없이 정리함.** 각 전략의 트레이드오프를 정확히 짚었고, Write-behind에 "트랜잭션 중요 데이터 사용 금지"라는 실무 판단까지 붙였다.
- 캐시를 쓰는 두 번째 이유(**불균등 부하 흡수**)를 놓치지 않았다. 원문의 핵심인데 자주 빠지는 부분.
- 실습 Q2(Write-behind의 위험)를 정확히 답하고 ACID의 지속성 위반과 연결.

### 보강 포인트

- ⚠️ **가장 큰 위험(썬더링 허드)이 초기 답변에서 누락 → 추가.** 원문이 나열한 단점 외에, 실무에서 가장 무서운 것은 **캐시 장애가 곧 전체 장애**가 된다는 점이다.
- **"Cache-aside는 읽기만 하니 DB는 문제없다"는 위험한 오해다.** (Q1 실습)

  ```text
  평소:      요청 10,000건 → 캐시가 9,500건 처리 → DB는 500건만  ✅
  캐시 죽음:  요청 10,000건 → 전부 미스 → DB로 10,000건 직행     💥
  ```

  **읽기만 하는 것이 문제다. 그 읽기가 한꺼번에 전부 몰려온다.** DB 부하가 순간적으로 20배가 된다.

  > **캐시는 속도를 높이는 장치일 뿐 아니라, DB를 가려주는 방패다.**

### 심화: 썬더링 허드(Thundering Herd) / 캐시 스탬피드

```text
캐시 노드 장애 → DB 과부하 → DB 장애 → 전체 서비스 다운
```

**연쇄 장애(cascading failure)** 의 전형이다. → [[2026-08-03-backend-application-layer]]

**노드 장애가 아니어도 발생한다.** 인기 있는 키 하나가 만료되는 순간, 그 키를 찾던 요청들이 **동시에 DB로 몰린다.**

**실무 대응**

| 방법 | 내용 |
|---|---|
| **캐시 워밍(pre-warming)** | 새 노드 투입 전에 **미리 데이터를 채워** 넣고 트래픽을 받게 함 |
| **점진적 교체** | 노드를 한 번에 갈지 않고 조금씩 |
| **요청 병합(single-flight)** | 같은 키에 대한 동시 미스를 **하나로 묶어** DB에 1번만 질의 |
| **TTL 지터** | 만료 시점에 랜덤을 섞어 동시 만료를 흩뜨림 |
| **캐시 이중화** | 캐시 자체를 여러 대로 → [[2026-07-25-backend-availability-patterns]] |

**요청 병합이 특히 영리하다.** 인기 키가 만료되어 동시에 1000개 요청이 미스가 나도, DB에는 **하나만 보내고 나머지는 그 결과를 기다리게** 한다.

### 캐시를 둘 수 있는 위치 — 요청은 다섯 층을 지난다

| 위치 | 예 |
|---|---|
| **클라이언트** | OS, 브라우저 |
| **CDN** | CDN 자체가 캐시의 한 종류 → [[2026-07-29-backend-content-delivery-network]] |
| **웹 서버** | 리버스 프록시, Varnish → [[2026-07-31-backend-reverse-proxy]] |
| **데이터베이스** | 기본 설정에 이미 포함 |
| **애플리케이션** | Redis, Memcached |

**어느 층에서 걸리든 뒤쪽은 일을 안 해도 된다.**

**애플리케이션 캐시**는 데이터가 RAM에 있어 디스크 기반 DB보다 훨씬 빠르지만 RAM이 제한적이라 **LRU(Least Recently Used)** 같은 알고리즘으로 '차가운' 항목을 밀어낸다. **Redis**는 영속성 옵션과 정렬 집합·리스트 같은 내장 자료구조를 추가로 제공한다.

### 무엇을 캐싱하나 — 쿼리 vs 객체

**쿼리 수준**: 쿼리를 해시해 키로 쓴다. 간단하지만 **만료가 치명적으로 어렵다.**

> **테이블 셀 하나가 바뀌면, 그 셀을 포함할 수 있는 모든 캐시 쿼리를 지워야 한다.** 어떤 쿼리가 그 셀을 포함하는지 알기 어렵다.

**객체 수준**: 데이터를 객체로 본다. `User` 객체를 캐싱하면 그 유저 데이터가 바뀔 때 **그 객체만 지우면** 된다. **무효화 범위가 명확**하다. 비동기 처리도 가능해진다(워커가 최신 캐시 객체를 소비).

→ **원문이 권하는 것은 객체 수준이다.**

**캐싱하기 좋은 것**: 사용자 세션, 완전히 렌더링된 웹 페이지, 활동 스트림, 사용자 그래프 데이터

⚠️ **파일 기반 캐싱은 피한다** — 복제와 오토스케일링이 어려워진다. → [[2026-07-30-backend-load-balancer]]의 무상태 원칙과 같은 이유.

### Write-through의 실무 요령

원문의 통찰: **"사용자는 읽기보다 갱신에서의 지연에 관대하다."**
*"저장 중..."* 은 기다려주지만 *"로딩 중..."* 은 못 참는다. **쓰기를 희생해 읽기를 얻는** 합리적 거래.

⚠️ 단점: 새 노드는 DB에서 갱신되기 전까지 비어 있고, **쓴 데이터 대부분이 안 읽힐 수 있다.** → **cache-aside와 함께 쓰는 것이 정석.**

### 이전 학습과의 연결

- **인기 항목의 쏠림을 캐시가 흡수한다** — 샤딩의 데이터 쏠림 문제를 앞에서 막아주는 것. 인기 있을수록 캐시 적중률이 높아져 정확히 문제 지점에서 잘 작동한다. → [[2026-08-05-backend-federation-sharding]]
- **stale 문제는 캐시가 있는 모든 곳에 따라온다** — CDN의 낡은 콘텐츠, DNS 전파 지연과 같은 뿌리. → [[2026-07-29-backend-content-delivery-network]], [[2026-07-28-backend-domain-name-system]]
- **Write-behind는 ACID의 지속성(Durability)을 위반한다.** "커밋되면 남는다"를 보장할 수 없다. → [[2026-08-04-backend-database-rdbms]]
- **Redis는 키-값 저장소**로 이미 배웠다. 캐시가 그 대표 용도. → [[2026-08-09-backend-nosql-types]]
