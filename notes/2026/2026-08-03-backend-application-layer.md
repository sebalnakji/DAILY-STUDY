## 질문

> **웹 계층과 애플리케이션 계층을 왜 분리하는가? 마이크로서비스란 무엇이며, 서비스 디스커버리는 왜 필요한가?**
>
> 원문: *Application layer / Microservices / Service Discovery*

## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

### 웹 계층과 애플리케이션 계층의 분리

- 웹 계층에서 **애플리케이션 계층(= 플랫폼 계층)** 을 분리하면 **두 계층을 독립적으로 확장·설정**할 수 있다.
- 예: 새 API(Application Programming Interface)를 추가하면 **애플리케이션 서버만 늘리면 되고**, 웹 서버는 늘릴 필요가 없다.
- **단일 책임 원칙(SRP, Single Responsibility Principle)** — 작고 자율적인 서비스들이 협력하는 구조를 지향한다.
- 작은 팀이 작은 서비스를 맡으면 **빠른 성장에 더 공격적으로 대응**할 수 있다.
- 애플리케이션 계층의 **워커(worker)** 는 **비동기 처리(asynchronism)** 를 가능하게 한다.

### 마이크로서비스(Microservices)

- **독립적으로 배포 가능한, 작고 모듈화된 서비스들의 모음.**
- 각 서비스는 **고유한 프로세스로 실행**되며, 잘 정의된 **경량 메커니즘**으로 통신해 하나의 비즈니스 목표를 수행한다.
- 예 (Pinterest): `user profile`, `follower`, `feed`, `search`, `photo upload` 등.

### 서비스 디스커버리(Service Discovery)

- 서비스가 **서로를 찾을 수 있게** 등록된 이름·주소·포트를 추적하는 시스템.
- 대표 도구: **Consul**, **Etcd**, **Zookeeper**.
- **헬스체크(health check)** 로 서비스 상태를 검증하며, 보통 HTTP(HyperText Transfer Protocol) 엔드포인트로 수행한다.
- Consul과 Etcd는 **키-값 저장소(key-value store)** 를 내장해 설정값이나 공유 데이터를 저장하는 데 쓸 수 있다.

### 왜 필요한가

마이크로서비스 환경에서는 서비스 인스턴스가 **수시로 늘고 줄고 IP가 바뀐다.** 주소를 코드에 하드코딩할 수 없으므로, **"이름으로 물어보면 현재 주소를 알려주는" 중앙 등록소**가 필요하다.

### 단점

- 느슨하게 결합된 서비스로 애플리케이션 계층을 추가하면, **아키텍처·운영·프로세스 관점에서 모놀리식과는 다른 접근**이 필요하다.
- 마이크로서비스는 **배포와 운영의 복잡도를 늘린다.**

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

**웹 계층에서 애플리케이션 계층(플랫폼 계층)을 분리하면 두 계층을 독립적으로 확장하고 설정할 수 있다.** 새 API를 추가할 때 웹 서버를 반드시 늘리지 않고도 애플리케이션 서버를 추가할 수 있다. **단일 책임 원칙**은 함께 동작하는 작고 자율적인 서비스를 지향한다. 작은 팀이 작은 서비스를 다루면 빠른 성장에 더 공격적으로 대비할 수 있다. 애플리케이션 계층의 **워커**는 비동기 처리를 가능하게 한다.

**마이크로서비스**는 독립적으로 배포 가능한 작고 모듈화된 서비스들의 모음이다. 각 서비스는 고유한 프로세스로 실행되며 잘 정의된 경량 메커니즘으로 통신해 비즈니스 목표를 수행한다. 예를 들어 Pinterest는 user profile, follower, feed, search, photo upload 같은 마이크로서비스를 가질 수 있다.

**서비스 디스커버리**는 Consul, Etcd, Zookeeper 같은 시스템으로, 등록된 이름·주소·포트를 추적해 서비스들이 서로를 찾도록 돕는다. 헬스체크로 서비스 무결성을 검증하며 보통 HTTP 엔드포인트를 사용한다. Consul과 Etcd는 설정값 등을 저장할 수 있는 키-값 저장소를 내장한다.

**단점**은 모놀리식과 다른 아키텍처·운영·프로세스 접근이 필요하다는 점과, 마이크로서비스가 배포·운영 복잡도를 늘린다는 점이다.

## 내가 정리한 내용

**1. 웹 계층과 애플리케이션 계층을 분리하는 이유**

두 계층을 **독립적으로 확장하고 설정**할 수 있기 때문이다. 분리하면 **병목이 있는 계층만** 확장하면 되지만, 분리하지 않으면 전부 확장해야 해서 **자원이 낭비**된다. 예를 들어 새 API(Application Programming Interface)를 추가할 때 애플리케이션 서버만 늘리고 웹 서버는 그대로 둘 수 있다.

**2. 마이크로서비스(Microservices)란?**

**독립적으로 배포 가능한, 작고 모듈화된 서비스들의 모음.** 각 서비스는 고유한 프로세스로 실행되며 경량 메커니즘으로 통신해 하나의 비즈니스 목표를 수행한다. (예: Pinterest의 user profile, follower, feed, search, photo upload)

본질적으로 **함수 호출을 네트워크 호출로 바꾸는 일**이다.

- **이점**: 서비스별 독립 배포가 가능해 작은 팀이 서로 기다리지 않고 빠르게 움직일 수 있다.
- **대가**: 배포·운영 복잡도가 늘고, 네트워크 호출에 따르는 부분 실패·타임아웃·분산 추적 문제를 떠안는다.

**3. 서비스 디스커버리(Service Discovery)가 왜 필요한가**

모놀리식에서는 함수로 호출하지만 마이크로서비스는 **네트워크로 호출**한다. 따라서 각 서비스를 호출할 때 **주소 정보가 필요**하다. 그런데 인스턴스가 늘고 줄거나 재배포되면서 **주소가 계속 변동**되므로, 그 정보를 모아두는 저장소가 필요하다. 그 역할을 하는 것이 서비스 디스커버리다(Consul, Etcd, Zookeeper). **헬스체크**로 서비스 상태도 함께 검증한다.

## 검토 결과

### 확인된 부분

- 계층 분리의 이유를 **"병목이 있는 계층만 확장 → 자원 낭비 방지"** 로 정확히 연결함.
- **서비스 디스커버리의 인과 사슬을 완전하게 구성함**: 함수 호출 → 네트워크 호출 → 주소 필요 → 주소 변동 → 저장소 필요 → 서비스 디스커버리. 이 항목은 보강할 것이 없다.
- 마이크로서비스의 정의를 정확히 서술하고, **"함수 호출을 네트워크 호출로 바꾸는 일"** 이라는 본질까지 담음.

### 보강 포인트

- **마이크로서비스는 이점과 대가를 함께 말해야 한다.** 초기 답변에는 정의와 메커니즘만 있고 "그래서 좋냐 나쁘냐"가 없었다. 면접에서 반드시 되묻는 주제.
  - **이점**: 독립 배포로 **작은 팀이 서로 기다리지 않는다.** 기술적 이유만큼 **조직적 이유**가 크다. 원문도 *"작은 팀이 작은 서비스를 맡으면 빠른 성장에 더 공격적으로 대응할 수 있다"* 고 서술.
  - **대가**: 원문의 경고는 *"개발이 어려워진다"* 가 아니라 **"배포와 운영의 복잡도가 는다"** 이다.
- **모놀리식에는 주소가 "있었는데 쉽게 알 수 있었던" 게 아니라 애초에 없었다.** (Q2 초기 답변 → 정밀화)
  ```java
  // 모놀리식 — 같은 프로세스 안
  User user = userProfileService.get(userId);   // 그냥 함수 호출
  ```
  네트워크도, 주소도, 포트도 없다. **찾을 대상 자체가 존재하지 않았다.**
  ```text
  // 마이크로서비스
  GET http://user-profile:8080/users/123        // 네트워크 호출
  ```

### 심화: 네트워크 호출이 되면서 딸려오는 것들

서비스 디스커버리는 시작일 뿐이다. **함수 호출이 네트워크 호출이 되면 네트워크의 모든 문제를 떠안는다.**

| 모놀리식 (함수 호출) | 마이크로서비스 (네트워크 호출) |
|---|---|
| 주소 불필요 | **서비스 디스커버리** 필요 |
| 실패 = 예외 하나 | **부분 실패**, 타임아웃, 재시도 |
| 즉시 반환 | **네트워크 지연** |
| 그냥 객체 전달 | 직렬화·역직렬화 비용 |
| 스택 트레이스로 추적 | **분산 추적** 필요 |

> **독립 배포를 얻는 대가로 네트워크의 복잡도를 산다.**

### 심화: 직렬 가용성이 여기서 돌아온다 ⚠️

요청 하나가 서비스 5개를 거치면:

```text
99.9%⁵ ≈ 99.5%
```

각각은 튼튼한데 **엮는 방식 때문에** 전체가 약해진다. 서비스를 잘게 쪼갤수록 **하나의 요청이 거치는 직렬 고리가 길어진다.** → [[2026-07-25-backend-availability-patterns]]

> **마이크로서비스는 조직의 독립성을 얻는 대신, 시스템의 신뢰성 예산을 쓴다.**

그래서 **회로 차단기(Circuit Breaker)**, **재시도**, **타임아웃**, **폴백**이 필수가 된다. 없으면 서비스 하나가 죽을 때 **연쇄 장애(cascading failure)** 로 전부 무너진다.

→ 이런 이유로 요즘은 **작게 시작해 필요할 때 쪼개라(Monolith First)** 는 조언이 정설에 가깝다.

### 이전 학습과의 연결

- **병목이 있는 곳만 늘린다** — 계층 분리의 근거는 확장성 논의와 같은 뿌리. → [[2026-07-20-backend-performance-vs-scalability]]

- **워커(worker)와 비동기 처리**: 애플리케이션 계층의 워커가 비동기 처리를 가능하게 한다. → 처리량을 얻는 대신 지연시간을 내주는 그 트레이드오프. [[2026-07-21-backend-latency-vs-throughput]]
