## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

### RDBMS(Relational Database Management System)

SQL 같은 관계형 데이터베이스는 **테이블로 조직된 데이터 항목의 집합**이다.

### ACID — 관계형 데이터베이스 트랜잭션의 속성

| 속성 | 뜻 | 설명 |
|---|---|---|
| **A** — Atomicity(원자성) | 전부 아니면 전무 | 각 트랜잭션은 **all or nothing** |
| **C** — Consistency(일관성) | 유효 상태 → 유효 상태 | 트랜잭션은 DB를 **유효한 상태에서 유효한 상태로** 옮긴다 |
| **I** — Isolation(격리성) | 동시 실행 = 순차 실행 | 트랜잭션을 **동시에 실행해도 순서대로 실행한 것과 같은 결과** |
| **D** — Durability(지속성) | 커밋되면 남는다 | 한 번 커밋된 트랜잭션은 **그대로 유지된다** |

> ⚠️ ACID의 **C(Consistency)** 와 CAP의 **C(Consistency)** 는 **다른 개념**이다. ACID의 C는 "제약조건을 위반하지 않는 유효한 상태", CAP의 C는 "모든 읽기가 최신 쓰기를 본다". → [[2026-07-22-backend-availability-vs-consistency]]

### 관계형 데이터베이스를 확장하는 6가지 기법

원문이 제시하는 목록이다.

1. **마스터-슬레이브 복제(master-slave replication)**
2. **마스터-마스터 복제(master-master replication)**
3. **페더레이션(federation)**
4. **샤딩(sharding)**
5. **비정규화(denormalization)**
6. **SQL 튜닝(SQL tuning)**

> 오늘은 1~2번(복제)까지. 3~6번은 다음 회차.

### 마스터-슬레이브 복제

- **마스터**가 읽기와 쓰기를 모두 처리하고, **쓰기를 하나 이상의 슬레이브로 복제**한다.
- **슬레이브는 읽기만** 담당한다.
- 슬레이브가 다시 다른 슬레이브로 복제하는 **트리 형태**도 가능하다.
- **마스터가 죽으면** 슬레이브가 마스터로 승격되거나 새 마스터가 준비될 때까지 **읽기 전용 모드로 계속 동작**할 수 있다.

**단점**

- 슬레이브를 마스터로 승격시키는 **추가 로직이 필요**하다.
- 복제 공통의 단점도 함께 적용된다.

### 마스터-마스터 복제

- **양쪽 마스터가 모두 읽기와 쓰기를 처리**하며, 쓰기에 대해 서로 조율한다.
- **한쪽 마스터가 죽어도 읽기와 쓰기를 모두 계속** 수행할 수 있다.

**단점**

- **어디에 쓸지 결정**하기 위해 로드밸런서가 필요하거나 애플리케이션 로직을 변경해야 한다.
- 대부분의 마스터-마스터 시스템은 **느슨한 일관성(ACID 위반)** 이거나, 동기화 때문에 **쓰기 지연시간이 증가**한다.

### 비교

| | 마스터-슬레이브 | 마스터-마스터 |
|---|---|---|
| 쓰기 | 마스터만 | **양쪽 모두** |
| 읽기 | 마스터 + 슬레이브 | 양쪽 모두 |
| 마스터 장애 시 | **읽기 전용**으로 버팀 | 읽기·쓰기 모두 지속 |
| 필요한 것 | 승격 로직 | **쓰기 라우팅** + 충돌 조율 |
| 대가 | 쓰기 확장 안 됨 | 일관성 저하 또는 쓰기 지연 |

> **핵심: 복제는 기본적으로 "읽기"를 확장한다. 쓰기 확장은 훨씬 어렵다.**

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

**SQL 같은 관계형 데이터베이스는 테이블로 조직된 데이터 항목의 집합**이다.

**ACID**는 관계형 데이터베이스 트랜잭션의 속성 집합이다.
- **원자성(Atomicity)**: 각 트랜잭션은 전부 아니면 전무다
- **일관성(Consistency)**: 모든 트랜잭션은 데이터베이스를 하나의 유효한 상태에서 다른 유효한 상태로 옮긴다
- **격리성(Isolation)**: 트랜잭션을 동시에 실행해도 순차적으로 실행한 것과 같은 결과를 낸다
- **지속성(Durability)**: 한 번 커밋된 트랜잭션은 그대로 유지된다

관계형 데이터베이스를 확장하는 기법으로는 **마스터-슬레이브 복제, 마스터-마스터 복제, 페더레이션, 샤딩, 비정규화, SQL 튜닝**이 있다.

**마스터-슬레이브 복제**에서는 마스터가 읽기와 쓰기를 처리하고 쓰기를 하나 이상의 슬레이브에 복제하며, 슬레이브는 읽기만 담당한다. 슬레이브는 트리 형태로 다시 복제할 수도 있다. 마스터가 오프라인이 되면 슬레이브가 마스터로 승격되거나 새 마스터가 준비될 때까지 시스템은 읽기 전용 모드로 동작할 수 있다. **단점**은 슬레이브를 마스터로 승격시키는 추가 로직이 필요하다는 점이다.

**마스터-마스터 복제**에서는 두 마스터가 모두 읽기와 쓰기를 처리하며 쓰기에 대해 서로 조율한다. 어느 한쪽이 다운되어도 읽기와 쓰기를 계속할 수 있다. **단점**은 어디에 쓸지 결정하기 위해 로드밸런서나 애플리케이션 로직 변경이 필요하다는 점, 그리고 대부분의 마스터-마스터 시스템이 느슨한 일관성(ACID 위반)을 갖거나 동기화로 인해 쓰기 지연시간이 증가한다는 점이다.

## 내가 정리한 내용

**1. ACID란?**

관계형 데이터베이스 **트랜잭션**이 지키는 4가지 속성이다.

- **Atomicity(원자성)** — 트랜잭션은 **전부 되거나 전부 안 되거나**. 이체에서 출금만 되고 입금이 실패하면 안 된다.
- **Consistency(일관성)** — 트랜잭션은 DB를 **유효한 상태에서 유효한 상태로** 옮긴다. 잔액이 음수가 되는 등 제약을 깨지 않는다.
- **Isolation(격리성)** — 여러 트랜잭션을 **동시에 실행해도 순차 실행한 것과 같은 결과**가 나온다.
- **Durability(지속성)** — 한 번 **커밋되면 유지된다.** 직후 서버가 죽어도 남아 있다.

※ ACID의 C와 CAP의 C는 **다른 개념**이다. ACID의 C는 "제약조건을 안 깨는 유효한 상태", CAP의 C는 "모든 읽기가 최신 쓰기를 봄"이다.

**2. 마스터-슬레이브 vs 마스터-마스터**

- **마스터-슬레이브**: 마스터가 읽기·쓰기를 모두 가지고, 슬레이브는 읽기만 담당한다. 마스터 장애 시 **읽기는 지속**할 수 있다(읽기 전용 모드). 단, 슬레이브를 마스터로 승격시키는 로직이 필요하다.
- **마스터-마스터**: 둘 다 읽기·쓰기를 담당하며, 한쪽 장애 시 **읽기와 쓰기 모두 지속**된다. 단, 어디에 쓸지 정하는 라우팅이 필요하고, 충돌 때문에 **일관성이 느슨해지거나 쓰기 지연이 증가**한다.

**3. 복제로 확장되는 것과 안 되는 것**

- **확장되는 것: 읽기.** 슬레이브를 늘리면 읽기 처리량이 비례해 늘어난다. 읽기는 데이터를 바꾸지 않으므로 어느 복사본에서 읽어도 되기 때문이다.
- **확장되지 않는 것: 쓰기.** 복제는 데이터를 **나누는 게 아니라 복사**하므로, 마스터를 늘려도 각 노드가 결국 전체 쓰기를 모두 수행해야 한다. 창구만 늘고 처리량은 그대로다.
- 쓰기를 확장하려면 데이터를 **나누는** 방식, 즉 **샤딩(Sharding)** 이 필요하다.

## 검토 결과

### 확인된 부분

- 마스터-슬레이브와 마스터-마스터의 **권한 구조와 장애 시 동작**을 정확히 구분함.
- 실습 Q1에서 "쓰기는 마스터만 가능 → 앱 서버를 늘려도 처리는 한 곳" 을 정확히 진단.
- 실습 Q2에서 마스터-마스터의 대가(라우팅 로직, 충돌, 동기화 지연, 일관성 저하)를 빠짐없이 나열하고, **"성능 개선 안 됨"** 이라는 결론을 직관적으로 맞힘.

### 보강 포인트

- **ACID는 이름 나열이 아니라 한 줄씩 설명해야 한다.** 초기 답변은 4개 명칭만 제시 → 면접관은 반드시 "각각 뭔가요?"를 되묻는다. **약자 확장은 아는 것의 증거가 아니다.**
- **"복제로 확장되는 것"의 답은 읽기 vs 쓰기다.** (Q3 초기 답변은 마스터-마스터의 대가만 서술)
  - **읽기는 진짜로 확장된다.** 슬레이브 3대 → 읽기 처리량 약 3배. **자원을 늘린 만큼 비례해서 증가**하므로 확장성의 정의를 충족한다. 읽기는 데이터를 바꾸지 않아 복사본 아무 데서나 읽어도 되고, 서로 조율할 필요가 없기 때문. → [[2026-07-20-backend-performance-vs-scalability]]
  - 실무에서 읽기:쓰기 비율이 보통 10:1 이상이라 복제만으로도 효과가 크다. 그래도 **쓰기 병목은 남는다.**

### 심화: 왜 마스터-마스터로도 쓰기가 2배가 안 되나

```text
마스터 A가 하는 일 = 자기가 받은 쓰기 + 마스터 B에서 복제해온 쓰기
마스터 B가 하는 일 = 자기가 받은 쓰기 + 마스터 A에서 복제해온 쓰기
                     └────────── 결국 둘 다 전체 쓰기량 ──────────┘
```

**받는 창구만 둘로 늘었지, 각자가 처리하는 총량은 그대로다.** 쓰기 1000건이 들어오면 A도 1000건, B도 1000건을 디스크에 쓴다. 데이터가 양쪽에 똑같이 있어야 하기 때문.

> **복제는 데이터를 나누지 않고 복사한다. 그래서 쓰기 부담이 줄지 않는다.**

**그럼 마스터-마스터는 왜 쓰나?** 쓰기 확장이 아니라 **가용성** 때문이다. 마스터-슬레이브는 마스터가 죽으면 쓰기가 멈추지만, 마스터-마스터는 계속 받을 수 있다. **목적이 다르다.**

### 심화: 실무 충돌 사례 — auto_increment ID

```text
같은 순간
  마스터 A: 게시글 저장 → id = 101 부여
  마스터 B: 게시글 저장 → id = 101 부여   ← 서로 모름!
                ↓ 복제 시도
             💥 충돌
```

`auto_increment` ID가 양쪽에서 독립적으로 증가해 **같은 번호를 발급**한다. 실무에선 A는 홀수, B는 짝수를 쓰게 하거나 UUID(Universally Unique Identifier)를 쓴다. **쪼개면 반드시 조율 비용이 생긴다.**

### 다음 회차 예고: 복제 vs 샤딩

```text
복제(Replication):  같은 데이터를 여러 곳에    → 읽기 확장
샤딩(Sharding):     다른 데이터를 여러 곳에    → 쓰기 확장
```

사용자 1~100만은 DB1, 100만~200만은 DB2로 나누면 **각 DB는 절반의 쓰기만** 처리한다. 이것이 쓰기 확장의 근본책.

### 이전 학습과의 연결

- **"병목은 항상 공유 자원"** — 앱 서버는 무한히 늘려도 쓰기를 받는 마스터는 한 대. 지금까지 반복해서 "DB 마스터가 1순위 용의자"였던 이유가 여기서 드러난다. → [[2026-07-20-backend-performance-vs-scalability]]
- **마스터-마스터는 사실상 AP를 선택한 구조.** 느슨한 일관성을 받아들이거나(AP), 동기화로 쓰기 지연을 감수한다(CP 쪽). → [[2026-07-22-backend-availability-vs-consistency]]
- **마스터-슬레이브 = Active-Passive, 마스터-마스터 = Active-Active** 와 같은 구조. 가용성 패턴에서 배운 개념이 DB 계층에서 반복된다. → [[2026-07-25-backend-availability-patterns]]
- **읽기 전용 모드로 버티기**도 가용성 설계의 일종. 완전 정지보다 부분 동작이 낫다.
