## 질문

> **로드밸런서는 무엇을 하는가? Layer 4와 Layer 7 로드밸런싱의 차이는? 수평 확장과는 어떤 관계인가?**
>
> 원문: *Load balancer*

## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

### 역할

들어오는 클라이언트 요청을 애플리케이션 서버나 데이터베이스 같은 **컴퓨팅 자원에 분배**하고, 그 응답을 해당 클라이언트에게 돌려준다. 효과는 세 가지다.

1. **비정상(unhealthy) 서버로 요청이 가지 않게 막는다** — 헬스체크
2. **자원 과부하를 방지한다**
3. **단일 장애점(SPOF, Single Point Of Failure) 제거를 돕는다**

- 구현: 하드웨어(비쌈) 또는 소프트웨어(HAProxy 등).

### 부가 기능

- **SSL(Secure Sockets Layer) termination**: 들어오는 요청을 복호화하고 응답을 암호화해, **백엔드 서버가 비싼 암복호화 작업을 하지 않게** 한다. 서버마다 X.509 인증서를 설치할 필요도 없어진다.
- **세션 유지(Session persistence)**: 앱이 세션을 추적하지 않는 경우, 쿠키를 발급해 **특정 클라이언트의 요청을 항상 같은 인스턴스로** 보낸다.

### 로드밸런서 자체의 이중화

로드밸런서 자체가 죽으면 전체가 죽으므로, **Active-Passive 또는 Active-Active**로 여러 대를 둔다. → [[2026-07-25-backend-availability-patterns]]

### 분배 기준(알고리즘)

- Random(무작위)
- Least loaded(부하가 가장 적은 서버)
- Session / cookies
- Round robin 또는 Weighted round robin
- Layer 4 / Layer 7

### Layer 4 vs Layer 7

| | Layer 4 | Layer 7 |
|---|---|---|
| 보는 계층 | **전송 계층(transport)** | **애플리케이션 계층(application)** |
| 판단 근거 | 출발지·목적지 **IP(Internet Protocol) 주소와 포트** (헤더). **패킷 내용은 안 봄** | 헤더, 메시지 **본문**, 쿠키 등 내용 |
| 동작 | 패킷을 상위 서버로 전달하며 **NAT(Network Address Translation)** 수행 | 트래픽을 **종료(terminate)** 하고 메시지를 읽은 뒤, 결정하고 선택된 서버로 새 연결을 연다 |
| 장점 | **시간·자원 소모가 적다** | **유연하다** (내용 기반 라우팅) |
| 예시 | — | 영상 트래픽은 영상 서버로, 민감한 결제 트래픽은 보안 강화 서버로 |

> **유연성을 대가로, Layer 4는 Layer 7보다 적은 시간과 컴퓨팅 자원을 쓴다.** 다만 현대 범용 하드웨어에서는 성능 차이가 미미할 수 있다.

### 수평 확장(Horizontal scaling)

- 로드밸런서는 **수평 확장**을 도와 성능과 가용성을 함께 높인다.
- **수평 확장(scale out)**: 범용(commodity) 장비를 여러 대로 늘림 → **비용 효율적이고 가용성이 높다.** 인력 채용도 쉽다.
- **수직 확장(scale up, Vertical Scaling)**: 한 대를 더 비싼 하드웨어로 키움.

**수평 확장의 단점**

- 복잡도가 늘고 서버 복제가 필요하다.
  - 서버는 **무상태(stateless)** 여야 한다 — 세션이나 프로필 사진 같은 사용자 데이터를 서버가 들고 있으면 안 된다.
  - 세션은 중앙 저장소(SQL/NoSQL 데이터베이스)나 영속 캐시(Redis, Memcached)에 둔다.
- 상위 서버가 늘어나면 하위의 캐시·데이터베이스가 **더 많은 동시 연결**을 감당해야 한다.

### 로드밸런서의 단점

- 자원이 부족하거나 설정이 잘못되면 **로드밸런서 자체가 성능 병목**이 된다.
- 단일 장애점을 없애려고 도입했지만 **복잡도가 증가**한다.
- **로드밸런서 한 대는 그 자체로 단일 장애점**이며, 여러 대로 구성하면 복잡도가 더 늘어난다.

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

**로드밸런서는 들어오는 클라이언트 요청을 애플리케이션 서버·데이터베이스 같은 컴퓨팅 자원에 분배**하고 그 응답을 클라이언트에게 반환한다. 비정상 서버로 요청이 가는 것을 막고, 자원 과부하를 방지하며, 단일 장애점 제거를 돕는다. 하드웨어(비쌈) 또는 HAProxy 같은 소프트웨어로 구현한다.

부가적으로 **SSL termination**(백엔드가 암복호화를 하지 않도록)과 **세션 유지**(쿠키로 같은 인스턴스에 고정) 기능을 제공한다. 로드밸런서 자체의 장애에 대비해 active-passive 또는 active-active로 여러 대를 둔다.

**Layer 4**는 전송 계층 정보(출발지·목적지 IP와 포트)를 보고 분배하며 패킷 내용은 보지 않고, NAT를 수행해 패킷을 전달한다. **Layer 7**은 애플리케이션 계층(헤더·메시지·쿠키)을 보고 분배한다. 트래픽을 종료하고 메시지를 읽은 뒤 선택된 서버로 연결을 연다. 예를 들어 영상 트래픽은 영상 서버로, 민감한 결제 트래픽은 보안 강화 서버로 보낼 수 있다. **유연성을 대가로 Layer 4가 자원을 덜 쓴다.**

**수평 확장**에서 범용 장비로 확장하는 것(scale out)은 한 대를 비싼 하드웨어로 키우는 **수직 확장**(scale up)보다 비용 효율적이고 가용성이 높다. 단, 서버는 무상태여야 하며 세션은 중앙 저장소나 영속 캐시에 두어야 한다.

**단점**으로는 로드밸런서 자체가 병목이 될 수 있고, 복잡도가 증가하며, 한 대만 두면 그 자체가 단일 장애점이 된다.

## 내가 정리한 내용

**1. 로드밸런서(Load Balancer)는 무엇을 하는가**

들어오는 클라이언트 요청을 **애플리케이션 서버·데이터베이스 등에 분배**하고, 그 응답을 해당 클라이언트에게 반환한다. 그 결과로 다음 효과가 있다.

- 헬스체크로 **비정상 서버에 요청이 가지 않게 막는다**
- **자원 과부하를 방지**한다
- **단일 장애점(SPOF, Single Point Of Failure) 제거**를 돕는다

부가적으로 **SSL(Secure Sockets Layer) termination**(백엔드가 암복호화를 하지 않도록 대신 처리, 서버별 인증서 설치 불필요)과 **세션 유지**(쿠키로 같은 인스턴스에 고정) 기능을 제공한다.

**2. Layer 4 vs Layer 7**

- **Layer 4**: IP(Internet Protocol) 주소 + 포트(헤더)만 확인한다. 내용을 보지 않으므로 경로 기반 분배는 불가능하지만, **빠르고 자원을 덜 쓴다.**
- **Layer 7**: 헤더 + 본문 + 쿠키까지 확인한다. 그래서 **내용 기반 라우팅**이 가능하다(`/video/*`는 영상 서버, `/billing/*`은 보안 서버). 대신 연결을 종료하고 다시 열어야 해 더 무겁다.
- 즉 **유연성의 대가로 Layer 4가 자원을 덜 쓴다.**

**3. 수평 확장(Scale Out)의 전제 조건**

서버가 **무상태(stateless)** 여야 한다. 수평 확장을 하려면 서버에 데이터를 저장하지 않고, **서버 밖 별도 저장소**(데이터베이스, Redis 같은 영속 캐시)에 저장해 관리해야 한다. 그렇지 않으면 요청이 다른 서버로 갈 때 세션이 유실된다.

## 검토 결과

### 확인된 부분

- 로드밸런서의 세 가지 효과를 정확히 나열함.
- Layer 4 / Layer 7이 각각 **무엇을 보는지** 정확히 구분함.
- **수평 확장의 전제 조건(무상태)** 을 완벽하게 서술함. 원인(서버가 데이터를 들고 있으면 안 됨)과 해법(서버 밖 저장소)을 모두 담았다. 이 항목은 보강할 것이 없다.
- 실습 Q1에서 로그아웃 원인을 **"서버가 로그인 정보를 갖고 있어서"** 로 정확히 진단하고, 근본 해법(중앙 저장소)을 제시.
- 실습 Q2에서 Layer 4로 경로 기반 분배가 불가능한 이유를 정확히 설명.

### 보강 포인트

- **정의가 빠지면 답이 닫히지 않는다.** 초기 답변은 효과 세 개만 나열 → "그래서 로드밸런서가 뭐 하는 건가요?"를 되묻게 된다. **정의(요청을 여러 서버에 분배) → 효과** 순서로 말할 것.
- **Layer 4/7은 "무엇을 보는지" 다음에 "그래서 뭐가 되는지"를 붙일 것.**

  | | Layer 4 | Layer 7 |
  |---|---|---|
  | 보는 것 | IP + 포트 (헤더) | 헤더 + 본문 + 쿠키 |
  | **그래서** | 내용을 못 봄 → **경로 기반 분배 불가** | **내용 기반 라우팅 가능** |
  | **대가** | **빠르고 자원 절약** | 무겁다(연결 종료 후 재연결) |

  - 비유: Layer 4는 **주소만 보고 배달하는 택배기사**, Layer 7은 **내용을 열어보고 분류하는 물류센터**.
  - Layer 4가 `/video/*`를 못 보는 근본 이유: **URL(Uniform Resource Locator) 경로는 HTTP 메시지 안에 있다.** Layer 4는 봉투(IP·포트)만 보고 편지를 뜯지 않는다.
  - 현대 하드웨어에서는 성능 차이가 미미할 수 있어 **실무는 대개 Layer 7**을 쓴다.
- **"하나의 서버만 사용"은 해결이 아니라 후퇴다.** (Q1 초기 답변) 로드밸런서를 도입한 목적(수평 확장) 자체를 버리는 것.

  | | 서버 1대로 | Sticky Session | 중앙 저장소 |
  |---|---|---|---|
  | 서버 대수 | 1대 | 3대 유지 | 3대 유지 |
  | 방식 | 확장 **포기** | 사용자별 **같은 서버 고정** | 세션을 서버 밖으로 |
  | 평가 | ❌ 해결 아님 | ⚠️ **차선책** | ✅ **근본책** |

- **Sticky Session이 차선책인 이유 (두 약점)**
  1. 그 서버가 죽으면 **세션이 통째로 유실** → 해당 사용자 전부 로그아웃
  2. **부하가 고르게 분산되지 않음** → 특정 서버에 헤비 유저가 몰릴 수 있음
  - → 원칙: **서버를 무상태로 만들고 상태는 서버 밖에 둔다.**

### 수평 확장 vs 수직 확장

| | 수평 확장(Scale Out) | 수직 확장(Scale Up) |
|---|---|---|
| 방법 | 값싼 범용 장비를 **여러 대** | 한 대를 **더 비싼 하드웨어로** |
| 비용 | 효율적 | 급격히 비싸짐 |
| 가용성 | **높음** (한 대 죽어도 생존) | 낮음 (그 한 대가 SPOF) |
| 한계 | 사실상 무제한 | **물리적 상한 존재** |

원문의 추가 포인트: **범용 하드웨어 인력이 채용하기 쉽다.** 특수 엔터프라이즈 장비 전문가는 구하기 어렵다.

**수평 확장의 또 다른 대가**: 상위 서버가 늘어나면 하위의 캐시·데이터베이스가 **더 많은 동시 연결**을 감당해야 한다. 앱 서버를 10대로 늘려도 데이터베이스가 한 대면 거기서 병목이 생긴다. → [[2026-07-20-backend-performance-vs-scalability]]

### 로드밸런서의 단점 — 그리고 아이러니

- 자원이 부족하거나 설정이 잘못되면 **로드밸런서 자체가 성능 병목**이 된다.
- 단일 장애점을 없애려 도입했지만 **복잡도가 증가**한다.
- ⚠️ **로드밸런서 한 대는 그 자체로 단일 장애점이다.** 여러 대로 구성하면 복잡도가 더 늘어난다.

> **단일 장애점을 없애려고 넣은 장치가 새로운 단일 장애점이 된다.**

그래서 로드밸런서도 **Active-Passive / Active-Active**로 이중화한다. DNS와 마찬가지로 **모든 요청이 반드시 거치는 직렬 고리**이기 때문. → [[2026-07-25-backend-availability-patterns]], [[2026-07-28-backend-domain-name-system]]

### 이전 학습과의 연결

- **Fail-over와의 차이**: Active-Passive는 heartbeat로 감지해 **수동적으로 갈아타지만**, 로드밸런서는 여러 서버를 **상시 헬스체크하며 능동적으로 골라낸다.** → [[2026-07-25-backend-availability-patterns]]
- 로드밸런서는 **처리량(Throughput)과 가용성을 함께** 끌어올리는 장치. → [[2026-07-21-backend-latency-vs-throughput]]
