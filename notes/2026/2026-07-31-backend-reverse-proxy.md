# 리버스 프록시(Reverse Proxy)란 무엇이며, 로드밸런서와 어떻게 다른가?

## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

### 정의

**내부 서비스들을 한곳에 모아(centralize), 외부에는 통일된 인터페이스를 제공하는 웹 서버.**

클라이언트 요청을 처리 가능한 서버로 **전달(forward)** 하고, 그 서버의 응답을 다시 클라이언트에게 반환한다.

```text
클라이언트  →  [리버스 프록시]  →  내부 서버들
              (외부에 노출되는 유일한 얼굴)
```

### 이점

- **보안 강화(Increased security)**
  - 백엔드 서버 정보를 **숨긴다**
  - IP(Internet Protocol) 블랙리스트
  - 클라이언트별 연결 수 제한
- **확장성·유연성 증가(Increased scalability and flexibility)**
  - 클라이언트는 **리버스 프록시의 IP만** 본다 → 뒤쪽 서버를 늘리거나 설정을 바꿔도 클라이언트는 모른다
- **SSL(Secure Sockets Layer) termination**
  - 들어오는 요청을 복호화하고 응답을 암호화 → **백엔드가 비싼 암복호화를 하지 않아도 된다**
  - 서버마다 X.509 인증서를 설치할 필요가 없어진다
- **압축(Compression)** — 서버 응답을 압축
- **캐싱(Caching)** — 캐시된 요청은 프록시가 바로 응답
- **정적 콘텐츠 직접 서빙** — HTML/CSS/JS, 사진, 동영상 등

### 로드밸런서(Load Balancer)와의 차이

| | 로드밸런서 | 리버스 프록시 |
|---|---|---|
| 존재 이유 | **서버가 여러 대**일 때 트래픽을 나눔 | **서버가 한 대여도** 이점이 있음 |
| 주 역할 | **분배**(같은 기능의 서버 묶음에 라우팅) | **대표 창구**(내부를 감추고 통일된 인터페이스 제공) |
| 없으면 | 서버 한 대에 부하 집중 | 백엔드가 직접 노출됨 |

- 로드밸런서는 **여러 서버가 있을 때** 유용하며, 보통 **같은 기능을 하는 서버 집합**으로 트래픽을 라우팅한다.
- 리버스 프록시는 **웹 서버·앱 서버가 한 대뿐이어도** 위의 이점들을 제공한다.
- **NGINX, HAProxy 같은 솔루션은 Layer 7 리버스 프록시와 로드밸런싱을 모두 지원한다.** → 실무에서 둘이 같은 소프트웨어로 구현되어 경계가 흐릿하게 느껴지는 이유.

### 단점

- 리버스 프록시 도입으로 **복잡도가 증가**한다.
- **리버스 프록시 한 대는 단일 장애점(SPOF, Single Point Of Failure)** 이며, 여러 대로 구성(failover)하면 복잡도가 더 늘어난다. → [[2026-07-30-backend-load-balancer]]의 아이러니와 동일.

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

**리버스 프록시는 내부 서비스를 중앙화하고 외부에 통일된 인터페이스를 제공하는 웹 서버**다. 클라이언트의 요청은 이를 처리할 수 있는 서버로 전달되고, 리버스 프록시가 그 응답을 클라이언트에게 반환한다.

추가 이점은 다음과 같다.
- **보안 강화**: 백엔드 서버 정보 은닉, IP 블랙리스트, 클라이언트별 연결 수 제한
- **확장성·유연성 증가**: 클라이언트는 리버스 프록시의 IP만 보므로, 서버를 확장하거나 설정을 바꿀 수 있다
- **SSL termination**: 백엔드가 암복호화를 수행하지 않아도 되며, 서버마다 인증서를 설치할 필요가 없다
- **압축**, **캐싱**, **정적 콘텐츠 직접 서빙**

**로드밸런서와의 차이**
- 로드밸런서는 **서버가 여러 대일 때** 유용하며, 보통 같은 기능을 하는 서버 집합으로 트래픽을 라우팅한다.
- 리버스 프록시는 **웹/앱 서버가 한 대뿐일 때도** 위의 이점들을 제공한다.
- NGINX와 HAProxy 같은 솔루션은 Layer 7 리버스 프록시와 로드밸런싱을 **모두 지원**한다.

**단점**은 복잡도 증가와, 리버스 프록시 한 대가 단일 장애점이 된다는 점이다.

## 내가 정리한 내용

**1. 리버스 프록시(Reverse Proxy)란?**

내부 서비스들을 한곳에 모아 외부에는 통일된 인터페이스를 제공하는 웹 서버. 클라이언트 요청을 처리 가능한 서버로 전달하고 그 응답을 반환한다.

이점으로는 **백엔드 정보 은닉 등 보안**(IP 블랙리스트, 클라이언트별 연결 수 제한), **SSL(Secure Sockets Layer) termination**(백엔드 대신 암복호화를 처리해 서버 부담을 덜고, 서버마다 인증서를 설치할 필요가 없음), **캐싱**, **압축**, **정적 콘텐츠 직접 서빙** 등이 있다.

또한 클라이언트는 리버스 프록시의 IP(Internet Protocol)만 보므로, **뒤쪽 서버를 늘리거나 설정을 바꿔도 클라이언트는 영향을 받지 않는다.**

**2. 로드밸런서(Load Balancer)와의 차이**

로드밸런서는 **서버가 여러 대일 때** 요청을 분배하는 역할이지만, 리버스 프록시는 **서버가 한 대여도** 보안·캐싱·SSL termination·정적 콘텐츠 서빙 등 많은 역할을 한다.

또한 **로드밸런싱은 리버스 프록시가 제공하는 기능 중 하나로 포함 관계**다. 그래서 NGINX나 HAProxy 같은 솔루션은 둘을 모두 지원한다.

## 검토 결과

### 확인된 부분

- 정의를 정확히 서술하고, **정의 → 이점** 순서로 구성함. (어제 지적된 "정의 생략" 패턴이 교정됨)
- 실습 Q1에서 판단 근거를 **"분배할 서버가 없어 무의미"** 로 제시. 원문의 판별 기준과 정확히 일치.
- 실습 Q2에서 **"구현은 겹치지만 개념이 다르다"** 를 정확히 짚고, **포함 관계**까지 스스로 정리함.

### 보강 포인트

- **"SSL 지원" → "SSL termination"** 으로 용어 정밀화. "지원"은 모호하며, 정확히는 **백엔드 대신 암복호화를 처리해 앱 서버의 부담을 더는 것**이다.
- **포함되는 것은 장치가 아니라 기능이다.** `리버스 프록시 ⊃ 로드밸런싱`. 로드밸런서(장치)가 아니라 로드밸런싱(기능)이 리버스 프록시의 기능 중 하나.
- **Q1에서 이점을 두세 개 나열하면 더 강해진다.** 서버 1대에서도 살아있는 이점:

  | 이점 | 서버 1대에서도 유효? |
  |---|---|
  | 보안(백엔드 은닉, IP 차단) | ✅ |
  | SSL termination | ✅ 앱 서버가 암복호화 부담 없음 |
  | **캐싱** | ✅ 반복 요청을 앱까지 안 보냄 |
  | **정적 콘텐츠 직접 서빙** | ✅ 이미지·JS를 앱 서버가 처리 안 함 |
  | 압축 | ✅ |

  특히 **캐싱과 정적 서빙**은 서버가 1대일 때 오히려 효과가 크다. 그 1대가 유일한 자원이므로 **앱까지 도달하는 요청을 줄이는 것**이 곧 생존이다.

### 핵심 판별법

> **"서버가 한 대뿐이어도 쓸 이유가 있는가?"**

- **로드밸런서** — 서버 1대면 나눌 게 없으므로 **무의미**
- **리버스 프록시** — 서버 1대여도 보안·캐싱·SSL·압축 이점이 **그대로 유효**

### 왜 헷갈리는가 — 개념은 다르지만 구현이 겹친다

**NGINX와 HAProxy는 Layer 7 리버스 프록시와 로드밸런싱을 모두 지원한다.** 실무에서 NGINX 하나를 띄우면 두 역할을 동시에 하므로 경계가 흐릿하게 느껴진다.

**구분하는 실익**: "지금 내가 무슨 문제를 푸는지"가 명확해진다.

- **부하가 문제다** → 로드밸런서 관점 → *서버를 늘려야 하나?*
- **노출·보안·성능이 문제다** → 리버스 프록시 관점 → *서버는 그대로 두고 앞단에서 해결*

같은 NGINX를 띄워도 **왜 띄우는지가 다르면 설정도 다음 단계도 달라진다.** 서버가 1대인데 "로드밸런서를 도입하자"는 문제를 잘못 짚은 것.

### Forward Proxy와의 대비 ("Reverse"가 붙은 이유)

| | Forward Proxy | Reverse Proxy |
|---|---|---|
| 누구 앞에 서나 | **클라이언트** 쪽 | **서버** 쪽 |
| 누구를 숨기나 | 클라이언트를 숨김 | **서버를 숨김** |
| 예시 | 회사 방화벽, VPN(Virtual Private Network) | NGINX, CloudFront |

> **Forward는 "누가 요청했는지"를 감추고, Reverse는 "누가 응답하는지"를 감춘다.**

### 단점 — 반복되는 아이러니

- 복잡도 증가
- ⚠️ **리버스 프록시 한 대는 그 자체로 단일 장애점(SPOF, Single Point Of Failure)** 이며, 이중화(failover)하면 복잡도가 더 늘어난다.

DNS(Domain Name System), 로드밸런서, 리버스 프록시 — **셋 다 모든 요청이 반드시 거치는 직렬 고리**라 같은 운명이다. → [[2026-07-28-backend-domain-name-system]], [[2026-07-30-backend-load-balancer]]

### 이전 학습과의 연결

- **SSL termination과 정적 콘텐츠 서빙**은 로드밸런서에서도 등장했던 기능. 실제로 두 개념의 구현이 겹치는 지점. → [[2026-07-30-backend-load-balancer]]
- **캐싱·정적 콘텐츠 서빙**은 CDN(Content Delivery Network)과 역할이 유사하다. 차이는 위치 — CDN은 **전 세계에 분산**되어 사용자 가까이에, 리버스 프록시는 보통 **원본 서버 앞단**에 있다. → [[2026-07-29-backend-content-delivery-network]]
