## 질문

> **RPC와 REST는 각각 무엇이며 어떻게 다른가? 각각의 단점은?**
>
> 원문: *Remote procedure call (RPC) / Representational state transfer (REST)*

## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

### RPC (Remote Procedure Call)

**클라이언트가 다른 주소 공간(보통 원격 서버)에서 프로시저를 실행시키는 방식.**

- 프로시저는 **로컬 호출인 것처럼 작성**되며, 서버와 통신하는 세부 사항이 클라이언트 프로그램에서 **추상화**된다.
- ⚠️ **원격 호출은 로컬 호출보다 느리고 신뢰성이 낮으므로, RPC 호출과 로컬 호출을 구분하는 것이 도움이 된다.**
- 대표 프레임워크: **Protobuf, Thrift, Avro**

**요청-응답 프로토콜의 흐름**

```text
① 클라이언트 프로그램 → 클라이언트 스텁 프로시저 호출 (로컬 호출처럼 스택에 인자를 쌓음)
② 클라이언트 스텁     → 프로시저 id와 인자를 요청 메시지로 마샬링(패킹)
③ 클라이언트 통신 모듈 → OS가 메시지를 서버로 전송
④ 서버 통신 모듈      → OS가 들어온 패킷을 서버 스텁으로 전달
⑤ 서버 스텁          → 언마샬링 후, id에 맞는 서버 프로시저를 인자와 함께 호출
⑥ 서버 응답은 위 과정을 역순으로 반복
```

**호출 예시**

```text
GET /someoperation?data=anId

POST /anotheroperation
{
  "data": "anId",
  "anotherdata": "another value"
}
```

> **RPC는 "행위(behavior)"를 노출하는 데 집중한다.** 성능상의 이유로 **내부 통신**에 자주 쓰이며, 용도에 맞게 네이티브 호출을 직접 만들 수 있다.

**네이티브 라이브러리(SDK)를 선택할 때**
- **대상 플랫폼을 알고 있을 때**
- **"로직"에 어떻게 접근할지 통제하고 싶을 때**
- 라이브러리 밖에서 **오류 처리가 어떻게 일어날지 통제**하고 싶을 때
- **성능과 최종 사용자 경험이 주된 관심사**일 때

**REST를 따르는 HTTP API는 공개 API(public API)에 더 자주 쓰인다.**

**RPC의 단점**
- **클라이언트가 서비스 구현에 강하게 결합(tightly coupled)** 된다.
- **새로운 연산이나 사용 사례마다 새 API를 정의**해야 한다.
- **디버깅이 어려울 수 있다.**
- **기존 기술을 그대로 활용하기 어려울 수 있다.** 예를 들어 Squid 같은 캐싱 서버에서 **RPC 호출이 제대로 캐싱되도록 하려면 추가 노력**이 필요하다.

### REST (REpresentational State Transfer)

**클라이언트가 서버가 관리하는 리소스 집합에 대해 동작하는 클라이언트/서버 모델을 강제하는 아키텍처 스타일.**

- 서버는 **리소스의 표현(representation)** 과, 리소스를 조작하거나 새 표현을 얻는 **액션**을 제공한다.
- **모든 통신은 무상태(stateless)이며 캐시 가능해야 한다.**

**RESTful 인터페이스의 네 가지 특질**

| 특질 | HTTP에서의 구현 |
|---|---|
| **리소스 식별** | **URI** — 어떤 연산이든 **같은 URI**를 사용 |
| **표현을 통한 변경** | **동사(HTTP verbs)**, 헤더, 본문 사용 |
| **자기 서술적 오류 메시지** | **상태 코드** 사용 — 바퀴를 다시 발명하지 말 것 |
| **HATEOAS** | 웹 서비스가 **브라우저에서 완전히 접근 가능**해야 함 |

**호출 예시**

```text
GET /someresources/anId

PUT /someresources/anId
{"anotherdata": "another value"}
```

> **REST는 "데이터(data)"를 노출하는 데 집중한다.** 클라이언트/서버 간 **결합도를 최소화**하며 **공개 HTTP API에 자주 쓰인다.**

- URI로 리소스를, 헤더로 표현을, GET·POST·PUT·DELETE·PATCH 같은 **동사로 액션**을 노출하는 **더 일반적이고 획일적인 방법**을 쓴다.
- **무상태이므로 수평 확장과 파티셔닝에 매우 좋다.** → [[2026-07-30-backend-load-balancer]]

**REST의 단점**
- 데이터 노출에 집중하므로, **리소스가 자연스럽게 단순한 계층으로 조직·접근되지 않으면 잘 맞지 않을 수 있다.** 예: *"지난 한 시간 동안 특정 이벤트 집합에 매칭되는 갱신 레코드 전부 반환"* 은 경로로 표현하기 어렵다. URI 경로 + 쿼리 파라미터 + 요청 본문의 조합으로 구현하게 된다.
- **소수의 동사(GET, POST, PUT, DELETE, PATCH)에 의존**하는데, 이것이 사용 사례에 맞지 않을 때가 있다. 예: *"만료된 문서를 아카이브 폴더로 이동"* 은 이 동사들에 깔끔히 들어맞지 않는다.
- **중첩 계층을 가진 복잡한 리소스를 가져오려면 여러 번의 왕복**이 필요하다. 예: 블로그 글 본문과 그 글의 댓글을 가져오기. **네트워크 상태가 변동적인 모바일 애플리케이션에서 이 다중 왕복은 매우 바람직하지 않다.**
- 시간이 지나며 **API 응답에 필드가 추가되면, 오래된 클라이언트도 필요 없는 새 필드를 전부 받게 된다.** 결과적으로 **페이로드가 부풀고 지연시간이 커진다.**

### RPC vs REST 호출 비교 (원문)

| 연산 | RPC | REST |
|---|---|---|
| 가입 | `POST /signup` | `POST /persons` |
| 탈퇴 | `POST /resign`<br>`{"personid": "1234"}` | `DELETE /persons/1234` |
| 사람 조회 | `GET /readPerson?personid=1234` | `GET /persons/1234` |
| 사람의 아이템 목록 조회 | `GET /readUsersItemsList?personid=1234` | `GET /persons/1234/items` |
| 아이템 추가 | `POST /addItemToUsersItemsList`<br>`{"personid":"1234", "itemid":"456"}` | `POST /persons/1234/items`<br>`{"itemid": "456"}` |
| 아이템 수정 | `POST /modifyItem`<br>`{"itemid":"456", "key":"value"}` | `PUT /items/456`<br>`{"key": "value"}` |
| 아이템 삭제 | `POST /removeItem`<br>`{"itemid": "456"}` | `DELETE /items/456` |

> **RPC는 URL에 "동사"가, REST는 URL에 "명사"가 온다.**
> RPC는 대부분 `POST`로 처리하고, REST는 **동사를 HTTP 메서드로** 표현한다.

### 정리

| | **RPC** | **REST** |
|---|---|---|
| 노출하는 것 | **행위(behavior)** | **데이터(resource)** |
| URL | 동사 중심 | **명사 중심** |
| 결합도 | **강함** (구현에 결합) | **약함** |
| 주 용도 | **내부 통신**(성능) | **공개 API** |
| 확장 | — | **무상태 → 수평 확장 유리** |
| 새 기능 | **연산마다 새 API** | 기존 동사 재사용 |

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

**RPC에서는 클라이언트가 다른 주소 공간(보통 원격 서버)에서 프로시저를 실행시킨다.** 프로시저는 로컬 호출인 것처럼 작성되며, 서버와 통신하는 세부 사항은 클라이언트 프로그램에서 추상화된다. **원격 호출은 로컬 호출보다 느리고 신뢰성이 낮으므로 둘을 구분하는 것이 좋다.** 대표 프레임워크로 Protobuf, Thrift, Avro가 있다.

RPC는 요청-응답 프로토콜이다. 클라이언트 프로그램이 클라이언트 스텁을 호출하면, 스텁이 프로시저 id와 인자를 **마샬링**해 요청 메시지로 만들고, OS가 서버로 전송한다. 서버 측 스텁이 **언마샬링**해 해당 id의 프로시저를 호출하며, 응답은 역순으로 진행된다.

**RPC는 행위를 노출하는 데 집중하며**, 용도에 맞게 네이티브 호출을 직접 만들 수 있어 **성능상의 이유로 내부 통신에 자주 쓰인다.** **단점**은 클라이언트가 서비스 구현에 강하게 결합되고, 새로운 연산마다 새 API를 정의해야 하며, 디버깅이 어렵고, 캐싱 서버 같은 기존 기술을 그대로 활용하기 어렵다는 점이다.

**REST는 클라이언트가 서버가 관리하는 리소스 집합에 대해 동작하는 클라이언트/서버 모델을 강제하는 아키텍처 스타일**이다. 서버는 리소스의 표현과 액션을 제공하며, **모든 통신은 무상태이고 캐시 가능해야 한다.**

RESTful 인터페이스의 네 가지 특질은 **URI로 리소스 식별**(어떤 연산이든 같은 URI), **HTTP 동사·헤더·본문으로 표현 변경**, **상태 코드로 자기 서술적 오류 메시지**, 그리고 **HATEOAS**다.

**REST는 데이터를 노출하는 데 집중하며** 클라이언트/서버 간 결합도를 최소화해 **공개 HTTP API에 자주 쓰인다.** 무상태이므로 **수평 확장과 파티셔닝에 좋다.**

**REST의 단점**은 리소스가 단순한 계층으로 조직되지 않으면 표현이 어렵고, 소수의 동사로 표현하기 힘든 연산이 있으며, 중첩 리소스를 가져오려면 **여러 번의 왕복**이 필요하고(특히 모바일에서 문제), 시간이 지나며 응답 필드가 늘어 **페이로드가 부풀고 지연시간이 커진다**는 점이다.

## 내가 정리한 내용

**1. RPC와 REST의 핵심 차이**

**RPC는 "행위(behavior)"를 노출하고, REST는 "데이터(리소스)"를 노출한다.** 그래서 **RPC의 URL에는 동사가**(`/readPerson?id=1234`), **REST의 URL에는 명사가**(`GET /persons/1234`) 온다. RPC는 대부분 POST로 처리하지만 REST는 동사를 HTTP 메서드로 표현한다.

- **RPC**는 원격 서버의 함수를 **마치 로컬 함수처럼** 호출한다. 인자를 마샬링해 보내고 서버 스텁이 언마샬링해 실행한다. 용도에 맞게 네이티브 호출을 만들 수 있어 **성능이 중요한 내부 통신**에 주로 쓴다.
- **REST**는 리소스 식별(URI), 표현을 통한 변경(HTTP 동사), 자기 서술적 오류(상태 코드), HATEOAS의 네 가지 특질을 가지며, **모든 통신은 무상태이고 캐시 가능**해야 한다. 결합도가 낮아 **공개 API**에 주로 쓰이며, **무상태라 수평 확장과 파티셔닝에 유리**하다.

**2. RPC의 단점**

- 클라이언트가 **서비스 구현에 강하게 결합**됨
- **새 연산마다 새 API**를 정의해야 함
- **디버깅이 어려움**
- **기존 기술을 그대로 쓰지 못함** (예: 캐싱 서버에서 RPC 호출을 캐싱하려면 추가 노력 필요)

**3. REST의 단점**

- **계층으로 표현하기 어려운 조회**가 있음 (예: "지난 한 시간 동안 특정 이벤트에 매칭되는 갱신 레코드")
- **소수의 동사에 안 맞는 연산** 존재 (예: "만료 문서를 아카이브로 이동")
- **중첩 리소스는 여러 번 왕복** 필요 — 네트워크가 변동적인 **모바일에서 특히 문제**
- **오버페칭**: 시간이 지나며 필드가 늘면 오래된 클라이언트도 필요 없는 필드를 전부 받아 **페이로드가 부풀고 지연이 커짐**

## 검토 결과

### 확인된 부분

- **RPC와 REST의 단점을 원문의 네 항목씩 빠짐없이** 정리함. 특히 오버페칭의 메커니즘(필드 추가 → 구형 클라이언트도 전부 수신 → 페이로드 증가)을 정확히 서술.
- 실습 Q1에서 RPC 추상화의 위험(네트워크 지연·실패를 잊게 됨)을 정확히 파악.
- 실습 Q2에서 왕복 3번의 모바일 성능 이슈를 정확히 진단.

### 보강 포인트

- **Q1이 "차이"가 아니라 "각각의 설명"이 됐다 → 대비 축을 먼저 세울 것.**
  > **RPC는 행위를 노출하고, REST는 데이터를 노출한다.**

  원문의 이 한 줄이 핵심이며 나머지는 전부 여기서 파생된다. 설명을 나열하기 **전에** 이 대비를 던지면 답이 구조를 갖는다.

  | | RPC | REST |
  |---|---|---|
  | 노출하는 것 | **행위** | **데이터** |
  | URL | **동사** (`/readPerson`) | **명사** (`/persons/1234`) |
  | 결합도 | **강함** | **약함** |
  | 주 용도 | **내부 통신**(성능) | **공개 API** |

### 심화: RPC 추상화의 구체적 대가 (Q1)

```python
# 로컬 함수라면 무해하다
for user_id in user_ids:      # 100명
    user = get_user(user_id)  # 메모리 접근 100번 → 무시할 비용
```

**RPC면 똑같이 생긴 코드가 네트워크 왕복 100번**이다. 각 5ms면 **500ms**.

> **코드는 똑같이 생겼는데 비용이 1000배 차이 난다. 추상화가 그 차이를 감춘다.**

→ **N+1 문제**가 정확히 이것. 페더레이션 후 앱 레벨 조인에서 한 명씩 반복하면 안 되는 이유. [[2026-08-05-backend-federation-sharding]]

**더 무서운 것 — 제3의 상태**

로컬 함수의 결과는 **성공** 또는 **예외** 두 가지뿐이다. **RPC에는 세 번째가 있다.**

```text
① 성공
② 실패
③ 타임아웃 — 성공했는지 실패했는지 모름   ← 로컬에는 없는 상태
```

**어제 배운 그 문제다** — *"POST 응답을 못 받았을 때 재시도해도 되나?"* 로컬 함수라면 생길 수 없는 고민이며, **멱등성 키가 필요한 이유**가 여기서 나온다. → [[2026-08-13-backend-http-tcp-udp]]

> 이를 **"분산 컴퓨팅의 오류(Fallacies of Distributed Computing)"** 라 부른다 — *"네트워크는 신뢰할 수 있다", "지연은 0이다"* 같은 잘못된 가정들. **RPC의 투명한 추상화가 이 착각을 부추긴다.**

→ 8/3의 *"마이크로서비스는 함수 호출을 네트워크 호출로 바꾸는 일"* 과 동일한 문제. [[2026-08-03-backend-application-layer]]

### 심화: 언더페칭과 오버페칭 (Q2)

**① 왕복 3번 (언더페칭)**

```text
GET /posts/123           → 글
GET /users/45            → 작성자
GET /posts/123/comments  → 댓글
```

**모바일 네트워크는 지연이 크고 변동적**이라 왕복 하나하나가 비싸다. 원문도 *"매우 바람직하지 않다"* 고 강하게 표현.

**② 오버페칭**

```text
GET /users/45 → { name, email, phone, address, bio, createdAt, ... }
                  ↑ 필요한 건 name뿐인데 전부 옴
```

> **필요한 건 못 받고(언더페칭), 필요 없는 건 받는(오버페칭)** — REST의 구조적 한계.

**해결책**

| 방법 | 내용 |
|---|---|
| **GraphQL** | 클라이언트가 **필요한 필드만 명시**해 **한 번에** 요청 |
| **BFF (Backend for Frontend)** | **화면 전용 엔드포인트**를 만들어 서버가 합쳐서 반환 |

**BFF가 실무에서 더 흔하다.** `GET /screens/post-detail/123` 처럼 화면 단위 API를 두면 REST의 순수성은 포기하지만 왕복이 1번으로 줄어든다. **REST 원칙과 실제 성능 사이의 트레이드오프.**

### RPC 동작 흐름

```text
① 클라이언트 프로그램 → 클라이언트 스텁 호출 (로컬 호출처럼 스택에 인자를 쌓음)
② 클라이언트 스텁     → 프로시저 id와 인자를 요청 메시지로 마샬링(패킹)
③ 클라이언트 통신 모듈 → OS가 메시지를 서버로 전송
④ 서버 통신 모듈      → OS가 들어온 패킷을 서버 스텁으로 전달
⑤ 서버 스텁          → 언마샬링 후, id에 맞는 서버 프로시저를 인자와 함께 호출
⑥ 서버 응답은 위 과정을 역순으로 반복
```

대표 프레임워크: **Protobuf, Thrift, Avro** (현대에는 gRPC)

**네이티브 라이브러리(SDK)를 선택할 때**: 대상 플랫폼을 알 때 / 로직 접근을 통제하고 싶을 때 / 라이브러리 밖의 오류 처리를 통제하고 싶을 때 / **성능과 최종 사용자 경험이 주 관심사**일 때

### RPC vs REST 호출 비교 (원문)

| 연산 | RPC | REST |
|---|---|---|
| 가입 | `POST /signup` | `POST /persons` |
| 탈퇴 | `POST /resign` + `{personid}` | `DELETE /persons/1234` |
| 사람 조회 | `GET /readPerson?personid=1234` | `GET /persons/1234` |
| 아이템 목록 | `GET /readUsersItemsList?personid=1234` | `GET /persons/1234/items` |
| 아이템 추가 | `POST /addItemToUsersItemsList` | `POST /persons/1234/items` |
| 아이템 수정 | `POST /modifyItem` | `PUT /items/456` |
| 아이템 삭제 | `POST /removeItem` | `DELETE /items/456` |

### 이전 학습과의 연결

- **REST의 무상태가 수평 확장을 가능하게 한다** — 로드밸런서에서 배운 무상태 원칙을 아키텍처 수준에서 강제하는 것. → [[2026-07-30-backend-load-balancer]]
- **HTTP 메서드와 멱등성**이 REST 설계의 기반. `PUT`은 멱등, `POST`는 아니라는 성질이 리소스 설계에 직결된다. → [[2026-08-13-backend-http-tcp-udp]]
- **캐시 가능성** — REST가 캐시 가능해야 한다고 요구하는 것은 HTTP의 자체 완결성과 중간 캐시 계층 덕이다. → [[2026-08-11-backend-cache]]
