## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

### 문제 설정 — 키우면 좋아지는데, 키우면 비싸진다

LLM에는 경험적 규칙이 있다. **파라미터를 늘리면 성능이 오른다**(스케일링 법칙). 문제는 비용이다.

**밀집 모델(dense model)** 에서는 **모든 토큰이 모든 파라미터를 거친다.**

```text
토큰 하나를 처리할 때

  파라미터 700억 개  →  토큰 하나당 700억 개 전부 계산
  파라미터 7000억 개 →  토큰 하나당 7000억 개 전부 계산

파라미터가 10배면 연산도 10배
```

**성능과 연산이 한 몸으로 묶여 있다.** 이 고리를 끊는 것이 MoE의 목표다.

### 핵심 아이디어 — 늘리되, 일부만 켠다

> **파라미터는 많이 두되, 토큰마다 그중 일부만 활성화한다.**

```text
밀집(dense)                        희소(sparse / MoE)
┌──────────────────┐              ┌───┬───┬───┬───┐
│                  │              │E1 │E2 │E3 │E4 │   전문가 8개
│   하나의 큰 FFN   │              ├───┼───┼───┼───┤   중
│  (모든 토큰이     │              │E5 │E6 │E7 │E8 │   토큰마다 2개만 켬
│   전부 통과)      │              └───┴───┴───┴───┘
└──────────────────┘                    ▲
                                    라우터가 고른다
```

**어제 다룬 CNN과 정확히 반대 방향의 선택**이다.

| | 효율을 얻는 방법 |
|---|---|
| **CNN** | **파라미터를 줄인다** (가중치 공유·지역 연결) → [[2026-09-11-ai-data-cnn]] |
| **MoE** | **파라미터는 늘리고, 쓰는 양만 줄인다** |

같은 "효율" 문제를 정반대에서 푼다.

### 구조 — 무엇을 전문가로 쪼개나

트랜스포머 블록은 크게 **어텐션 층**과 **피드포워드 층(FFN)** 으로 나뉜다 — [[2026-08-06-ai-data-self-attention]]

**MoE는 이 중 FFN만 여러 개로 복제한다.**

```text
        ┌─────────────────┐
        │  어텐션 (공유)    │   ← 모든 토큰이 통과
        └────────┬────────┘
                 ▼
        ┌─────────────────┐
        │  라우터(Router)   │   ← 어느 전문가에게 보낼지 결정
        └────────┬────────┘
         ┌───┬───┼───┬───┐
         ▼   ▼   ▼   ▼   ▼
        E1  E2  E3  …  E8      ← FFN 8개 (전문가)
         └───┴───┼───┴───┘
                 ▼
              가중 합
```

| 구성 요소 | 역할 |
|---|---|
| **전문가(Expert)** | 각각이 독립적인 FFN. 서로 다른 패턴에 특화된다 |
| **라우터 / 게이팅 네트워크(Router, Gating Network)** | **토큰마다** 어느 전문가에게 보낼지 점수를 매긴다 |
| **Top-k 라우팅** | 점수 상위 `k`개 전문가만 활성화. Mixtral은 **k=2** |

> 💡 **라우팅은 토큰 단위다.** 문장 단위가 아니라 **토큰 하나하나가 각자 다른 전문가**로 갈 수 있다. 같은 문장 안에서도 "the"와 "미분"이 다른 전문가로 갈라질 수 있다.

### Mixtral 8×7B — 이름이 함정이다

| 항목 | 값 |
|---|---:|
| 전문가 수 | 8개 |
| 토큰당 활성화 | **2개** |
| **총 파라미터** | 약 **47B** |
| **활성 파라미터**(토큰당) | 약 **13B** |

> ⚠️ **"8×7B"인데 왜 56B가 아니라 47B인가?**
>
> **어텐션 층과 임베딩은 전문가마다 복제되지 않고 공유되기 때문**이다. 복제되는 건 FFN뿐이다. 그래서 단순 곱셈보다 작다.
>
> 이걸 아는지 모르는지가 면접에서 **"이름만 아는 사람"과 "구조를 아는 사람"** 을 가른다.

**의미**: 47B 모델의 지식을 갖고 있으면서, 연산량은 13B 모델 수준이다.

### 왜 이게 작동하는가

**모든 토큰에 모든 지식이 필요하지는 않다.**

코드를 처리할 때 필요한 패턴과 시(詩)를 처리할 때 필요한 패턴은 다르다. 밀집 모델은 **매번 둘 다 거친다.** MoE는 **필요한 쪽만 켠다.**

> 🏫 **비유**: 종합병원에 의사가 100명 있다. 환자가 올 때마다 100명 전원이 진료하는 게 밀집 모델이고, **접수처(라우터)가 증상을 보고 2명에게 보내는 것**이 MoE다. 병원의 총 역량은 100명분인데 환자 한 명당 비용은 2명분이다.

다만 실제로 학습된 전문가가 "코드 전문가", "수학 전문가"처럼 **사람이 알아볼 수 있게 나뉘지는 않는다.** 구문적·통계적 패턴으로 갈라지는 경우가 많다.

## 기준 답변

### 밀집 모델 vs 희소 모델

| 항목 | **밀집(Dense)** | **희소(Sparse / MoE)** |
|---|---|---|
| 토큰당 연산 | **모든** 파라미터 | **일부** 파라미터만 |
| 총 파라미터 = 활성 파라미터 | **예** | **아니오** (총 ≫ 활성) |
| 같은 연산량 대비 성능 | 기준 | **더 높다** |
| **필요 메모리(VRAM)** | 파라미터 크기만큼 | **총 파라미터 전부 올려야 한다** ⚠️ |
| 학습 안정성 | 안정적 | **불안정**(라우팅 때문에) |
| 파인튜닝 | 쉽다 | **까다롭다**(과적합 쉬움) |
| 예시 | Llama, GPT-3 | Mixtral, Switch Transformer |

### MoE의 대가 — 메모리는 줄지 않는다

**가장 흔한 오해가 여기 있다.**

```text
MoE가 줄이는 것 : 연산량(FLOPs)     ✅
MoE가 줄이지 않는 것 : 메모리        ❌
```

**어느 전문가가 호출될지 미리 모르므로, 전문가 전부를 메모리에 올려 두어야 한다.** Mixtral 8×7B는 연산은 13B급인데 **메모리는 47B급**을 요구한다.

> 💡 [[2026-09-02-ai-data-kv-cache]]에서 본 구도와 같다. KV 캐시도 **연산을 아끼는 대신 메모리를 썼다.** LLM 최적화는 자주 **연산 ↔ 메모리 축 위에서 자리를 옮기는 일**이지, 둘 다 줄이는 경우는 드물다.

### 부하 불균형(Load Imbalance) — 라우터의 고질병

라우터도 학습되는 신경망이라, **특정 전문가만 편애하는 방향으로 수렴**하기 쉽다.

```text
학습 초기에 E3가 우연히 조금 잘함
  → 라우터가 E3로 더 많이 보냄
  → E3만 더 학습됨 → 더 잘하게 됨
  → 라우터가 더 보냄 …

결과 : E3는 과부하, 나머지 7개는 거의 안 쓰임
       → "전문가 8개"라는 용량이 허명이 된다
```

**해결책**

| 기법 | 내용 |
|---|---|
| **보조 손실(Auxiliary Loss)** | 전문가별 사용량이 고르지 않으면 **벌점을 준다.** 균형을 손실 함수에 넣어 강제 |
| **용량 계수(Capacity Factor)** | 전문가 하나가 받을 수 있는 토큰 수에 **상한**을 둔다. 넘치면 **버린다(token dropping)** |
| **노이즈 추가** | 라우팅 점수에 잡음을 섞어 탐색을 유도 |

> ⚠️ 보조 손실은 **주 손실과 경쟁한다.** 균형을 너무 강하게 강제하면 라우팅이 무의미해지고(아무 데나 보냄), 너무 약하면 붕괴한다. `α`로 조절하는 또 하나의 하이퍼파라미터다 — [[2026-08-31-ai-data-hyperparameter-tuning]]

### 그 밖의 어려움

| 문제 | 내용 |
|---|---|
| **학습 불안정** | 라우팅이 이산적(discrete) 선택이라 기울기가 매끄럽지 않다 |
| **파인튜닝 난이도** | 전문가별로 데이터가 쪼개져 **각 전문가가 보는 데이터가 적어진다** → 과적합 |
| **분산 학습 복잡도** | 전문가를 여러 GPU에 나누면 **토큰을 GPU 간에 주고받아야** 한다(All-to-All 통신) |

### 한 문장 요약

> **MoE는 "총 파라미터"와 "토큰당 연산"을 분리해, 큰 모델의 지식을 작은 모델의 연산 비용으로 쓰려는 구조다. 연산은 줄지만 메모리는 줄지 않고, 라우터의 부하 불균형이 최대 난점이다.**

## 내가 정리한 내용

### 1. MoE의 핵심 아이디어

- **밀집 모델(Dense Model)** 은 모든 토큰이 모든 파라미터를 거친다.
- **MoE는 파라미터를 늘리되**(FFN 층을 여러 개로 **복제**), 토큰마다 **그중 일부만 활성화**해 연산을 최적화한다.

```text
❌ 하나의 FFN을 8조각으로 쪼개고 2조각만 쓴다
   → 총 파라미터 그대로, 활성 파라미터는 1/4 → 그냥 작아진 모델

✅ 정상 크기 FFN을 8개 복제하고 2개를 쓴다
   → 총 파라미터 약 8배, 활성은 원래의 2배
   → 지식 용량은 커지고 연산은 감당 가능한 수준
```

**MoE의 존재 이유가 "파라미터를 늘리는 것"이다.** 스케일링 법칙상 파라미터가 많아야 성능이 오르는데 밀집 모델은 그러면 연산도 같이 폭발한다. MoE는 **파라미터만 늘리고 연산은 안 따라 늘게** 만든 구조다.

### 2. Mixtral 8×7B의 숫자 — 왜 56B가 아닌가

**어텐션 층과 임베딩 층은 모든 전문가가 공유**하기 때문에 실제 총 파라미터는 단순 곱셈보다 적다.

```text
총 파라미터   = 어텐션 + 임베딩 + FFN × 8      ≈ 47B
활성 파라미터 = 어텐션 + 임베딩 + FFN × k      ≈ 13B    (k = 토큰당 선택되는 FFN 수, Mixtral은 2)
```

즉 **47B 모델의 지식을 갖고 있으면서 연산량은 13B 모델 수준**이다.

### 3. 두 가지 대가

**① 메모리는 줄지 않는다.** MoE가 줄이는 건 **연산량이지 메모리가 아니다.** 라우팅이 토큰마다 새로 결정되므로 **어느 전문가가 필요한지 미리 알 수 없고**, 따라서 전부 메모리에 올려 두어야 한다.

**② 부하 불균형(Load Imbalance).** FFN을 선택하는 라우터도 신경망이라 학습이 필요한데, **하나의 FFN만 제대로 학습되어 그것만 선택되면** 실제 파라미터 수는 많지만 낮은 효율을 낸다.

비용으로 보면 더 아프다.

```text
메모리 비용 : 47B 전부 올린다        ← 다 낸다
실제 지식   : 한 전문가만 학습됨      ← 못 받는다
→ 그럴 거면 그냥 밀집 13B 모델을 쓰는 게 나았다
```

**MoE를 쓰는 이유 자체가 사라진다.** 그래서 보조 손실(Auxiliary Loss)은 단순 최적화가 아니라 **MoE 성립의 전제 조건**이다.

### 4. CNN과의 대비

- **CNN은 파라미터 수를 줄여** 최적화하고, **MoE는 파라미터 수는 늘리되 사용하는 양을 줄여** 연산을 최적화한다.
- **둘 다 "사용하는 파라미터 수를 줄여 연산을 최적화한다"** 는 점은 같다.
- 다만 **줄이는 방식이 정적이냐 동적이냐**가 갈린다.

| | CNN | MoE |
|---|---|---|
| 어떤 파라미터를 쓰나 | **입력과 무관하게 항상 같은 것** | **입력마다 다른 것** |
| 성격 | **정적(static)** | **동적 = 조건부 계산(conditional computation)** |
| 총 파라미터 | **실제로 적다** | **많다** (전부 보유) |
| 추가로 필요한 것 | 없음 | **라우터** + 부하 균형 장치 |
| **메모리** | **줄어든다** | **안 줄어든다** |

**대가의 유무가 갈린다.** CNN은 파라미터가 실제로 적으니 거의 공짜고(가정이 맞다는 전제하에), MoE는 **메모리를 전액 지불하고 연산만 할인받는다.**

## 검토 결과

### 확인된 부분

- **왜 56B가 아닌지를 공식으로 정리했다.** `총 = 어텐션 + 임베딩 + FFN×8`, `활성 = 어텐션 + 임베딩 + FFN×k`. 숫자를 외운 게 아니라 **구조에서 유도**했다. 오늘 답변 중 가장 좋다.
- **메모리와 부하 불균형**을 양쪽 다 정확히 짚었다. 특히 **"실제 파라미터 수는 많지만 낮은 효율"** 이라는 표현이 정확하다.
- **"둘 다 사용하는 파라미터 수를 줄인다"** — CNN과 MoE를 **하나의 원리로 통합**했다. 서로 다른 두 기법에서 공통 구조를 뽑아낸 것이다.

### 보강 포인트

#### ① MoE는 파라미터를 **늘린다** — 그대로 두는 게 아니다

| | 내용 |
|---|---|
| **전** | 파라미터는 **그대로 두되**, FFN 층을 **분리시켜** 일부만 활성화 |
| **후** | 파라미터를 **늘리되**(FFN을 8개로 **복제**), 토큰마다 그중 일부만 활성화 |

**두 해석이 완전히 다른 모델이 된다.** 쪼개서 일부만 쓰면 그냥 작아진 모델이고, 복제해서 일부만 쓰면 지식 용량이 커진 모델이다. 교정 후 내용은 위 `내가 정리한 내용` 1번에 반영.

> 💡 **Q2에서 쓴 공식이 이미 정답이었다** — `FFN × 8`이라고 썼으니 8배로 늘어난 것이다. Q1·Q4의 "그대로 두되"라는 표현만 자기 공식과 어긋났다. **말과 수식이 어긋나면 수식을 믿고 말을 고치는 게 맞다.**

#### ② CNN과의 "다른 점"이 빠졌다

같은 점(사용 파라미터 감소)은 정확했으나 **정적 vs 동적**이라는 결정적 차이가 없었다. 교정 후 내용은 위 `내가 정리한 내용` 4번의 표에 반영.

#### ③ 부하 불균형이 "왜 치명적인가"를 비용으로

"낮은 효율"까지는 맞지만, **메모리 비용은 전액 내면서 이득만 못 받는 구조**라는 점을 말하면 심각성이 분명해진다. 교정 후 내용은 위 `내가 정리한 내용` 3번에 반영.

### 심화: 왜 전문가를 미리 골라 올려 둘 수 없나

```text
라우팅은 토큰마다 새로 결정된다
토큰1 → E2, E5
토큰2 → E1, E7     ← 매번 달라진다
토큰3 → E2, E3
```

**어느 전문가가 필요한지는 그 토큰이 실제로 들어와 봐야 안다.**

그럼 필요할 때마다 가져오면 되지 않을까? 실제로 그런 기법이 있다(**오프로딩, offloading**). 그런데 잘 안 된다.

```text
토큰 하나 처리          = 수 밀리초
전문가 전송(CPU→VRAM)  = 수십~수백 밀리초

→ 전송이 연산보다 훨씬 비싸다
→ 매 토큰 전송하면 MoE로 아낀 연산 이득이 통째로 날아간다
```

**연산을 아끼려고 만든 구조인데 전송 비용이 그보다 커지면 의미가 없다.** 그래서 실무에서는 전부 VRAM에 올린다.

### 심화: 라우터 붕괴(Router Collapse)

```text
학습 초기에 E3가 우연히 조금 잘함
  → 라우터가 E3로 더 많이 보냄
  → E3만 더 학습됨 → 더 잘하게 됨
  → 라우터가 더 보냄 …

결과 : E3는 과부하, 나머지 7개는 거의 안 쓰임
       → "전문가 8개"라는 용량이 허명이 된다
```

잃는 것은 **유효 용량(effective capacity)** 이다.

**해결책**

| 기법 | 내용 |
|---|---|
| **보조 손실(Auxiliary Loss)** | 전문가별 사용량이 고르지 않으면 **벌점**을 준다 — 균형을 손실 함수에 넣어 강제 |
| **용량 계수(Capacity Factor)** | 전문가당 받을 토큰 수에 **상한**. 넘치면 **버린다**(token dropping) |
| **노이즈 추가** | 라우팅 점수에 잡음을 섞어 탐색 유도 |

> ⚠️ 보조 손실은 **주 손실과 경쟁한다.** 균형을 너무 강하게 강제하면 라우팅이 무의미해지고(아무 데나 고르게 보냄), 너무 약하면 붕괴한다. `α`로 맞춰야 하는 또 하나의 하이퍼파라미터 문제 → [[2026-08-31-ai-data-hyperparameter-tuning]]

### 심화: 연산 ↔ 메모리 축 위의 이동

| 기법 | 내준 것 | 산 것 |
|---|---|---|
| **KV 캐시** | 메모리 | 연산 → [[2026-09-02-ai-data-kv-cache]] |
| **MoE** | 메모리 | 연산 |
| **그래디언트 체크포인팅** | 연산 | 메모리 → [[2026-09-04-ai-data-backpropagation]] |
| **양자화** | 정밀도 | 메모리 + 연산 |

**LLM 최적화는 대체로 연산 ↔ 메모리 축 위에서 자리를 옮기는 일**이고, 둘 다 줄이는 경우는 드물다. 양자화 정도가 예외인데 그건 **정밀도**라는 제3의 자원을 내준다.

### 심화: 그 밖의 어려움

| 문제 | 내용 |
|---|---|
| **학습 불안정** | 라우팅이 **이산적(discrete) 선택**이라 기울기가 매끄럽지 않다 |
| **파인튜닝 난이도** | 전문가별로 데이터가 쪼개져 **각 전문가가 보는 데이터가 적어진다** → 과적합 |
| **분산 학습 복잡도** | 전문가를 여러 GPU에 나누면 **토큰을 GPU 간에 주고받아야** 한다(All-to-All 통신) |

또한 학습된 전문가가 "코드 전문가", "수학 전문가"처럼 **사람이 알아볼 수 있게 나뉘지는 않는다.** 구문적·통계적 패턴으로 갈라지는 경우가 많다.

### 이전 학습과의 연결

- [[2026-09-11-ai-data-cnn]] — **정반대 방향의 효율 전략.** CNN은 파라미터를 줄이고(정적), MoE는 늘리되 일부만 쓴다(동적). 그럼에도 **"사용하는 파라미터를 줄인다"** 는 결과는 같다.
- [[2026-09-02-ai-data-kv-cache]] — **메모리를 내주고 연산을 사는** 같은 거래. LLM 최적화의 기본 축이다.
- [[2026-09-04-ai-data-backpropagation]] — 그래디언트 체크포인팅은 **반대 방향** 거래(연산을 내주고 메모리를 산다).
- [[2026-08-06-ai-data-self-attention]] — MoE가 쪼개는 대상이 **FFN**이고, **어텐션은 공유**된다. 트랜스포머 블록의 구조를 알아야 47B 계산이 나온다.
- [[2026-09-08-ai-data-model-distillation]] — 둘 다 **"큰 모델의 성능을 싸게 쓰려는" 시도**다. 증류는 작은 모델로 옮기고, MoE는 큰 모델의 일부만 켠다.
- [[2026-08-31-ai-data-hyperparameter-tuning]] — 보조 손실의 `α`가 전형적인 튜닝 대상이다.
- [[2026-08-12-backend-asynchronism]] — 부하 불균형과 **용량 상한·요청 버리기(token dropping)** 는 백엔드의 백프레셔와 같은 구조다.
