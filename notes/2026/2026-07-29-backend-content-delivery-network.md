# CDN(Content Delivery Network)이란 무엇이며, Push와 Pull은 어떻게 다른가?

## 질문

> **CDN이란 무엇이며, Push CDN과 Pull CDN은 어떻게 다른가?**
>
> 원문: *Content delivery network*

## 핵심 개념

질문에 답하기 위해 필요한 핵심 개념을 정리한다.

- **정의**: **전 세계에 분산된 프록시 서버 네트워크**로, 사용자와 더 가까운 위치에서 콘텐츠를 제공한다.
- **주로 다루는 것**: HTML/CSS/JS, 이미지, 동영상 같은 **정적 파일**. (CloudFront 등 일부는 동적 콘텐츠도 지원)
- **어떤 서버로 갈지는 DNS(Domain Name System)가 알려준다.** → [[2026-07-28-backend-domain-name-system]]의 geolocation 라우팅과 직결.
- **성능이 개선되는 두 가지 경로**
  1. 사용자가 **가까운 데이터센터**에서 콘텐츠를 받는다 → 지연시간 감소
  2. **원본 서버가 그 요청을 처리하지 않아도 된다** → 원본 부하 감소
  - 즉 CDN은 **지연시간과 처리량을 동시에** 개선한다. → [[2026-07-21-backend-latency-vs-throughput]]

### Push CDN

- 서버에서 **변경이 생길 때마다 CDN으로 밀어 넣는다.** 콘텐츠 제공 책임을 내가 전부 진다(직접 업로드 + URL 재작성).
- 만료·갱신 시점을 직접 설정할 수 있다.
- 새 콘텐츠나 변경분만 올리므로 **트래픽은 최소**, 대신 **저장 공간은 최대**.
- **적합**: 트래픽이 적거나, 콘텐츠가 자주 바뀌지 않는 사이트. 한 번 올려두고 재요청이 없다.

### Pull CDN

- **첫 사용자가 요청할 때** CDN이 원본 서버에서 콘텐츠를 가져온다. 콘텐츠는 원본에 두고 URL만 CDN으로 바꾼다.
- 캐시되기 전 **첫 요청은 느리다**(cache miss).
- **TTL(Time To Live, 캐시 유효기간)** 이 캐시 유지 기간을 결정한다.
- 저장 공간은 최소지만, 실제로 바뀌지 않았는데 만료되어 다시 당겨오면 **중복 트래픽**이 생긴다.
- **적합**: 트래픽이 많은 사이트. 최근 요청된 콘텐츠만 남아 트래픽이 고르게 분산된다.

### 비교

| | Push CDN | Pull CDN |
|---|---|---|
| 언제 올라가나 | 변경 시 **내가 밀어 넣음** | 첫 요청 시 **CDN이 당겨감** |
| 첫 요청 | 이미 있으므로 빠름 | **느림**(cache miss) |
| 저장 공간 | 최대 | 최소 |
| 트래픽 | 최소 | 만료 시 중복 발생 가능 |
| 관리 책임 | 내가 전부 | CDN이 자동 |
| 적합 | 트래픽 적음 / 변경 드묾 | **트래픽 많음** |

### 단점

- **비용**: 트래픽에 따라 상당할 수 있다. (단, CDN을 안 썼을 때의 비용과 비교해야 한다)
- **stale 콘텐츠**: TTL 만료 전에 원본이 바뀌면 낡은 내용이 제공된다. → [[2026-07-22-backend-availability-vs-consistency]]의 최종 일관성과 같은 뿌리.
- **URL 변경 필요**: 정적 콘텐츠 URL을 CDN을 가리키도록 바꿔야 한다.

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

**CDN은 전 세계에 분산된 프록시 서버 네트워크로, 사용자와 가까운 위치에서 콘텐츠를 제공한다.** 일반적으로 HTML/CSS/JS, 사진, 동영상 같은 정적 파일을 서빙하며, Amazon CloudFront처럼 동적 콘텐츠를 지원하는 CDN도 있다. 어떤 서버에 접속할지는 사이트의 DNS 해석이 알려준다.

CDN이 성능을 크게 개선하는 방식은 두 가지다.
- 사용자가 가까운 데이터센터에서 콘텐츠를 받는다
- 내 서버가 CDN이 처리한 요청을 감당하지 않아도 된다

**Push CDN**은 서버에 변경이 생길 때마다 새 콘텐츠를 받는다. 직접 업로드하고 URL을 재작성해야 하며, 새롭거나 변경된 콘텐츠만 올리므로 트래픽은 최소화되지만 저장 공간은 최대가 된다. 트래픽이 적거나 콘텐츠가 자주 바뀌지 않는 사이트에 적합하다.

**Pull CDN**은 첫 사용자가 요청할 때 원본 서버에서 콘텐츠를 가져온다. 캐시되기 전까지 요청이 느리며, TTL이 캐시 기간을 결정한다. 저장 공간은 최소화되지만 파일이 실제로 바뀌지 않았는데 만료되어 다시 당겨오면 중복 트래픽이 발생한다. 트래픽이 많은 사이트에 적합하다.

**단점**으로는 트래픽에 따른 비용, TTL 만료 전 갱신 시 낡은 콘텐츠 제공, 정적 콘텐츠 URL 변경 필요가 있다.

## 내가 정리한 내용

**1. CDN(Content Delivery Network)이란?**

전 세계에 분산된 프록시 서버 네트워크로, 사용자와 가까운 곳에서 콘텐츠를 제공한다. 주로 HTML/CSS/JS, 이미지, 동영상 같은 정적 파일을 다룬다.

성능이 좋아지는 경로는 두 가지다.

1. 사용자가 **가까운 데이터센터**에서 받는다 → **지연시간(Latency)** 개선
2. **원본 서버가 그 요청을 처리하지 않아도 된다** → **처리량(Throughput)** 개선

즉 트레이드오프 없이 두 축을 동시에 개선한다.

**2. Push CDN vs Pull CDN**

콘텐츠가 CDN에 **올라가는 시점**이 다르다. Push는 변경이 생길 때 **내가 밀어 넣고**, Pull은 첫 사용자 요청 시 **CDN이 원본에서 당겨간다.** 그래서 Push는 관리를 내가 책임지고 저장 공간을 많이 쓰며, Pull은 자동이지만 첫 요청이 느리다(cache miss).

**트래픽이 많은 사이트는 Pull**이 적합하다. 요청된 콘텐츠만 캐시에 남아 **인기 콘텐츠에 자원이 집중**되고 관리도 자동이기 때문이다.

**3. 단점**

1. **비용**이 트래픽에 비례한다. 단, CDN을 쓰지 않을 때의 원본 서버 증설 비용과 비교해야 한다.
2. **stale(낡은) 콘텐츠** — TTL(Time To Live) 만료 전에 원본이 바뀌면 옛 콘텐츠가 제공된다. 캐시 무효화(Purge)나 **캐시 버스팅**(파일명에 해시를 붙여 URL을 바꾸는 방식)으로 대응한다.
3. 정적 콘텐츠 **URL(Uniform Resource Locator) 변경**이 필요하다.

## 검토 결과

### 확인된 부분

- CDN의 정의(전 세계 분산 프록시 서버, 가까운 곳에서 제공)를 정확히 서술.
- 실습 Q1에서 "내 서버 부하 감소 → **처리량**"을 정확히 연결.
- Pull CDN이 트래픽 많은 사이트에 적합한 이유를 **"인기 콘텐츠에 자원이 집중된다"** 로 정확히 파악.
- 실습 Q2에서 stale 이미지 문제의 원인(캐시 + TTL)과 DNS와 같은 뿌리임을 정확히 진단.

### 보강 포인트

- **"두 가지 경로"는 결과가 아니라 원인으로 답할 것.** 초기 답변은 결과(지연시간·처리량)만 서술 → 면접관은 "왜 그렇게 되죠?"를 되묻는다. **원인 → 결과**로 붙일 것.
- **Push/Pull의 근본 차이는 "관리 주체"가 아니라 "콘텐츠가 올라가는 시점"이다.** 관리 주체는 거기서 파생된 결과.
  - 이름이 곧 정의: **Push는 밀고, Pull은 당긴다.**

  | | Push CDN | Pull CDN |
  |---|---|---|
  | **언제 올라가나** | 변경 시 **내가 밀어 넣음** | 첫 요청 시 **CDN이 당겨감** |
  | 그래서 관리는 | 내가 전부 책임 | 자동 |
  | 첫 요청 | 이미 있으니 빠름 | **느림**(cache miss) |
  | 저장 공간 | 최대 | 최소 |

- **단점에서 stale 콘텐츠가 누락됨 → 추가.** 단순 누락 이상의 의미가 있다. **CDN의 본질이 캐시**이므로 stale은 부수적 결함이 아니라 **구조가 지불하는 대가**다. 이걸 빼면 캐시의 본질을 모르는 답으로 읽힌다. 대책(퍼지, 캐시 버스팅)까지 붙이면 강한 답이 된다.

### 심화: DNS와 CDN의 stale 대응이 다른 이유

둘 다 캐시라 stale 문제를 공유하지만, **해결 수단이 다르다.**

| | DNS(Domain Name System) | CDN(Content Delivery Network) |
|---|---|---|
| 캐시 대상 | 도메인 이름 | 파일 URL |
| 이름을 바꿀 수 있나 | ❌ 도메인은 못 바꿈 | ✅ **URL을 바꿀 수 있음** |
| 해결책 | **TTL 단축**밖에 없음(사전 준비 필수) | TTL + **퍼지 + 캐시 버스팅** |

**CDN만의 두 무기**

1. **캐시 무효화(Purge / Invalidation)** — CDN 사업자에게 "이 파일 캐시를 버려라"고 명령할 수 있다. DNS는 전 세계 리졸버 캐시를 강제로 비울 방법이 없어 불가능하다.
2. **캐시 버스팅(Cache Busting)** — 더 근본적인 해법.
   ```text
   before:  /img/logo.png          ← 내용이 바뀌어도 URL이 같아 캐시가 안 바뀜
   after:   /img/logo.a3f9c2.png   ← 내용이 바뀌면 파일명도 바뀜 = 새 URL = 무조건 새로 받음
   ```
   캐시를 무효화하는 게 아니라 **새 이름을 줘서 캐시를 우회**한다. 그래서 이런 파일은 TTL을 1년으로 잡아도 안전하다.

> **DNS는 이름을 못 바꾸니 TTL로 버티고, CDN은 이름을 바꿀 수 있으니 문제를 원천 차단한다.**

### 이전 학습과의 연결

- **CDN은 지연시간과 처리량을 동시에 개선한다 — 트레이드오프가 없다.** 배치(batching)처럼 "처리량을 얻으려 지연시간을 내주는" 것이 아니라 **불필요한 왕복 자체를 없애기** 때문. → *"낭비를 없애는 데는 대가가 없고, 모아서 처리하는 데는 대가가 있다."* [[2026-07-21-backend-latency-vs-throughput]]
- 원본 서버 부하 감소 = 같은 하드웨어로 더 많은 사용자 감당 = **확장성(Scalability)**. → [[2026-07-20-backend-performance-vs-scalability]]
- 어떤 엣지 서버로 보낼지는 **DNS의 geolocation 라우팅**이 결정한다. → [[2026-07-28-backend-domain-name-system]]
- stale 콘텐츠 = **최종 일관성(eventual consistency)** 과 같은 뿌리. 캐시가 있는 곳엔 언제나 따라온다. → [[2026-07-22-backend-availability-vs-consistency]]
