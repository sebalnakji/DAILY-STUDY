## 핵심 개념

### Step 1. 사용 사례와 제약

**범위에 포함**
- 사용자가 **트윗을 게시**한다 → 서비스가 **팔로워에게 트윗을 밀어 넣고**, 푸시 알림과 이메일을 보낸다
- 사용자가 **유저 타임라인**(자신의 활동)을 본다
- 사용자가 **홈 타임라인**(팔로우한 사람들의 활동)을 본다
- 사용자가 **키워드로 검색**한다
- 서비스는 **고가용성**을 갖는다

**범위 밖**: Firehose 스트림 전송, 가시성 설정에 따른 필터링, 분석

**가정**
- 트래픽은 고르게 분포하지 않는다
- **트윗 게시는 빨라야 한다** — 단, **수백만 팔로워가 있는 경우는 예외**
- **활성 사용자 1억 명**
- **하루 5억 트윗** (월 150억)
  - 트윗 하나당 평균 **팬아웃 10건** 배달
  - 하루 **50억 건** 팬아웃 배달 (월 1,500억)
- **월 2,500억 읽기 요청**
- **월 100억 검색**

**타임라인**: 조회가 빨라야 하고, **트위터는 쓰기보다 읽기가 많다.** 읽기를 최적화하되 **트윗 수집(ingest)은 쓰기가 많다.**

### 어림 계산

```text
트윗 하나 크기
  tweet_id   8 bytes
  user_id   32 bytes
  text     140 bytes
  media     10 KB (평균)
  ─────────────────────
  합계     ~10 KB

월 신규 트윗 콘텐츠 150 TB  (10KB × 5억 × 30일)
3년이면 5.4 PB

초당 읽기 요청      100,000건
초당 트윗            6,000건
초당 팬아웃 배달    60,000건
초당 검색 요청       4,000건
```

**환산 가이드**: `400 requests/sec = 10억 requests/month`

→ [[2026-08-19-backend-latency-numbers]]

### Step 3. 핵심 컴포넌트

#### 사용 사례 ①: 트윗 게시 — **팬아웃이 핵심**

- **유저 타임라인**(자신의 트윗)은 **관계형 DB**에 저장할 수 있다.
- **홈 타임라인 구성이 훨씬 까다롭다.** 모든 팔로워에게 트윗을 팬아웃하면(**초당 6만 건 배달**) **전통적 관계형 DB가 과부하**된다.
  - → **NoSQL 데이터베이스나 메모리 캐시** 같은 **쓰기가 빠른** 저장소를 선택해야 한다.
  - 원문 인용: **메모리에서 1MB 순차 읽기는 약 250us, SSD는 4배, 디스크는 80배.**
- 사진·영상 같은 **미디어는 Object Store**에 저장한다.

**흐름**

```text
클라이언트 → 웹 서버(리버스 프록시) → Write API
  ① 트윗을 SQL DB의 유저 타임라인에 저장
  ② Fan Out Service 호출:
     - User Graph Service에 질의해 팔로워 목록 확보(메모리 캐시)
     - 팔로워들의 홈 타임라인에 트윗 저장 (메모리 캐시)
       → O(n) 연산: 팔로워 1,000명 = 1,000번 조회·삽입
     - Search Index Service에 저장 (빠른 검색용)
     - 미디어를 Object Store에 저장
     - Notification Service로 푸시 알림 발송
       → 큐를 사용해 비동기 발송
```

**메모리 캐시가 Redis라면** 네이티브 리스트를 다음 구조로 쓸 수 있다.

```text
| 8 bytes   8 bytes  1 byte | 8 bytes   8 bytes  1 byte |
| tweet_id  user_id  meta   | tweet_id  user_id  meta   |
```

**공개 API는 REST, 내부 통신은 RPC.** → [[2026-08-14-backend-rpc-rest]]

#### 사용 사례 ②: 홈 타임라인 조회

```text
클라이언트 → 웹 서버 → Read API → Timeline Service
  - 메모리 캐시에서 타임라인 데이터(tweet_id, user_id) 조회 — O(1)
  - Tweet Info Service에 multiget으로 트윗 상세 조회 — O(n)
  - User Info Service에 multiget으로 유저 상세 조회 — O(n)
```

> **핵심: 캐시에는 ID만 저장하고, 상세 정보는 별도 서비스에서 한 번에 가져온다(multiget).**

#### 사용 사례 ③: 유저 타임라인 조회

**SQL 데이터베이스**에서 유저 타임라인을 가져온다. 홈 타임라인과 달리 **자신의 트윗만** 나온다.

#### 사용 사례 ④: 키워드 검색

```text
클라이언트 → 웹 서버 → Search API → Search Service
  ① 입력 쿼리를 파싱/토큰화
     - 마크업 제거
     - 텍스트를 용어(term)로 분해
     - 오타 수정
     - 대소문자 정규화
     - 쿼리를 불리언 연산으로 변환
  ② Search Cluster(예: Lucene)에 질의
     - 클러스터의 각 서버에 scatter-gather
     - 병합·랭킹·정렬 후 반환
```

### Step 4. 규모 확장

> ⚠️ **초기 설계에서 최종 설계로 바로 뛰어들지 말 것.** 벤치마크 → 프로파일링 → 병목 해결 → 반복.

#### 팬아웃 서비스가 병목이다 ⭐

> **수백만 팔로워를 가진 트위터 사용자는 트윗이 팬아웃 과정을 통과하는 데 몇 분이 걸릴 수 있다.**
> 이는 그 트윗에 대한 **@replies와 경쟁 조건(race condition)** 을 일으킬 수 있는데, **serve 시점에 트윗을 재정렬**해 완화할 수 있다.

**해법: 유명인은 팬아웃하지 않는다**

> **팔로워가 아주 많은 사용자의 트윗은 팬아웃을 피할 수 있다.** 대신 그런 사용자의 트윗은 **검색으로 찾아** 사용자의 홈 타임라인 결과와 **병합**하고, **serve 시점에 재정렬**한다.

- 일반 사용자 → **푸시(팬아웃)**: 미리 각 팔로워의 타임라인에 넣어둔다
- 유명인 → **풀(pull)**: 조회할 때 가져와 합친다
- → 이것이 **하이브리드 팬아웃**이다.

#### 추가 최적화

- 홈 타임라인마다 **수백 개 트윗만** 메모리 캐시에 유지
- **활성 사용자의 홈 타임라인만** 메모리 캐시에 유지
  - 지난 30일간 비활성이었다면 **SQL DB에서 타임라인을 재구성**한다 (User Graph Service로 팔로우 목록 조회 → SQL DB에서 트윗을 가져와 캐시에 추가)
- Tweet Info Service에는 **한 달치 트윗만** 저장
- User Info Service에는 **활성 사용자만** 저장
- **Search Cluster는 지연을 낮추기 위해 트윗을 메모리에 유지**해야 할 가능성이 높다

#### SQL 데이터베이스 병목

- 메모리 캐시가 부하를 줄여주지만, **SQL 읽기 복제본만으로는 캐시 미스를 감당하기 어렵다.**
- **높은 쓰기 volume은 단일 SQL Write Master-Slave를 압도한다.**
- → **페더레이션, 샤딩, 비정규화, SQL 튜닝**이 추가로 필요하며, 일부 데이터를 **NoSQL**로 옮기는 것도 고려한다.

## 기준 답변

기준 레포의 답변을 바탕으로 핵심만 재구성한다.

**Step 1**: 트윗 게시(팔로워에게 푸시), 유저 타임라인 조회, 홈 타임라인 조회, 키워드 검색, 고가용성이 범위다. **활성 사용자 1억 명, 하루 5억 트윗**, 트윗당 **평균 팬아웃 10건**, 월 2,500억 읽기, 월 100억 검색을 가정한다. 트윗 하나는 미디어 포함 **약 10KB**로 월 **150TB**, 3년 **5.4PB**다. **초당 읽기 10만 건, 트윗 6천 건, 팬아웃 배달 6만 건, 검색 4천 건**이다.

**Step 3**: 유저 타임라인은 관계형 DB에 저장할 수 있지만, **홈 타임라인 구성이 까다롭다.** 초당 6만 건의 팬아웃 배달은 전통적 관계형 DB를 과부하시키므로 **NoSQL이나 메모리 캐시처럼 쓰기가 빠른 저장소**를 골라야 한다. 미디어는 Object Store에 둔다.

트윗 게시 시 **Fan Out Service**가 User Graph Service로 팔로워를 찾아 **각 팔로워의 홈 타임라인에 트윗을 저장**하는데, 이는 **O(n) 연산**이다(팔로워 1,000명 = 1,000번 조회·삽입). 동시에 검색 인덱스에 저장하고, 큐를 통해 **비동기로 알림**을 보낸다.

홈 타임라인 조회는 메모리 캐시에서 **ID만 O(1)로 가져온 뒤**, Tweet Info Service와 User Info Service에 **multiget**으로 상세를 조회한다.

검색은 쿼리를 **파싱·토큰화**(마크업 제거, 용어 분해, 오타 수정, 대소문자 정규화, 불리언 변환)한 뒤 **Lucene 같은 Search Cluster에 scatter-gather**로 질의해 병합·랭킹·정렬한다.

**Step 4**: **팬아웃 서비스가 병목**이다. 팔로워가 수백만인 사용자는 팬아웃에 몇 분이 걸려 **@replies와 경쟁 조건**을 일으킬 수 있으며, **serve 시점 재정렬**로 완화한다. 또는 **팔로워가 많은 사용자는 팬아웃을 아예 하지 않고**, 검색으로 그들의 트윗을 찾아 홈 타임라인과 **병합 후 재정렬**할 수 있다.

추가 최적화로 홈 타임라인마다 수백 개 트윗만 캐시에 유지하고, **활성 사용자만** 캐시에 두며(비활성 사용자는 SQL DB에서 재구성), 한 달치 트윗만 저장한다. **높은 쓰기 volume이 단일 Write Master-Slave를 압도**하므로 페더레이션·샤딩·비정규화·SQL 튜닝이 필요하다.

## 내가 정리한 내용

**1. 팬아웃이란? 왜 어려운가**

**트윗 하나를 모든 팔로워의 타임라인에 배달하는 것**, 즉 **쓰기 1번이 팔로워 수만큼의 쓰기로 증폭되는 구조**다.

어려운 이유는 두 가지다.

- **O(n) 증폭**: 팔로워 1,000명이면 쓰기 1,000번. 초당 6천 트윗이 **초당 6만 건 배달**이 되어 전통적 관계형 DB를 과부하시킨다. → 그래서 **NoSQL이나 메모리 캐시처럼 쓰기가 빠른 저장소**를 쓴다.
- **팔로워 수가 극단적으로 불균등**: 평균은 10명이지만 어떤 계정은 1억 명이다. **평균으로 설계하면 유명인 하나에 시스템이 무너진다.**

**2. 푸시 vs 풀의 트레이드오프**

- **푸시(팬아웃)**: 쓰기는 무겁지만 **조회가 가볍다.** 게시 시점에 각 팔로워의 타임라인에 미리 넣어둔다.
- **풀**: 쓰기는 가볍지만 **조회가 무겁다.** 조회 시점에 팔로우한 사람들의 트윗을 모아 병합한다.

트위터는 **읽기가 쓰기보다 약 17배 많으므로**(초당 읽기 10만 vs 트윗 6천) **읽기를 최적화하는 푸시를 기본**으로 한다. 즉 **오래 걸리는 작업을 미리 해두는** 방식이다.

**3. 하이브리드 팬아웃**

**사용자에 따라 푸시와 풀을 나눠 쓰는 것**이다.

- **일반 사용자 → 푸시**: 게시 시 미리 팔로워 타임라인에 배달
- **팔로워가 아주 많은 사용자 → 풀**: 팬아웃하지 않고, 조회 시 검색으로 그들의 트윗을 찾아 홈 타임라인과 **병합**
- 마지막에 **serve 시점에 재정렬**해 순서를 맞춘다

유명인은 소수인데 팬아웃 비용은 압도적이므로(1억 팔로워면 1억 번 삽입, 초당 6만 건 처리 기준 약 28분), **그들만 예외 처리하는 것이 훨씬 효율적**이다.

## 검토 결과

### 확인된 부분

- **푸시 vs 풀의 트레이드오프를 정확히 대칭으로 파악.** 어느 쪽이 무겁고 가벼운지 헷갈리지 않았다.
- **하이브리드 팬아웃의 개념**(사용자에 따라 전략을 바꾼다)을 정확히 이해.
- 실습 Q2에서 **답글이 원글보다 먼저 도착하는 경쟁 조건**을 정확히 지적.

### 보강 포인트

- ⚠️ **팬아웃의 정의가 "DB 과부하"가 아니다.** (Q1 초기 답변 → 교정)
  - **DB 과부하는 결과**이고 **팬아웃은 원인**이다. `1 → N`으로 퍼져나가는 **증폭 구조 자체**가 팬아웃이다.

  ```text
  트윗 1건 게시
     ↓ 팬아웃
  팔로워 1,000명의 타임라인에 각각 삽입 → 쓰기 1,000번
  ```

- **"상황에 맞는 최적화가 필요해서 어렵다"는 순환 설명이다.** 구체적 이유 두 가지(O(n) 증폭 / 팔로워 수의 극단적 불균등)를 대야 한다.
- **푸시를 고르는 근거는 읽기:쓰기 비율.** 초당 읽기 10만 vs 트윗 6천 = **약 17배**. 많은 쪽을 최적화하는 것이 합리적이다.

### 심화: 유명인 팬아웃의 비용 (Q2)

원문은 *"몇 분"* 이라고 하지만 숫자를 넣으면 더 심각하다.

```text
시스템 처리 능력: 초당 6만 건 팬아웃
1억 팔로워 계정 트윗 1건

1억 ÷ 6만 ≈ 1,667초 ≈ 28분
```

**그것도 다른 트윗이 전혀 없다고 가정했을 때다.** 실제로는 **시스템 전체를 마비**시킨다.

**두 가지 조치가 함께 간다.**

| 조치 | 목적 |
|---|---|
| **유명인은 풀로 전환** | 근본 해결 — 1억 번 삽입 → 0번 |
| **serve 시점 재정렬** | 경쟁 조건 완화 (답글 순서 문제) |

### 이 문제에는 이름이 있다 — 셀러브리티 문제 / 핫 키 문제

**같은 뿌리의 문제를 이미 세 번 만났다.**

| 상황 | 문제 |
|---|---|
| **샤딩** | 헤비 유저가 한 샤드에 몰려 **그 샤드만 죽어남** → [[2026-08-05-backend-federation-sharding]] |
| **캐시** | 인기 키가 만료되면 **한꺼번에 DB로 몰림** → [[2026-08-11-backend-cache]] |
| **팬아웃** | 유명인 한 명이 **시스템 전체를 마비** |

> **전부 "분포가 균등하지 않다"에서 온다.**

Step 1의 가정에 **"트래픽은 고르게 분포하지 않는다"** 가 맨 앞에 있는 이유가 여기서 드러난다. **그 한 줄이 설계 전체를 좌우한다.**

### 조회 설계 — 캐시에는 ID만

```text
① 메모리 캐시에서 타임라인 조회 → tweet_id, user_id만  — O(1)
② Tweet Info Service에 multiget → 트윗 상세          — O(n)
③ User Info Service에 multiget → 유저 상세           — O(n)
```

**Redis 리스트 구조**

```text
| tweet_id(8B)  user_id(8B)  meta(1B) | tweet_id  user_id  meta | ...
```

**17바이트씩**이라 수백 개를 넣어도 가볍다. 상세 정보를 다 넣으면 캐시가 터진다.

**multiget은 N+1 회피**다. 100개를 한 번에 가져오지 하나씩 100번 요청하지 않는다. → [[2026-08-05-backend-federation-sharding]]

### 추가 최적화 — "뜨거운 것만 비싼 곳에"

- 홈 타임라인마다 **수백 개 트윗만** 메모리 캐시에 유지
- **활성 사용자의 타임라인만** 캐시 (30일 비활성이면 SQL DB에서 재구성)
- Tweet Info Service에는 **한 달치 트윗만**
- User Info Service에는 **활성 사용자만**
- Search Cluster는 지연을 낮추려 **트윗을 메모리에 유지**

→ LRU 사고방식과 같다. [[2026-08-11-backend-cache]]

### 검색 설계

```text
① 쿼리 파싱/토큰화
   - 마크업 제거 / 용어 분해 / 오타 수정 / 대소문자 정규화 / 불리언 변환
② Search Cluster(Lucene)에 scatter-gather
③ 병합·랭킹·정렬 후 반환
```

토큰화 단계가 **LLM의 토크나이제이션과 발상이 같다**(텍스트를 검색 가능한 단위로 쪼갠다). → [[2026-07-29-ai-data-tokenization]]

### Pastebin과의 대비 — 규모가 설계를 바꾼다

| | Pastebin | Twitter |
|---|---|---|
| 초당 쓰기 | **4건** | **6,000건** (팬아웃 6만) |
| 저장소 선택 | 관계형 DB로 충분 | **NoSQL·메모리 캐시 필수** |
| 확장 | 캐시 + 읽기 복제본이면 됨 | **페더레이션·샤딩까지 필요** |
| 고유 문제 | — | **팬아웃, 셀러브리티** |

> **같은 4단계 절차를 쓰지만, 규모가 다르면 선택이 달라진다.** → [[2026-08-20-backend-design-pastebin]]
